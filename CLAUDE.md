This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Bun workspaces (`apps/*`, `packages/*`) orchestrated by Turborepo. Run from repo root unless noted.

```bash
bun install                 # installs all workspaces
bun run dev                 # turbo: starts apps/web (vite dev --port 3000, falls back to 3001+ if occupied — check the log's "Local:" line, don't assume 3000)
bun run build               # turbo: builds all workspaces
bun run test                # turbo: runs packages/core's bun test suite

# Database (packages/core, run through root turbo)
bun run db:generate         # drizzle-kit generate → packages/core/drizzle/*.sql
bun run db:migrate          # drizzle-kit migrate
bun run db:check            # packages/core/src/db/check.ts — `select 1` sanity check
bun run db:studio           # drizzle-kit studio
```

```bash
bun run auth:generate        # regenerates src/db/schema/auth.ts from packages/core/src/auth/index.ts.
                              # auth.ts is CLI-owned — never hand-edit it. Run this after changing any
```

Linting and formatting are repo-wide and run from the root. **Biome is gone** — `oxlint` lints and `oxfmt` formats:
```bash
bun run check                # oxfmt --check + oxlint — what CI runs
bun run typecheck            # turbo: tsc --noEmit in both workspaces — also what CI runs
bun run lint                 # oxlint only
bun run format               # oxfmt --write
```

Two root configs cover **both** workspaces, and each workspace's own `lint`/`check` scripts point back at them (`--config ../../oxlint.config.ts`) so the same commands work from inside either package. Both are root devDependencies — don't add a second copy to a workspace, since two versions format differently and the drift is invisible until CI disagrees with your editor.

- **`.oxfmtrc.json`** — formatting. Migrated from the old biome config with `oxfmt --migrate=biome`, so the house style is unchanged: tabs, double quotes, width 80. `sortImports` replaces biome's `organizeImports`, and oxfmt also formats JSON and CSS, which biome's `files.includes` allowlist had left alone.
- **`oxlint.config.ts`** — linting. Four layers:
  1. `plugins` + `categories.correctness` — the parity layer, standing in for what biome's `recommended` used to catch (react, react-hooks, jsx-a11y, typescript, import, oxc).
  2. **anti-slop** ([dmmulroy/anti-slop](https://github.com/dmmulroy/anti-slop), vendored at `tools/oxlint/anti-slop/` and registered as a `jsPlugins` entry. Fifteen rules that reject low-evidence TypeScript: `unknown` in a contract, a `Record<string, unknown>` value type, a hand-rolled `typeof` narrowing where a parse belongs, a type assertion with no stated invariant. **Every one is an `error` and the tree is clean of them.**
  3. **stella**, five rules vendored at `tools/oxlint/stella/` from [stella's `.oxlint-plugins`](https://github.com/stella/stella/tree/main/.oxlint-plugins) (Apache-2.0). That directory holds ~130 rules; these are the ones that survived being measured against this repo. Each guards an invariant the codebase already held with nothing keeping it that way: `no-vacuous-throw-assertion` (an argument-less `.toThrow()` passes for any thrown value, so it keeps passing once the code fails for an unrelated reason — it found five, four of them in `assistant.test.ts`), `no-document-cookie`, `require-suppression-description` + `no-foreign-directive` (the ratchet on the ~40 suppressions, and the thing that stops `biome-ignore` comments returning now that biome is gone), and `no-partial-record-satisfies`.
  4. A handful of named rules that are none of the above — see the comments in the file.

**Both plugins are vendored, not depended on — those files are ours to edit.** Four anti-slop rules carry a `Local amendment to the upstream rule` comment saying why: Zod's `.shape` is not a symbol this repo names; a `.catch()` handler's parameter is `unknown` because TypeScript makes it so; leading comments on an `export const` attach to the ExportNamedDeclaration, so the SAFETY lookup has to see through it. Read the comment before "fixing" one of these back. The stella rules were re-typed onto `defineRule` and share a trimmed `utils.ts`; provenance is in `tools/oxlint/stella/index.ts` so a re-sync stays a diff.

**The other ~126 stella rules were skipped, and mostly not because they are wrong.** They fall in three groups: stella-domain (matter glyphs, playbook verdicts, case-law boundaries) or aimed at a stack this repo does not run (Effect, Eden, i18n); already covered by anti-slop or a native rule; and — the interesting group — rules this repo simply passes. `require-query-key-factory` finds nothing because every key already spreads `queryKeys(org)`; `require-fetch-timeout` finds nothing because the one browser `fetch` carries a controller signal and `externalFetch` owns the rest; `require-timestamptz-column` only hits CLI-generated `auth.ts`. Two were skipped as noise rather than as wrong: `forbid-process-env-outside-env-ts` (69 reads across 23 files — that is a refactor, not a lint adoption) and `no-db-await-in-loop` (~20 sites, all already triaged, including the reminder-job loop this file documents as a deferred fix).

**Every suppression needs a reason.** `stella/require-suppression-description` fails the build on a bare `oxlint-disable`; the reason goes inline as a `-- <why>` trailer, or as a prose comment on the line directly above when it needs more than a clause. The directive must still be the **last** comment line either way, so the multi-line form reads explanation-then-directive.

**`SAFETY:` comments are load-bearing.** `require-safety-comment-for-type-assertion` fails the build on any non-`as const` assertion without one, so every remaining `as` in the tree states the invariant that makes it sound. A new assertion needs a real reason, not a restatement of the cast. Placement is fussy: the comment must be the line directly above the assertion **or** its containing statement, `//` not `{/* */}` (JSX comments are nodes, not comments), and a multi-line explanation must put the directive line last.

Tests have two helpers for the case that used to reach for an assertion — `at(rows, i)` and `present(value, what)` in `src/test/harness.ts`. Both fail the test naming what was missing, rather than turning a bad fixture into a null-dereference twenty lines later.

**57 warnings are expected and do not fail the build.** Fourteen are `typescript/no-non-null-assertion` (`process.env.X!` in the auth and drizzle configs, plus array-index assertions in two test files). The other 43 are pre-existing React and a11y findings that biome's ruleset never reported — `react/set-state-in-effect` (18), `jsx-a11y/no-autofocus` (10), `jsx-a11y/control-has-associated-label` (9), and a few others. They are real and deliberately left visible rather than switched off; promote each to `"error"` in `oxlint.config.ts` as it is burned down.

**One thing was lost in the move and is worth knowing:** nothing lints CSS any more. oxlint is JS/TS only and oxfmt only formats. `landing.css` carries a comment recording the two rules that used to be turned off for it and why both are right there.

## Architecture

Two workspaces today — `apps/web` (TanStack Start/React) and `packages/core` (`@farmer/core`) — but the split is deliberate, not incidental: `packages/core` is written to also be reusable by a future `apps/api` and `apps/mcp` process.

**Boundary rule:** `packages/core` never imports TanStack/React. All business logic lives in `src/services/`, one file per aggregate. Every exported service function takes an explicit `ctx: { organizationId, userId }` (`src/services/types.ts`) as its first argument — **tenancy is a parameter, never ambient** — so the identical function is callable from a server function, a REST route, a background job, or (eventually) another process.

`packages/core` layout:
- `src/db/` — `drizzle-orm/postgres-js` client (`index.ts`) + schema split across:
  - `schema/auth.ts` — better-auth-owned (user/session/account/verification/organization/member/invitation). CLI-generated, see `auth:generate`.
  - `schema/domain.ts` — client, project, **task**, projectTask, projectMember, recurringBlockRule(+Skip), timeEntry.
  - `schema/people.ts` — memberProfile, memberTypeHistory (effective-dated person type).
  - `schema/schedule.ts` — memberSchedule, memberWorkingHoursDay, disabledHoliday.
  - `schema/close.ts` — monthlyClose, monthlyCloseRow.
  - `schema/settings.ts` — integrationSettings, syncedMeetingTombstone, commitFillTombstone, filingRule, orgSettings, reminderSettings, monthlyHourFund, notOnInvoiceStatusOption, notOnInvoiceEntry.
  - `schema/github.ts` — orgGithubInstallation, projectGithubRepo, timeEntryGithubCommit.
  - `schema/slack.ts` — slackInstallation, memberSlackIdentity, slackReminderLog.
  - `schema/notifications.ts` — pushSubscription, notificationSettings, projectBudgetAlert.
  - `schema/import.ts` — importRun, importMapping (what each Harvest import created, so undo can remove exactly that).
  - `schema/assistant.ts` — assistantSettings, assistantConversation, assistantMessage. The pending-approval state (`pendingApproval`, `approvalSummary`, `approvalPreview`) lives on the message row, not on the connection — see The assistant.
- `src/services/` — the domain layer. Aggregates: access, account, assistant, clients, close, compliance, day-assembly, filing-rules, github, google-calendar, harvest-import, holidays, hour-fund, integration-settings, mcp, members, not-on-invoice, notifications, org-settings, organization, projects, recurring-block-rules, reminder-settings, reports, slack, tasks, time-entries, working-hours. Plus the shared, non-aggregate modules: `guards.ts`, `ledger.ts`, `unfiled.ts`, `notify.ts`, `reminder-recipients.ts`, `context.ts`, `db-ctx.ts`, `ports.ts`, `day-fill.ts`, `types.ts`, and the two tool registries `assistant-tools.ts` + `mcp-tools.ts`.
- `src/schema/` — Zod input schemas, one module per aggregate, genuinely shared across three call sites: the RHF form resolver, the server function `.validator()`, and the `api/v1` REST handlers. Range inputs carry their own ceilings (62 days for a time-entry range, 366 for a report), so a caller cannot ask for a full-table scan by widening the dates. Don't re-validate by hand at a new call site — that is exactly how `api/v1/time-entries` ended up bypassing the 62-day cap.
- `src/lib/` — `time.ts` (UTC-in/display-zone-out duration + timezone helpers on `date-fns`/`@date-fns/tz`; the only place timezone math should happen), `working-day.ts`, `day-plan.ts`, `automation-window.ts`, `org-time.ts`, `org-country.ts`, `slug.ts`, `email.ts`, `http.ts`, `single-org.ts`, `oauth-state.ts`, the integration clients (`github-client.ts`, `google-calendar-client.ts`, `slack-client.ts`), and the report arithmetic the browser also needs: `utilization.ts`, `report-period.ts`, `report-format.ts`. Also the two deployment flags (`assistant-flag.ts`, `mcp-flag.ts`), `dev-auth.ts`, `openrouter-client.ts`, `json.ts`. `harvest/` is the Harvest CSV parser and import planner — pure, because it runs in a browser Web Worker (see The Harvest import).
- `src/jobs/` — background work; exported as `@farmer/core/jobs`. `scheduler.ts` is the runner, `worker.ts` a standalone process entry; `automation-sync.ts`, `log-reminders.ts`, `slack-reminders.ts`, `budget-alerts.ts` are one tick of work each.
- `src/test/harness.ts` — `createTestDb()` gives each test file an empty, freshly migrated **PGLite** (real Postgres, in-process WASM) and points the `db` proxy at it for the file's duration. Service tests need no DATABASE_URL, no container and no cleanup. `src/db/index.ts` resolves its handle lazily for this reason. **One engine is shared for the whole run and re-schema'd per file**, because a `WebAssembly.Memory` never shrinks: per-file instances made the suite's footprint the sum of every database it had ever opened (~11GB across thirty files), which a laptop absorbs and a 7GB CI runner answers with SIGKILL. `bunfig.toml` preloads `src/test/preload.ts` to close that engine once at the end — a live handle at exit is exit code 99 and a red CI for a suite where nothing failed.

`apps/web` layout:
- `src/routes/` — TanStack Router file-based routing. `$orgSlug/route.tsx` is the org-scoped layout: its `beforeLoad` resolves the session, the organization and the caller's role in ONE server call (`enterOrganization`) alongside `getPublicAppConfig`, and redirects out if any check fails — every nested route inherits that guard. It was four sequential server-function round trips, one of them a session write that ran on every navigation; `enterOrganization` only repoints the session when the active org actually differs. Under it: `time/` (index/`week`/`month`), `projects/`, `reports.tsx`, `close.tsx`, and `settings/` (organization, members, my-schedule, clients, tasks, recurring-blocks, holidays, hour-fund, reminders, import, integrations, preferences). `login.tsx` is the sign-in entry point (a redirect into Google, except in development and on OAuth errors); `accept-invite/$invitationId.tsx` handles invitations; `no-access.tsx` breaks a redirect loop. `api/auth/$.ts` mounts better-auth; `api/login.ts` starts the Google flow; `api/github/setup.ts` and `api/slack/callback.ts` are OAuth redirect targets; `api/v1/*` are public REST read endpoints reusing the same services via `resolveApiOrgContext(request)`, which lives in `server/api-auth.ts` — deliberately NOT in `server/auth.ts`, see the client-bundle rule below. `reports.tsx` is the shell only; its eight tab bodies live in `components/reports/`.
- `src/server/` — thin `createServerFn` wrappers, one file per aggregate, mirroring `services/`. **Auth is attached via middleware** (`sessionMiddleware` / `orgMiddleware` / `orgAdminMiddleware` from `server/auth.ts`), read from the handler's `context` arg — not by calling `requireOrgContext()` inline. That makes the protection part of the function's declared shape rather than an easy-to-forget first line. Every file in `server/` uses them; `auth.ts` itself is the only place the bare helpers are called, because route `beforeLoad`s need them. `orgMiddleware` also re-checks membership against the database (see Authorization), and does so inside its `.server()` callback rather than in a shared helper — a top-level function body in `auth.ts` ships to the browser, so a deferred `import("@farmer/core/services")` there becomes a real client chunk of the services barrel, which `scripts/prune-client-assets.ts` then has to delete.
- `src/queries/` — TanStack Query `queryOptions` factories, one per aggregate; routes prefetch via loaders, components read via `useSuspenseQuery`. `queries/keys.ts` holds the root of every key family, and **every key names its organization**: `queryKeys(orgSlug).timeEntries`, so factories take the slug as their first argument (`timeEntriesRangeQuery(orgSlug, from, to)`) and components get it from `useOrgSlug()`, loaders from `params.orgSlug`. Factories spread their root and invalidations name the same one, so a write and the query it stales cannot drift. Never write a bare `queryKey: ["…"]` literal on either side, and never drop the org — an org-blind key is an answer from the previous workspace, which is what the layout route used to carry twenty lines of QueryClient-stamping and staged cache-purging to compensate for. Server functions are deliberately NOT generated from a shared declaration — see `docs/adr/0001-no-server-function-generator.md`.
- `src/components/ui/` — shadcn on **Base UI** (`@base-ui/react`), not Radix (`components.json` style is `base-nova`). Composition uses the `render` prop, not `asChild`.
- **Table search is one pair of modules, and it filters the view only.** `lib/search.ts` (`matchesSearch`) and `components/ui/search-input.tsx` back all 18 search boxes — every report tab, the close sheet, `projects/index.tsx`, and five settings lists (clients, holidays, members, recurring-blocks, tasks). The match is case- and accent-insensitive and hits any word in any field. **Totals and stats are computed over the full dataset, never over the filtered rows** — a filter narrows what somebody sees, not what gets summed, because a utilization figure that quietly tracked the search box is a wrong number rather than a filtered one.
- **Light/dark is `data-theme` on `<html>` and nothing else.** Both palettes are written out in full in `styles.css`; `lib/theme.ts` owns the attribute, and the DOM is the state — there is no provider and no second copy, because `themeInitScript` runs inline in `<head>` (see `__root.tsx`) long before React exists. It has to: the choice lives in localStorage, so the server cannot render it, and applying it on hydrate flashes the light palette on every cold load. That mismatch is why `<html>` carries `suppressHydrationWarning`. No stored choice follows the OS; one click outranks it from then on. The landing page reads the product's own tokens and follows the reader's theme like every other page (`landing.css`), and the calendar's category tints (`lib/category-colors.ts`) are still light washes computed in JS — they stay legible in dark mode but read bright.

**Critical, non-obvious rule:** never put a static top-level `import ... from "@farmer/core/db"` / `"/auth"` / `"/services"` in any route or `src/server/*.ts` file. `postgres` touches `Buffer` at module scope, which crashes hydration in the browser — silently: forms fall back to native submission instead of throwing. Always import inside the handler body:
```ts
export const createTimeEntry = createServerFn({ method: "POST" })
  .middleware([orgMiddleware])
  .validator(createTimeEntryInput)
  .handler(async ({ data, context }) => {
    const { timeEntriesService } = await import("@farmer/core/services");
    return timeEntriesService.create(context.ctx, data);
  });
```
This is also why `requireOrgAdmin` routes through the `getMyRole` server function instead of importing services directly — it's called from a route `beforeLoad`, which also runs client-side during SPA navigation.

### Authorization

**Two independent axes, and `services/access.service.ts` is the only place that knows the matrix.**

- **One global role:** org Admin (better-auth's `member.role` = `owner` | `admin`, both mapping to the single Admin tier). There is deliberately no super-admin.
- **A per-assignment project role:** `member` | `team_lead` | `pm` on `projectMember`. The same person is PM on one project and a plain member on another, so a project role is never a property of the person.

**Membership is a precondition, not a capability.** `accessService.resolve` throws `NotAMemberError` when the caller has no membership row, rather than describing them as "nobody" (`isAdmin: false`, no assignments). That was the right answer to every project-level question and the wrong answer to "are they in the room" — a Ctx is built from `session.activeOrganizationId`, which is stamped on when the workspace is entered and never revisited, so an ex-member's Ctx stayed valid-looking until the session expired, and every org-wide read that only filters on `organizationId` (`clientsService.list`, `tasksService.list`, `orgSettingsService.get`) answered it. `orgMiddleware` and `resolveApiOrgContext` resolve `Access` at the boundary for the same reason, which also warms the request's memo.

`accessService.resolve(ctx)` returns an `Access` — two queries, then answered from memory. Resolve it **once per request** via `ctxAccess(ctx)` (`services/context.ts`), which memoizes it on the Ctx; before that memo existed it ran 66 times across the codebase, several times per request.

The lines that matter: Team Lead gets visibility and team management but **never money and never close**; PM adds close and the two money fields; a Member sees strictly their own entries. `scopeFor(role)` returns `null` for admins meaning "unscoped" — callers translate that into no project filter rather than a 200-id `IN` list, and an empty array is a real answer meaning "nothing". Admins are **not** synthesised into a project role: `roleOn()` returns their real assignment so the close sheet's "your projects" filter still works.

`server/auth.ts`'s `getMyAccess` flattens this for the client to gate UI with. It is **not** authorization — every service re-resolves `Access` server-side and asserts.

Two gates that read as one and are not: `assertTaskAvailable` (guards.ts) asks whether a TASK may be used on a project; `assertCanTrackOn` asks whether this PERSON may write there. Anything that creates time entries needs both. `recurringBlockRulesService` had only the first, so a rule could name any project in the org and then materialize real hours onto it. It now runs both at create **and on every materializing pass** (plus project status and task archival), because a rule outlives the assignment, project and task that made it valid; a rule that no longer applies is skipped, not deleted.

### The month-end close

The anchor feature (`close.service.ts`), and the thing the numbers get invoiced from.

- One `monthlyClose` per project per month. Lifecycle: **Open → Submitted (PM) → Finalized (Admin)**. A PM may re-open and re-submit freely before finalization; an Admin may finalize even if the PM never submitted, and is the only one who may re-open a finalized month.
- Three columns per person: **Reported** (live sum of entries), **Adjusted** (the PM's reconciliation, null = displays as Reported), **Final** (Admin-only, null = displays as Adjusted). `effectiveAdjusted`/`effectiveFinal` are the fallback chain, and use `??` not `||` — an explicit zero is a real value.
- **Rows are a union**, not just the project's assignments: active assignments ∪ everyone who logged time on the project that month ∪ anyone already stored on the sheet. An unassigned contributor's hours silently falling off the sheet is a billing error.
- **Finalize snapshots Reported / Expected / Overtime.** Entries stay hand-editable in finalized months on purpose, so Reported keeps moving afterwards; the variance report compares Final against Reported *as it stood when Final was frozen*. Re-opening deliberately leaves the snapshots in place. **Final is different:** finalize materializes it, and a Final it filled in from the fallback chain is marked `finalDerived`, so re-open returns it to the chain and a PM's post-re-open Adjusted reaches the next finalize. A Final an admin typed (or a Harvest import wrote) is not derived and survives re-open. Reads never create a close record — a month nobody touched simply reports as Open.
- **Finalize refuses while anyone has unfiled time.** The one hard stop: freezing a month while hours are unattributed means that time later lands on a month already closed against a number that predates it. Deliberately not enforced on `submit`, since only the person themselves can file their own time and blocking the PM would leave them stuck.
- **Expected** = `monthly fund − (absence days × 8h)`, and only on `product_team` projects. Null — never zero — when there's no fund yet or the person is a contractor without an override. `absenceDaysOverride` lives on the sheet only and never writes back to entries: divergence is the signal that someone forgot to log absence.

### The ledger

`services/ledger.ts` is the one definition of what counts as logged time. Fifteen hand-rolled `sum(durationSeconds) … groupBy` queries used to spell this out separately across reports, close, compliance and projects; three disagreed, visibly, in the UI.

What may vary between callers is the **projection** (columns, joins, grouping key). What must not vary is the **classification** and the tenancy/range predicate. So `ledgerWhere` owns the predicate and `LedgerScope` the vocabulary: `worked`, `project`, `unfiled`, `absence`, `all`. Callers with a bespoke projection compose `ledgerWhere` rather than being forced through a grouped API; close and reports now do so everywhere, so there is no hand-rolled copy of the predicate left.

**A day holds at most 24 hours** (`MAX_DAY_SECONDS`, `lib/working-day.ts`). Every manual write that grows a day checks it and throws `DayCapacityError`: create, update, the week grid, copy day/week, day assembly and the PM absence writes. An edit that does not grow the day is allowed even on a day already over. The engines are exempt, since a fill block is sized from the remainder and a synced meeting mirrors the calendar.

**Unfiled** = worked time with no project yet (a synced meeting, a commit fill block, an accepted assembly suggestion) — real work, not yet attributed, therefore a to-do. Absence is not unfiled (it never carries a project by definition), and neither is a project-less **Break** — nobody bills a client for lunch, so counting it nagged people to file something unfileable and blocked the close on it.

### Automation

**`jobs/automation-sync.ts` is where every entry nobody typed comes from** — recurring blocks, calendar meetings, commit work-time blocks. These used to run inside `timeEntriesService.listRange`, i.e. **on page load**, which meant a read did writes whose extent depended on whichever screen was open; scrolling the Month view back filed months of entries into already-closed timesheets. The per-user pass is `timeEntriesService.runAutomationsForUser`, and its **order is load-bearing**: a commit fill block is sized from what the day already holds, so recurring blocks must materialize first. It reports `ran`/`skipped`/`failed` separately — an engine whose window came back null did nothing, and folding that into success is what let "Sync now" claim it synced after touching nothing. The sweep runs `AUTOMATION_SYNC_CONCURRENCY` people at a time behind a per-person timeout. Archived people are not swept: their meetings would otherwise keep landing as unfiled time and block the close on every project they are still assigned to. "Sync now" shares the sweep's per-person guard and timeout, so the two never run one person twice at once.

**`lib/automation-window.ts` is the one window policy**, and the only place any of the three engines may learn how far it reaches: `to` is today in the **org** timezone (never the future — a row on a day nobody has lived counts in reports and gets rewritten underneath them), **or yesterday under `completeDaysOnly`**; `from` is the latest of `today - AUTOMATION_GRACE_DAYS`, the day the switch was flipped, and the day after `orgSettings.automationLockedThrough`. The `*_since` stamps alone were not enough: a stamp is a floor, not a window. Grace is a **downtime recovery budget**, not a backfill policy — every day inside the window is a day whose sync-owned rows can still be rewritten from the source. `completeDaysOnly` belongs to the commit engine alone: its block claims the rest of the working day and is sized from the day's *whole* target, so run against today a 09:15 commit produced a 7.5h block at 09:20 that `onConflictDoNothing` then froze.

**`automationLockedThrough` (org settings) locks the robots, not the people.** Entries stay hand-editable in finalized months on purpose, so this is deliberately narrower: the last day no *automation* may write to. Not made redundant by the short grace window — for the first days of every month that window reaches into the month just reconciled and invoiced. A single watermark rather than a per-month lock table. A failed read of it fails the whole pass rather than defaulting to unlocked. The meeting engine honours the window in both directions: a synced row dated before the window is never moved or rewritten, even when Google now reports the event on a later day, and an event dated outside the window is not written at all. The commit engine likewise drops any commit day outside its range, because GitHub filters on committer date while the engine buckets by author date, and a rebased branch carries old author dates.

**The commit engine attaches before it creates.** Commits are *evidence*: `syncCommitWorkTimeForRange` resolves a target per project (that project's work entry → the day's fill block → a project-less Development entry) and only files a rest-of-day block when commits found no home at all. Welding the two together meant a person who had already logged their day properly lost the commits entirely — the best-behaved case was the one that dropped data. Blank descriptions are backfilled from commit subjects; non-blank ones are never overwritten. When a fill block empties and is dropped (`recomputeDayFill` or `listRange`), `rehomeDroppedFillCommits` (`day-fill.ts`) first moves its commits to the same fallback target, because the attachment rows would otherwise cascade away with the block.

**`dayAssemblyService.suggest` takes `includeDismissed`** — the toggle that re-offers meetings and rest-of-day blocks the person deleted. Tombstones are what stop the engines rebuilding them, which is right by default and a dead end when the deletion was a mistake. Re-offered suggestions carry `dismissed: true` so the dialog renders them **unticked**.

**`filing-rules.service.ts` is the standing answer to "which project does this meeting belong to".** A synced meeting lands project-less on purpose and the File-your-time dialog is where it gets attributed — right for the one-off, wrong for the weekly stand-up, which is fifty rows a year of one answer. A rule is created by ticking "Always file these here" in that dialog, and `syncMeetingsForRange` applies it at write time so the occurrence never appears as unfiled at all.

Four things about it are load-bearing. It is keyed on **(task, normalized title)** — not on the calendar event or series, because a series cancelled and recreated is a new event id but the same decision, and not on duration, because a stand-up that ran long once is still the stand-up. **An empty description cannot carry a rule**: the dialog falls back to the task name for display, so a rule keyed on `""` would claim every untitled meeting the sync imports — the one-default-project behaviour this exists instead of. The rule is derived by `rememberFrom` from the entries `fileMany` actually filed, so the client cannot ask for a standing rule about time it did not just attribute. And `resolveForTask` **re-checks `canTrackOn` + `assertTaskAvailable` + project status on every pass**, because a rule outlives the assignment that made it valid — a rule that no longer applies is dropped silently and the entry lands unfiled, which is where it would have been anyway.

A rule-filed row stays `syncLocked = false`. The rule decides where the time goes, not who owns the row, so Google is still the source of truth for the meeting's title, length and existence and a cancelled one still disappears. Taking ownership is what filing **by hand** means (`file` sets `syncLocked`), and that is a different act from having pre-answered where it goes. Rules are listed and removed under Settings → Preferences; removing one leaves the entries it already filed alone.

Two engine details that differ and should stay differing: the MEETING path upserts with `onConflictDoUpdate … setWhere syncLocked = false`; `onConflictDoNothing` guards the COMMIT path.

### Tasks

The task taxonomy replaced the old "entry types". One global list per org (`scope: "organization"`) plus **site-scoped built-ins** shared by every org. Projects cherry-pick org tasks via `projectTask`; there is deliberately no project scope.

Engines resolve tasks by **`systemKey`**, never by name (`meeting`, `development`, `break`, `vacation`, `sick`). The old lookup matched `name = 'Development'`, so an org renaming the task silently switched the whole engine off — no block, no error. Names stay freely editable.

`guards.ts` treats any site-scoped non-absence task as universal — available on every project without being picked. Requiring an admin to add Meeting to each project meant forgetting it on one made that project unable to accept the calendar sync's own entries.

### The Harvest import

An admin drops the Harvest CSV exports on Settings → Import (`settings/import.tsx`); `harvest-import.service.ts` writes them. The design and the owner's decisions are in `docs/plans/harvest-import.md`.

- **Parsing and planning run in the browser, in a Web Worker** (`components/import/harvest.worker.ts`, on `packages/core/src/lib/harvest/`). A real export is ~240k rows: the Worker keeps the day chunks and the page holds only the review, because a structured clone of every row on each re-plan would freeze the tab. The server takes the plan in steps — `start` (clients, tasks, people, projects), `importDays` in chunks of `HARVEST_CHUNK_MAX_ROWS`, `removeDays`, `finish` — and every step is safe to repeat, so "Retry" continues from the cursor. `start` is made repeatable by a run id the browser generates once per attempt: a second `start` with the same id returns the run it already created, because a committed `start` whose response was lost used to leave an orphan `started` run that blocked undo of the previous one.
- **The unit is a person-day, compared by digest.** A day already imported unchanged is skipped, a changed one replaced, and a day somebody edited here is **kept**, never overwritten. A day the file no longer has is removed only when the admin confirms the file is a full export. That is what makes dropping the same files twice a no-op.
- **`finish` writes finalized history closes (Final = Harvest billable hours) and moves `automationLockedThrough` to the day before the cutoff**, so no engine writes into imported history.
- **A guessed email makes an archived person with `emailUnconfirmed`.** A Harvest person with no address gets `first.last@domain`; they cannot sign in until an admin confirms the address on People (Restore for an archived person, "Confirm email" for an active one), since a wrong guess is otherwise somebody else's login. An address the admin **typed** on the review screen is not a guess: it counts as confirmed (`emailConfirmed` on the person plan).
- **`finish` rewrites only the project-months this run covered**: a month in this file's billable input, a month holding a day this run imported or replaced, or an import-made close whose stored Reported no longer matches its entries. It used to regroup every imported entry through `historyThrough` and write `Final = 0` for any month the file lacked, so a re-export filtered to one year zeroed every older close. A non-billable month is sent as an explicit zero, so a missing figure means "this file does not have it".
- **Undo also refuses when an import-made close was changed here afterwards**, by the same "changed since" test `finish` uses.
- **Undo removes exactly what `importMapping` says the run created** — and only for the latest run. It does not restore days the run replaced, does not rewrite a close back, does not move the lock back, and refuses outright once a created person has signed in, an entry made here uses a created row, or a month on a created project was closed here.
- **Two questions block the plan until the admin answers them on the review screen**, because neither has a safe default:
  - **Names that differ only in accents or punctuation** ("Ive Vasiljević" / "Ive Vasiljevic") — one person or different people (`choices.duplicates`, keyed on the ASCII fold). "One person" merges the spellings into the chosen one, and the other gets an `alias` person plan: `start` maps it to the same user, not `created`, so undo removes only the mapping. A group whose every spelling an earlier run mapped is not asked again — one user is one person, two users stay two.
  - **Negative correction rows** — `subtract` takes each off the row with the same person, day, project, task and overtime flag (an exact match first, then the largest), rounds the rest again and gives it a new `…:net` key; `leave_out` imports the other rows as they are. The keys differ, so changing the answer later replaces those days on the next run. A correction with no row big enough to take from stays under "needs attention" either way.
- Rows of two source people who are one user here (an alias, or two names matched to one member) are one person-day in the plan, as `importDays` groups them, so the digest covers the same rows as the stored one.

### Notifications

`services/notify.ts` — `notify(recipient, event)` is the single way anything tells a person anything. The recipient is always an `(organizationId, userId)` pair, so membership is checked on every channel; a `KINDS` table says which channels a kind uses and which `notificationSettings` column gates it. Adding a channel is one adapter plus one row in that table. Never throws — it returns which channels delivered. Substitutable via `setNotifyAdaptersForTests`. `notificationsService.sendPush` is the push *transport* and is not a call site: push subscriptions belong to a device, so nothing there can know which org is speaking.

**Reminders are configured per org on Settings → Reminders** (`reminderSettingsService`: `get`, `update`, `preview`; design in `docs/plans/reminder-settings.md`). A missing `reminderSettings` row is the defaults, which reproduce the old fixed schedule. Who gets a reminder is decided in one place, `services/reminder-recipients.ts`, which both jobs and the preview call — so the preview cannot disagree with what the job then sends.

- **`KINDS` rows carry a `reminder` flag, and `deliveryBlocks()` holds reminder kinds back from archived people and people who have never signed in** (no `account` row). Budget alerts are not reminders and are not blocked. A test person therefore needs an `account` row to receive a reminder.
- **Both jobs read org-level state once per org**, not once per member, and both take `{ now }`. The Slack job ticks every 15 minutes, skips a kind that already ran today or is not due before any heavy query, and checks the delivery gates before it claims `slackReminderLog` — so a blocked person does not burn the day's claim. `forgetSlackReminderRunsForTests()` clears its in-memory record of the day's runs.
- **`nudgeBehindPacePct` is one number** for the nudge, the month-end "only behind" option and the digest; the admin compliance report keeps its own 0.9. `complianceMissingDays` stays on `orgSettings` because that report reads it too.

### Ports and outbound calls

`services/ports.ts` — `calendarSource()` / `commitSource()`, the substitutable seam the sync engines read through. Production adapter is the real service; tests install an in-memory one via `setCalendarSourceForTests`.

**`lib/http.ts` (`externalFetch`) puts a deadline on every outbound call.** `fetch` has no default timeout, and the sweep awaits users behind a `running` flag that refuses a new tick while one is in flight — so one wedged socket to Google didn't degrade the sweep, it *ended* it silently until restart. `withTimeout` is the same idea one layer up.

### Authentication

**Google is the only identity in production, and there is no login page there.** `emailAndPassword` is off, so there is no form to render and nothing to choose — "log in" is a redirect.

- **`routes/api/login.ts` is the sign-in surface.** A server route: it asks better-auth for the Google authorize URL and re-shapes that 200-plus-`Location` response into a real 302, copying the OAuth state/PKCE cookie across. Server-side rather than a client `authClient.signIn.social()` call so an unauthenticated document request reaches Google without the app hydrating at all.
- **`routes/login.tsx` stays a *page* route on purpose**, even though it renders almost never. Every `redirect({ to: "/login" })` and sign-out points at it, and a page route's `beforeLoad` runs both server-side and in the browser; `redirect({ href, reloadDocument: true })` turns either into the full-page hop `/api/login` needs.
- **Two cases render instead of redirecting.** `?error=…` — better-auth's `errorCallbackURL`, most usefully the single-org invite-only gate; that branch must not redirect, or an uninvited visitor bounces between `/login` and Google forever. And development, below.
- **`lib/dev-auth.ts` turns email + password back on off-production.** The gate is `NODE_ENV !== "production"` and deliberately **not** an opt-in env var: an opt-in flag is the kind of thing that gets copied from a `.env` onto a server, and this is the one feature where that mistake is a second way into the product. Both the Dockerfile and `apps/web`'s `start` script pin `NODE_ENV=production`, so every supported way of serving this app has it off; a fourth way of hosting it must set the variable too. Downstream nothing is special-cased — the same `databaseHooks.user.create` hooks bootstrap the org and seed its tasks, and single-org mode's invite gate still applies to a password signup. The client learns it from `getPublicAppConfig().devAuth`, which is also what hides Preferences → Sign-in methods in production: with no endpoint that can set a password and no way to unlink your only identity, both rows were permanently disabled.
- **`/` never redirects, in any mode.** Single-org mode used to bounce every visitor to their workspace and, signed out, on through `/login` to Google — so a deployment had no reachable front door at all: no address that answered with a page, and nowhere a sign-in screen offering anything but Google could live. The homepage now renders for everyone and its CTA resolves the destination (workspace / `/no-access` / `/login`).
- **`prompt: "select_account"` on the google provider is deliberate.** With no login screen there is nowhere to offer "use a different account".
- `session.freshAge: 0` — better-auth 403s `SESSION_NOT_FRESH` on unlink-account once a session is older than a day, and this app has no step-up re-auth flow, so integration disconnects would break.
- Invite context rides through as query params and is rebuilt into the Google `callbackURL`. `redirect` is attacker-supplied in principle, so `api/login.ts` accepts only a same-site absolute path (`/…` but not `//…`).

### Integrations (GitHub + Google Calendar + Slack)

GitHub and Google Calendar are per-member and opt-in via `integrationSettings` (a missing row = every toggle off, so connecting an account never silently enables background sync); Slack is per-org and admin-only. All three live on `$orgSlug/settings/integrations`, which renders admin-only sections behind `role`.

- **GitHub uses two distinct credential types, don't conflate them.** The per-user OAuth account link (`socialProviders.github`) is used **only for identity** — it touches exactly two endpoints, `GET /user` (resolve the login, to filter commits by author) and `GET /user/installations` (enumerate installations the person may connect). All actual repo/commit reads go through a **per-org GitHub App installation token** (`orgGithubInstallation`), obtained after an admin installs the App and GitHub redirects to `api/github/setup.ts`, which re-verifies admin role and resolves the org from a signed `state` (`lib/oauth-state.ts`). The state binds the org, the user and an issue time, and expires after 15 minutes. The Slack callback refuses any request without a valid one: it used to fall back to the session's active org, which let an attacker hand an admin a callback URL that installed the attacker's workspace. GitHub setup falls back only when no state was sent at all, because an App installed from GitHub's own UI arrives that way, and it is safe there because `connectInstallation` re-verifies the installation against the caller's own GitHub account. Repo reads are scoped to the caller: `attachCommits` requires an assignment on each repo's project and a hex `sha` (GitHub's `/commits/{ref}` accepts a branch name), and listing every repo the App reaches is admin-only. Env: `GITHUB_CLIENT_ID/SECRET` (OAuth) are separate from `GITHUB_APP_ID/SLUG/PRIVATE_KEY` (the App; private key is base64-encoded PEM).
- **The `repo` scope on that OAuth app looks removable and is not.** It is a broad grant (read *and* write on every private repo the person can reach) that reads no repo content in this app, so it reads like a leftover — but GitHub documents `GET /user/installations` as working only for OAuth/classic tokens carrying `repo`, and that call is the authorization gate in `connectInstallation` (you may only attach an installation you actually administer). Removing it breaks GitHub App connection for anyone who links their account afterwards. The real fix, if the grant is ever judged too broad, is to issue a GitHub App *user access token* instead of using a classic OAuth app — a provider change, not a scope edit. The comment at the call site says all this; read it before touching the line.
- **Google Calendar** is a per-user grant scoped to `calendar.events`, and lives on a **separate `genericOAuth` provider (`"google-calendar"`)** rather than on the login provider — so signing in never demands calendar access, and a plain login row can't be mistaken for a live calendar connection. It needs `accessType: offline` + `prompt: consent` to get a refresh token, or reads break after the ~1h access token expires. `syncedMeetingTombstone` records meetings the user deleted post-sync; `commitFillTombstone` is the same idea per *day* for the commit engine's rest-of-day block, which previously had nothing but the one-fill-per-day index — an index the deletion itself cleared, so the block came straight back. Creating a fill block deliberately clears the tombstone, since that is a change of mind.
- **Slack** is one workspace per org (`slackInstallation`), installed by an admin through Slack's OAuth v2 flow. The bot token is written straight to the database — no client, form or validator ever handles it, and no server function returns it. The redirect URI is derived once in `slackRedirectUri()` because Slack byte-compares it across the two legs. Membership hooks (`afterAcceptInvitation`, `afterAddMember`) auto-match new people to Slack; `linkMember` swallows its own errors, so a Slack outage costs the match, not the membership. Env: `SLACK_CLIENT_ID/SECRET`.

### The assistant

An OpenRouter-backed chat page (`$orgSlug/assistant`) that answers questions about tracked time and can log more of it. `services/assistant.service.ts` is the agent loop; `services/assistant-tools.ts` is what it may do.

- **Every tool is an adapter onto an existing service, called with the CALLER'S own `Ctx`.** That is the whole authorization story and it is deliberately not restated per tool: a Member's `list_time_entries` returns their own rows because `listRange` filters on `ctx.userId`, and their `create_project` is refused because `canCreateProjects` says so. Tool parameters are the *existing* Zod inputs from `src/schema/*` via `z.toJSONSchema()`, so the model inherits the same ceilings the UI has — hand-writing a JSON Schema per tool is how `api/v1/time-entries` lost the 62-day cap.
- **Three tool tiers, and the line is "can they undo this by asking for the opposite".** `read` answers; `write` (logging and correcting time, booking absence, reconciling a close row, creating clients/projects/tasks) runs inline; `destructive` (deleting an entry, archiving anything, finalizing or re-opening a month) suspends for approval. Asking before every write turned "reconstruct my week from my commits" into fifteen dialogs, which is the interaction the feature exists to replace. The two close transitions look like one decision and are two: `close_submit` is a write because a PM may re-submit freely, while `close_finalize` is destructive despite deleting nothing — it freezes the snapshots the variance report and the invoice are read off, and re-opening deliberately leaves them in place.
- **`toolDefinitions(access)` is scoped to the caller, and that is not the authorization.** The service behind each tool re-resolves `Access` and asserts; `AssistantTool.available` only decides what the model is *told* it can do. Every definition is re-sent on every step of every turn, so offering a Member the close sheet and the admin reports is a standing token cost plus a step spent being refused. Predicates stay coarse ("is a PM anywhere", never "on THIS project") because the arguments don't exist when the list is built — narrowing them would be the second copy of the §4 matrix.
- **A tool's arguments must be producible by some read, or it is uncallable.** `file_time_entries` takes entry ids and, for months, nothing returned any: `unfiled_summary` only counted them and `list_time_entries` reported a null project for absence too. Hence `list_unfiled_entries`; hence `list_commits` returning `projectGithubRepoId` + `sha` for `attach_commits`, and `list_tasks` including the absence tasks `listSelectable` excludes by design, which is what `log_absence` needs.
- **`assistantSettings.systemPrompt` is house rules an admin appends**, fenced in `<house-rules>` and explicitly ranked below the built-in prompt. Not a security boundary — an admin already holds the key — but a precedence one: the base prompt encodes domain facts (quarter-hour granularity, ids are looked up not invented) that stay true whatever conventions an org layers on.
- **Destructive tools suspend the loop for approval, and the pending state lives on the message row** (`assistantMessage.pendingApproval` + `approvalSummary`), not on the open SSE connection. Approving is a *second* `run` call that resolves it, so a tab closed mid-approval leaves a card that still works on reload. `approvalSummary` is stored rather than recomputed because it comes from `assistant-tools.ts`, which imports the services barrel and so can never reach the browser — and because it is the wording the person actually consented to. `summarize` takes the Ctx and may look its argument up, since "Archive project 3f2a9b1c…" is no more consentable than "archive a project"; it is best-effort and falls back rather than throwing, because a card that failed to render leaves a pending write nobody can answer either way.
- **A batch write suspends once and is approved row by row.** A tool that supplies `preview` (today `apply_day_assembly` and `file_time_entries`) stops the turn like a destructive one, and its card is a table of what it would touch; `withSelection` rebuilds the arguments from every row EXCEPT the ones the person unticked, so "yes to four of these five" has a spelling that approve/reject alone does not. It is phrased as exclusion because the card shows at most 25 rows: phrased as inclusion, approving a 40-row batch wrote 25. This is not the fifteen dialogs the `write` tier avoids — fifteen rows in one card is one decision. The rows are stored on the message (`approvalPreview`, including whether they were tickable) for the same reason `approvalSummary` is: they cannot be rebuilt in the browser, and re-reading them after the write would show today's data rather than what somebody consented to. Approving with an empty selection is a refusal, not a write of nothing.
- **A message typed past a pending card is a "no" to it.** The server writes a decline result for every unanswered call and clears `pendingApproval` BEFORE it stores the user message; stored in the other order, the history became `assistant(tool_calls) → user → tool`, which 400s on every later turn. `toWireMessages` also repairs threads already stored that way. The composer is disabled while a card waits, as a courtesy on top of that. Approval claims the call atomically (`claimCall`, a row lock plus a re-read), so two tabs approving one card run the tool once, and each suspension overwrites `approvalSummary`/`approvalPreview`, so the second destructive call of a turn is described in its own words.
- **A rejected tool call still writes a `tool` message.** An assistant turn carrying `tool_calls` must be followed by one result per call id or the next request 400s, so "no" has to be an answer rather than a silence.
- **`components/assistant/answer.tsx` is the hand-rolled reader, and the prompt's formatting rules are its mirror.** Paragraphs, `#`–`###` headings, bullet and numbered lists, bold/italic/inline code, links, `---`, fenced code, and GFM pipe tables with column alignment. Beyond markdown it understands three directives, all of which the model is told about verbatim in `systemPrompt`: `[[YYYY-MM-DD]]` renders as a link to that day's timesheet (the cheap half of citations — the expensive half is every figure carrying its entry ids, which is a change to what every report returns), and fences tagged `farmer-chart` (a fixed two-form chart, `answer-chart.tsx`) and `farmer-next` (follow-up chips). A construct promised in the prompt and missing here renders as its own syntax, so the two files change together. Everything re-parses on every streamed delta, so half-arrived input must degrade rather than throw — a malformed chart falls back to a visible code block instead of taking its numbers with it. Two rules there are recoveries from a small model's sloppy markdown rather than grammar: a fence whose body is *nothing but* a pipe table is read as that table (a fence is what a model reaches for when a wide column looks ragged to it, and the result on screen is the raw pipes this reader exists to prevent), and `farmer-next` is read whether or not its closing fence arrived — it is the last thing in the answer and so the first casualty of a turn that stops a token early. Both recover from a wrapper the model ADDED; neither can invent a directive it never wrote, which is why the prompt spells the chip fence out as literal characters. **A table's columns are measured, not just aligned** (`measureColumns`): `table-layout: auto` shrinks every column towards its min-content width in proportion to what it asked for, and a browser breaks `2026-08-28` at its hyphens to get there — so a date folded onto two lines beside a description column that had room to spare. Every column of 28 characters or less is pinned `nowrap`, which makes the whole shrink land on the prose column that can absorb it; if no column is prose, nothing is pinned, since a table of fifteen short columns has nothing to absorb anything and wrapping beats a scrollbar. The prose column also carries a `22ch` floor, which only bites on a phone: five columns cannot fit there, and without it the one column allowed to shrink collapses into a two-word ribbon forty lines deep, while every short column keeps its full width. A delimiter with no colon now parses as `null` rather than as `left`, which is what lets a column of numbers be set right and in tabular figures without overriding a model that asked for something else.
- **The transcript is a swap, a pin and a bleed, and each is load-bearing.** Opening a thread crossfades through the app's own `FadeSwap`, keyed on the LOADED thread rather than on the URL — the query keeps the thread you were reading on screen (`placeholderData`) until the one you clicked arrives, so a switch is one transition instead of thread → the empty hero → thread. `PinToEnd` lands the new transcript at its newest message: it lives *inside* the swapped panel because a layout effect on the page would run on the frame the URL changed, which scrolls to the end of the thread you just left. After that a ResizeObserver holds the end — height arrives later than state does (tables lay out, fonts swap, an answer streams) — but only while `pinnedRef` says the reader is near the bottom, so an answer arriving while they are three screens back does not haul them down. The route's loader awaits the thread on the SERVER and only warms it on the client: a link opened cold has no screen to preserve and may as well arrive whole, while a click already has one, and blocking there would trade a readable page for a pending one. And `.answer-wide` (styles.css) is what lets a table or a chart out of the 46rem reading column, up to the transcript's own width — `align-self`, never `margin-inline: auto`, since auto margins take the free space before alignment is consulted and resolve to zero once it is negative, which reads as a wide table hanging off the right of the screen.
- **`bun run db:seed-assistant-ui` (packages/core) seeds a "UI kitchen sink" thread** holding every construct above plus a live suspended approval, so the renderer can be looked at without spending a model call on it. Idempotent by title; dev only.
- **The turn streams over a server ROUTE** (`routes/api/assistant/stream.ts`), not a `createServerFn` — a server function resolves to one value. It is rate-limited per user (`server/assistant-rate-limit.ts`, 20 turns a minute), since one turn is up to eight billed model calls on the org's key, and it passes only the app's own error classes to the browser; anything else is logged and replaced with a generic message. It authenticates through `server/api-auth.ts`, not `server/auth.ts`, for the client-bundle reason described above.
- **`lib/openrouter-client.ts` passes its own timeout.** `externalFetch`'s 15s default is an `AbortSignal.timeout` on the whole request, and a streamed answer is not complete until the last token — at 15s it doesn't fail to connect, it guillotines a working answer mid-sentence.
- **Three switches, all different.** `ASSISTANT_ENABLED=false` (env, default on) is the operator taking the feature off this deployment: no nav row, no route, a 404 from the stream endpoint, and every service path refused — except `settings.disconnect`, deliberately, so a key stays removable after the feature is switched off. `assistantSettings.enabled` is an admin pausing it for one org. A missing `assistantSettings` row is "never connected". A plain env var rather than `VITE_` for the same reason as `SINGLE_ORG_SLUG`; the client learns it from `getPublicAppConfig`.
- **The nav reads all three, not just the env one.** `$orgSlug/route.tsx` resolves `assistantAvailable` (deployment flag AND connected AND not paused) and hands it to both navs, so a paused or never-connected org has no Browse/Chat tabs in the sidebar and no Assistant row on mobile. Gating only on the env var left a Chat tab whose destination was a page explaining that the assistant isn't connected. The layout's loader warms `assistantSettingsQuery` so the tabs are settled on first paint rather than appearing and then vanishing; the ROUTE still renders its "ask an admin to connect this" screen, because someone who typed the URL deserves the explanation.
- **Model choice is admin-only.** There is no picker in the chat and `createConversationInput` carries no `model` — a conversation pins `assistantSettings.defaultModel` as it stood when it started, so changing the default never re-answers an old thread.
- The OpenRouter key is per-org, admin-set, and follows the Slack bot token's rule — written straight to the database, never returned. `settings.get` answers with a leading-characters-only hint (`sk-or-v1-abc123••••••••`); deliberately not the card-style last four, since the tail is the unguessable part.

### The MCP server

The same tool layer as the assistant, over Streamable HTTP, for Claude Code and any other MCP client (`apps/web/src/routes/api/mcp/$orgSlug.ts`). There is no second registry and no second authorization story: `assistant-tools.ts` is the surface, every tool runs a service with the caller's own `Ctx`, and each service re-resolves `Access` and asserts.

- **The organization is in the URL, and it has to be.** An access token resolves to a `userId` and scopes — there is no `session.activeOrganizationId` for it to carry, and every Ctx needs an organization. `/api/mcp/$orgSlug` matches the service layer's own rule that tenancy is an explicit parameter, and gives somebody who works in two workspaces two connector entries rather than a mode they must remember they are in. The alternative is an `org` argument on all 52 schemas, saying what the URL already said.
- **`mcpService.resolveOrgContext(userId, orgSlug)` is the only membership check in front of the whole surface**, and it lives in `packages/core` rather than the route because it is a domain question and because it is the one part of this worth testing (`services/mcp.test.ts`). The route keeps what only it can know — which credential was presented — in `resolveMcpOrgContext` (`server/api-auth.ts`), which accepts the session cookie or an MCP bearer token. A slug nobody owns and a slug the caller is not in are the same answer, so a valid token cannot be used to enumerate workspaces. **An MCP token outlives a membership by much more than a session does**: it sits in a config file until somebody revokes it, which is why this check is the thing that decides whether the URL still answers.
- **Every tool is exposed, and the three tiers become annotations.** `mcp-tools.ts` maps `read` to `readOnlyHint` and `destructive` to `destructiveHint`; the client decides what to prompt about. So the assistant's approval CARDS do not survive the trip: the two batch tools (`apply_day_assembly`, `file_time_entries`) lose their row-by-row card and are all-or-nothing writes here. `toolsFor(access)` still scopes the list, for the same reason it does in the assistant — a stored connection outlives the role that made it.
- **`packages/core` holds no MCP SDK import.** `mcp-tools.ts` returns plain objects; the SDK is deferred inside the route handler, because `routeTree.gen.ts` imports every route module statically and a top-level SDK import would ship it to the browser.
- **Its own switch, deliberately not the assistant's.** `MCP_ENABLED=false` (env, default on, `packages/core/src/lib/mcp-flag.ts`) 404s the endpoint — 404 and not 403, since there is nothing there to be authorized for. `ASSISTANT_ENABLED=false` must leave MCP working: the two features share a tool registry and nothing else, and an operator who switched one off has said nothing about the other. Settings → Integrations shows the connection URL when the flag is on, and it is not admin-gated — a connection is a person's own.
- **better-auth is the authorization server** (`mcp({ loginPage: "/api/mcp-login" })`), and it ships without a consent screen: the client is the person's own editor, and the token grants exactly what they can already do in the UI. Three tables (`oauthApplication`, `oauthAccessToken`, `oauthConsent`) and dynamic client registration come with it. The two discovery documents are real routes under `routes/[.]well-known/`, not handlers in `server.ts` — `vite dev` never loads `server.ts`, so they would exist only in production. `routes/api/mcp-login.ts` rebuilds the authorize URL and hands it to `/api/login?redirect=…`; it exists so neither `login.tsx` nor `api/login.ts` has to widen its search schema to eight OAuth parameters, and getting it wrong fails as an infinite redirect rather than an error.
- **In-memory rate limits, per process, in two layers** (`server/mcp-rate-limit.ts`). Per user: 300 requests and 30 writes a minute. Per caller address, and this one needs no I/O: 1,200 requests and 30 failed-credential requests a minute, counted by `admitMcpCaller`/`recordMcpAuthFailure` **before** any session or token lookup, so an unauthenticated flood costs no queries. The address comes from the proxy's headers (`cf-connecting-ip`, then `x-real-ip`, then the first `x-forwarded-for` hop), so a deployment whose proxy does not overwrite them lets a caller pick its own key — which weakens that layer to a per-*claimed*-address limit, with the per-user one still behind it. Per-process is correct here for the same reason `startSchedulers` is — this deployment is one instance. An agent loop asks much harder than a person does, which is also why the `listRange` write-on-read below matters more through this endpoint than through `api/v1`.

### Single-organization mode

Setting `SINGLE_ORG_SLUG=<slug>` turns a deployment into a one-workspace, invite-only instance. Unset (the default) is the normal multi-tenant product, and every code path below is a no-op. It is a slug rather than a boolean so "which organization?" is never implicit — the only implicit answer available ("the oldest row") picks wrong on any database that already has two.

- **The switch is `packages/core/src/lib/single-org.ts`** — server-only. The client never reads the env var: `apps/web/src/server/config.ts` (`getPublicAppConfig`) hands it the mode plus the org's name/logo/slug. Deliberately **not** a `VITE_` variable — those bake at build time, and the Dockerfile builds one image meant to run under different environments.
- **The signup gate is a `databaseHooks.user.create.before` hook, not a screen.** Signing in with Google *is* the signup, and the user is created mid-OAuth-callback. The hook throws an `APIError` carrying a `code` — that field is load-bearing, since better-auth's OAuth callback only turns a thrown error into a redirect back to `errorCallbackURL` when one is set, and otherwise surfaces a raw 403 mid-round-trip.
- **Bootstrap: the first person to sign in on an unclaimed instance creates the org and owns it.** The race is settled by the unique index on `organization.slug`, not a read-then-write check.
- **`allowUserToCreateOrganization: false` + `disableOrganizationDeletion: true`** are what actually close those endpoints; hiding the switcher's "New organization" item is presentation.
- **URLs keep the `/$orgSlug` prefix.** Tenancy stays an explicit parameter, matching the service-layer rule.
- **`/no-access` exists to break a redirect loop.** A signed-in user with no membership would otherwise bounce `/` → workspace → `/` forever. It lists their live invitations through a local server fn, because better-auth's `listUserInvitations` rejects any caller whose email isn't verified, unconditionally, and this app has no verification flow.

### Production

Dev is `vite dev`. **Production is a Bun-native host, not Nitro/srvx**: `vite build` emits a web-standard `{ fetch }` handler with nothing to serve it, so `apps/web/server.ts` (TanStack's official start-bun reference) brings its own `Bun.serve` — static-asset preloading plus the in-process schedulers. `Dockerfile` builds and runs exactly this.

**This backend is a long-lived process, not a serverless function — background work goes in a job, never in a request handler.** The scheduler lives in `@farmer/core/jobs/scheduler.ts` rather than in `server.ts` so it can run three ways off one implementation:

| Where | How | Why |
|---|---|---|
| Production web host | `startSchedulers()` in `server.ts` | default; single instance |
| Development | `vite dev` spawns `packages/core/src/jobs/worker.ts` (the `farmer:dev-worker` plugin) | `vite dev` never loads `server.ts`, and nothing syncs on page load any more. Runs the **automation sweep only**: the other three jobs message real people and dev usually points at a shared database. `DEV_WORKER=false` to opt out |
| Separate worker container | `bun run worker` from `packages/core` | set `AUTOMATION_SYNC_ENABLED=false` (and friends) on the web host; run exactly one worker |

Two features carry a deployment switch of their own, both plain env vars rather than `VITE_` ones (same reason as `SINGLE_ORG_SLUG` — the Dockerfile builds one image for several environments): `ASSISTANT_ENABLED` and `MCP_ENABLED`, each default on, each independent of the other.

Each job is env-gated by `<NAME>_ENABLED` / `<NAME>_INTERVAL_MINUTES` — the full list is in the `scheduler.ts` header. All of it assumes a single instance; the jobs are idempotent, so a second replica is redundant rather than harmful. Note the tables in `scheduler.ts` are built by hoisted **functions**, not module-scope `const`s — that is load-bearing in the bundled image, and the header explains why.

## Testing

`bun test` from `packages/core` (or `bun run test` from the root). Runs against PGLite via `src/test/harness.ts` — real Postgres, real migrations, a fresh database per file on one shared engine (see the note in the layout section above; it is what keeps the run inside CI's memory). No DATABASE_URL, no container, no cleanup.

Two things the harness does *not* do, which fixtures must account for: it runs the migrations but **not** `db/seed-tasks.ts`, so Vacation/Sick Leave don't exist unless you insert them; and migration `0024` already seeds the site-scoped **Meeting** and **Break** tasks (and `0038` **Paid Leave**), so inserting those again violates `task_site_name_uidx` — look them up by `systemKey` instead.

Coverage is uneven, and worth knowing before you trust a green run.

Covered: `access`, `close`, `ledger`, `notify`, `org-settings`, `day-assembly`, `filing-rules` (the engine hook and every case where a rule must decline — a project the person left, an archived one, a title that only matches by accident), `holidays`, `projects` (list scoping, money and stats redaction), `recurring-block-rules` (including its assignment gate), `guards` (tenancy), `harvest-import` (a second import of the same files changes nothing, a day edited here is kept, undo removes exactly what the run made and refuses once somebody built on it) with `lib/harvest` beside it, `members` (the roster over 100 people, `emailUnconfirmed`, effective-dated types, and the archive/restore of an imported person), `tasks`, `clients`, `working-hours`, `organization`, `account`, `integration-settings`, `notifications`, `github` (only `attachCommits` scoping and the admin-only repo list, through `setGithubClientForTests`), `lib/oauth-state`, and `time-entries` across nine files (`absence-range`, `automation-since`, `commit-attach`, `copy-day`, `copy-day-guards`, `meeting-sync`, `time-entries.copy`, `time-entries.absence-fill`, `time-entries.day-capacity`), plus `assistant`, `mcp` (the membership check in front of the whole tool surface), the automation sweep, the budget-alerts job, both reminder jobs and their preview (`jobs/reminders.test.ts`), the member roster (`members.roster`), the range ceilings in `src/schema/`, and the pure `lib/` arithmetic.

Also covered, and worth knowing what each file is *for* — these are the four services that turn close data into a number somebody invoices or acts on, so they are pinned on properties rather than on outputs: `reports` (utilization prefers the frozen `expectedAtFinalizeSeconds` over any later fund edit; each trend point equals the single-month roll-up; variance reads the finalize snapshot, not a live recompute; the detail's total stays whole when its rows hit the cap; Team Lead scoping on every tab), `compliance` (absence lowers the target and is *not* credited as work — the double-count that hid people from the pace check), `hour-fund` (null is not zero; `prefillYear` never clobbers a hand-entered figure and survives a concurrent write), `not-on-invoice` (strictly zero Final, finalized months only, internal hours don't count).

`compliance.service` takes an optional `{ now }` so the two views can be pinned to a date — every figure in them is a fraction of the month elapsed, and on the 1st `behindPace` is correctly empty. Same seam as `runAutomationsForUser`.

**Not covered at all:** the `slack` and `google-calendar` **services** (their `lib/` clients do have tests — `lib/google-calendar-client.test.ts`, `lib/github-client.test.ts`), the rest of `github` (the commit scan and installation flows), `notificationsService.sendPush` (it reads VAPID keys from the environment), and member role changes (better-auth's `updateMemberRole`, which has no service function). Changing any of those means the suite cannot tell you whether you broke them.

Two PGLite limits the fixtures have already hit: a single multi-row insert of a few thousand rows overruns its bind-parameter handling and kills the instance for the rest of the FILE (chunk at ~500), and site-scoped tasks are unique on both name and `systemKey`, so seed Vacation once in `beforeAll` rather than per test.

## Gotchas

- **Never read the org roster through better-auth's `auth.api.listMembers`.** It throws in an organization over 100 people, which a Harvest import makes routine — archived people count towards the total. `membersService.roster` (`members.service.ts`) queries the tables directly and is what `server/members.ts`'s `listMembers` server fn calls; `auth/index.ts` also raises `membershipLimit` to 10,000 for the paths that still go through better-auth. Don't confuse either with `projectsService.listMembers`, which is a per-project assignment read and unrelated.
- Bun does not walk up parent directories for `.env` in a workspace — `bun run` inside `packages/core` or `apps/web` won't see the root `.env`. Addressed by symlinking the root `.env` into each workspace package; do the same for any new workspace.
- **`vite build` emits server code into `dist/client`, and `server.ts` serves everything it finds there.** The deferred `await import("@farmer/core/services")` inside each server-fn handler is chunked by rolldown *before* the server-fn transform strips the handler, so the client build ends up with an orphan island — better-auth's config, the drizzle schema, `slack.service`, `notify` — that nothing imports and no route preloads, but which `server.ts`'s `**/*` glob happily publishes at `/assets/<hash>.js`. `apps/web/scripts/prune-client-assets.ts` runs as the second half of `bun run build` and deletes it. **It currently prunes nothing** — the island came in through `resolveApiOrgContext`'s deferred `import("@farmer/core/auth")` sitting at the top level of `server/auth.ts`, a module the browser bundle pulls in for its middleware, and moving that function to `server/api-auth.ts` (imported only by server routes) closed the last path. Keep the script: it is the detector, it prints what it removed, and the leak returns the moment a client-reachable module gains a deferred server import. It computes reachability from what the server build can actually name and aborts the build rather than guess — don't "simplify" it into an unconditional delete, and don't drop it from the `build` script.
- `timeEntriesService.listRange` still performs writes on read — it recomputes (and drops) each day's fill block against the rows just read, bounded to the automation window, so it never rewrites a day the engines may not touch. That is deliberate and commented, but it means a GET is not idempotent, including through `api/v1` and through the MCP server's `list_time_entries`. **The MCP case is the one to watch**: an agent loop re-reads a range far harder than a person opens a screen, so every one of those calls is another pass at rewriting that day's fill block.
- The `nitro-nightly` package and `.bin/nitro` symlink present in `node_modules` are dead leftovers from initial scaffolding, not wired into `vite.config.ts`. The build has no hosting preset at all; production is served by the hand-written `apps/web/server.ts`, which is *why* one is needed.
- Base UI shadcn components have runtime-only failure modes that typecheck/build/lint all miss: `<Button render={<Link/>}>` to a non-`<button>` element needs `nativeButton={false}` or it throws in the console; `<Select>` needs an `items={[{value, label}]}` prop or the trigger displays the raw value instead of the resolved label.
- Always verify interactive changes in a real browser, not curl/SSR output — the hydration crash described above passed every curl-based check while silently breaking every form in the app. A headless Chromium is available via `playwright-core` + system `google-chrome` if no browser tool is otherwise configured.
