# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Bun workspaces (`apps/*`, `packages/*`) orchestrated by Turborepo. Run from repo root unless noted.

```bash
bun install                 # installs all workspaces
bun run dev                 # turbo: starts apps/web (vite dev --port 3000, falls back to 3001+ if occupied — check the log's "Local:" line, don't assume 3000)
bun run build               # turbo: builds all workspaces
bun run test                # turbo: runs the bun test suites of packages/core and apps/cli
bun run check               # oxfmt --check + oxlint — what CI runs
bun run typecheck           # turbo: tsc --noEmit in every workspace — also what CI runs
bun run lint                # oxlint only
bun run format              # oxfmt --write

# Database (packages/core, run through root turbo)
bun run db:generate         # drizzle-kit generate → packages/core/drizzle/*.sql
bun run db:migrate          # drizzle-kit migrate
bun run db:check            # `select 1` sanity check
bun run db:studio           # drizzle-kit studio
```

Package-local scripts — run from `packages/core`:
```bash
bun run auth:generate        # regenerates src/db/schema/auth.ts from src/auth/index.ts.
                              # auth.ts is CLI-owned — never hand-edit it. Run this after changing any
                              # better-auth plugin config, then db:generate + db:migrate.
bun run db:seed-tasks        # site-scoped built-in tasks + each org's starter tasks. Idempotent. `vite dev`
                              # (the `farmer:seed-site-tasks` plugin) and the Docker entrypoint both run it.
bun run db:seed              # demo data: one client/project/task. NOT idempotent, dev only.
bun run db:seed-assistant-ui # an assistant thread holding every renderer construct plus a suspended
                              # approval, so no model call is spent. Idempotent by title, dev only.
                              # Optional args: [org-slug] [user-email].
bun run db:deploy            # src/db/migrate.ts — applies pending migrations without drizzle-kit
bun run worker               # the standalone background worker (see Production)
bun test                     # the test suite (PGLite, no DATABASE_URL needed)
```

From `apps/web`:
```bash
bun run build                # vite build → dist/{client,server}, then prunes dist/client (see Gotchas)
bun run start                # NODE_ENV=production bun run server.ts — the production host
bun run generate-routes      # tsr generate — regenerates routeTree.gen.ts
```

### Lint and format

`oxlint` lints and `oxfmt` formats. Two root configs cover every workspace, and each workspace's `lint`/`check` script points back at them (`--config ../../oxlint.config.ts`). Both tools are root devDependencies only — a second copy in a workspace formats differently, and the drift stays invisible until CI disagrees with your editor.

- **`.oxfmtrc.json`** — tabs, double quotes, width 80, `sortImports`. It also formats JSON and CSS. Nothing lints CSS.
- **`oxlint.config.ts`** — four layers, ignoring `.claude/**`, `tools/oxlint/**`, `routeTree.gen.ts`, `src/db/schema/auth.ts` and `dist`:
  1. `plugins` + `categories.correctness` (react, react-hooks, jsx-a11y, typescript, oxc, import).
  2. **anti-slop** (vendored at `tools/oxlint/anti-slop/`, from [dmmulroy/anti-slop](https://github.com/dmmulroy/anti-slop)): fifteen rules that reject low-evidence TypeScript — `unknown` in a contract, a `Record<string, unknown>` value type, a hand-rolled `typeof` narrowing where a parse belongs, a type assertion with no stated invariant. All `error`, and the tree is clean of them.
  3. **stella** (vendored at `tools/oxlint/stella/`, from [stella's `.oxlint-plugins`](https://github.com/stella/stella/tree/main/.oxlint-plugins), Apache-2.0): `no-vacuous-throw-assertion` (an argument-less `.toThrow()` passes for any thrown value), `no-document-cookie`, `require-suppression-description`, `no-foreign-directive` and `no-partial-record-satisfies`. The other ~126 upstream rules were measured against this repo and skipped: domain-specific, already covered, or already passing.
  4. A handful of named rules and overrides — among them the `no-restricted-imports` override that keeps `apps/cli` off the server graph (see The CLI). See the comments in the file.

**Both plugins are vendored, not depended on — those files are ours to edit.** Three anti-slop rules carry a `Local amendment to the upstream rule` comment saying why (Zod's `.shape`; a `.catch()` handler's parameter is `unknown`; leading comments on an `export const` attach to the ExportNamedDeclaration). Read the comment before "fixing" one back. Provenance for the stella rules is in `tools/oxlint/stella/index.ts`, so a re-sync stays a diff.

**Every suppression needs a reason.** A bare `oxlint-disable` fails the build. The reason goes inline as a `-- <why>` trailer, or as a prose comment on the line above; the directive must be the **last** comment line either way.

**`SAFETY:` comments are load-bearing.** `require-safety-comment-for-type-assertion` fails the build on any non-`as const` assertion without one, so a new assertion needs a real invariant, not a restatement of the cast. The comment must be the line directly above the assertion **or** its containing statement, `//` not `{/* */}` (JSX comments are nodes, not comments), with the directive line last. Tests use `at(rows, i)` and `present(value, what)` from `src/test/harness.ts` instead of an assertion — both fail the test naming what was missing.

**Warnings do not fail the build** (about 50 today): `typescript/no-non-null-assertion` in the auth and drizzle configs and two test files, plus React and a11y findings (`react/set-state-in-effect`, `jsx-a11y/no-autofocus`, `jsx-a11y/control-has-associated-label` and a few others). They are left visible on purpose; promote a rule to `"error"` in `oxlint.config.ts` once it is burned down.

## Architecture

Three workspaces — `apps/web` (TanStack Start/React), `apps/cli` (`@farmer/cli`, the `farmer` command-line tool, see The CLI) and `packages/core` (`@farmer/core`). The split is deliberate: `packages/core` must stay reusable from another process.

**Boundary rule:** `packages/core` never imports TanStack/React. All business logic lives in `src/services/`, one file per aggregate. Every exported service function takes an explicit `ctx: { organizationId, userId }` (`src/services/types.ts`) as its first argument — **tenancy is a parameter, never ambient** — so the same function is callable from a server function, a REST route, a background job or an MCP tool.

`packages/core` layout:
- `src/db/` — `drizzle-orm/postgres-js` client (`index.ts`, resolved lazily — see Testing) + schema:
  - `schema/auth.ts` — better-auth-owned: user/session/account/verification/organization/member/invitation, plus the plugin tables (`oauthApplication`/`oauthAccessToken`/`oauthConsent` for MCP, the device codes for the CLI). CLI-generated, see `auth:generate`.
  - `schema/domain.ts` — client, project (`projectType`), task (`taskScope`, `taskGroup`, `systemKey`), projectMember, recurringBlockRule(+Skip), timeEntry.
  - `schema/people.ts` — memberProfile, memberTypeHistory (effective-dated `memberType`), teamLeadPerson, invitationEmail (whether an invite email reached the provider; it sits here because `invitation` is CLI-generated).
  - `schema/schedule.ts` — memberWorkingHoursDay, disabledHoliday.
  - `schema/settings.ts` — integrationSettings, syncedMeetingTombstone, commitFillTombstone, pullRequestReviewTombstone, filingRule, orgSettings, reminderSettings, monthlyHourFund.
  - `schema/github.ts` — orgGithubInstallation, projectGithubRepo, timeEntryGithubCommit, timeEntryGithubPrActivity (one row per pull request EVENT — opened, merged, closed, reviewed — not per PR).
  - `schema/slack.ts` — slackInstallation, memberSlackIdentity, slackReminderLog.
  - `schema/notifications.ts` — pushSubscription, notificationSettings.
  - `schema/import.ts` — importRun, importMapping (what each Harvest import created, so undo removes exactly that).
  - `schema/assistant.ts` — assistantSettings, assistantConversation, assistantMessage.
- `src/services/` — one file per aggregate: access, account, assistant, clients, compliance, day-assembly, filing-rules, github, google-calendar, harvest-import, holidays, hour-fund, integration-settings, members, notifications, org-context (the slug-to-Ctx membership check MCP and the CLI share), org-settings, organization, projects, recurring-block-rules, reminder-settings, reports, sessions (Preferences → Signed-in devices), slack, tasks, team-leads, time-entries, uploads, working-hours. Shared modules: `guards.ts`, `ledger.ts`, `unfiled.ts`, `notify.ts`, `reminder-recipients.ts`, `context.ts`, `db-ctx.ts`, `ports.ts`, `day-fill.ts`, `pr-reviews.ts` (the review-block rules the commit engine and the day assembler share), `types.ts`, and the two tool registries `assistant-tools.ts` + `mcp-tools.ts`.
- `src/schema/` — Zod input schemas, one module per aggregate, shared by the RHF form resolver, the server function `.validator()`, the REST handlers (`api/v1` and the CLI's API) and the assistant/MCP tool parameters. Range inputs carry their own ceilings (62 days for a time-entry range, 366 for a report), so a caller cannot ask for a full-table scan by widening the dates. **Don't re-validate by hand at a new call site** — that is how a caller ends up bypassing the ceiling.
- `src/api/` — exported as `@farmer/core/api`: the REST API's response shapes and the projection functions that build them, plus `MIN_CLI_VERSION` and the CLI's error codes. Types-only imports, because the CLI binary imports it at runtime.
- `src/lib/` — `time.ts` (UTC-in/display-zone-out durations and timezones on `date-fns`/`@date-fns/tz`; **the only place timezone math should happen**), `working-day.ts`, `day-plan.ts`, `automation-window.ts`, `org-time.ts`, `org-country.ts`, `task-taxonomy.ts` (task groups, the standard org tasks and Harvest name aliases — shared by the seed and the import), `task-rules.ts`, `search.ts` (the list filter the web app and the CLI share), `report-period.ts` + `report-format.ts` (report arithmetic the browser also needs), the integration clients (`github-client.ts`, `google-calendar-client.ts`, `slack-client.ts`, `openrouter-client.ts`), `github-activity.ts` (pure: which day a pull request event belongs to, and whose it is), `http.ts`, `oauth-state.ts`, `single-org.ts`, `dev-auth.ts`, the deployment flags `assistant-flag.ts` + `mcp-flag.ts` + `cli-flag.ts`, `uploads.ts` (browser-safe) + `storage.ts` (server-only), `slug.ts`, `email.ts`, `json.ts`. `harvest/` is the Harvest CSV parser and import planner — pure, because it runs in a browser Web Worker.
- `src/jobs/` — exported as `@farmer/core/jobs`. `scheduler.ts` is the runner, `worker.ts` a standalone process entry; `automation-sync.ts`, `log-reminders.ts`, `slack-reminders.ts` and `upload-sweep.ts` are one tick of work each.
- `src/test/harness.ts` — see Testing.

`apps/web` layout:
- `src/routes/` — TanStack Router file-based routing.
  - `$orgSlug/route.tsx` is the org-scoped layout: its `beforeLoad` resolves the session, the organization and the caller's role in ONE server call (`enterOrganization`) alongside `getPublicAppConfig`, and redirects out if any check fails — every nested route inherits that guard. `enterOrganization` repoints the session only when the active org actually differs.
  - Under it: `index.tsx` (home: today, plus week and month targets), `time/` (a `route.tsx` layout with the targets strip and the unfiled banner, then `index`/`week`/`month`), `projects/` (the list, and `$projectId/` with `index`/`team`/`settings`), `reports.tsx`, `assistant.tsx`, and `settings/` (an `index.tsx` hub plus organization, members, my-schedule, clients, tasks, recurring-blocks, holidays, hour-fund, reminders, import, integrations, preferences).
  - Outside it: `index.tsx` (the landing page), `login.tsx`, `accept-invite/$invitationId.tsx`, `no-access.tsx`, `device.tsx` (approves a CLI login) and `cli/` (the install scripts and binary downloads).
  - Server routes: `api/auth/$.ts` (better-auth), `api/login.ts`, `api/mcp-login.ts`, `api/github/setup.ts`, `api/slack/callback.ts`, `api/files/$.ts`, `api/assistant/stream.ts`, `api/mcp/$orgSlug.ts`, `[.]well-known/oauth-*.ts`, `api/v1/projects` + `api/v1/time-entries` (cookie-authed REST reads), and `api/v1/{meta,me,session}` + `api/v1/orgs/$orgSlug/*` (the CLI's API). All of that auth lives in `server/api-auth.ts` — deliberately NOT `server/auth.ts`, see the client-bundle rule below.
  - `reports.tsx` is the shell. Its four tabs — Time, Overtime, Tracking (`compliance`) and Absence — are declared in `components/reports/search.ts` and live in `components/reports/`. `periodSearch` there is shared with the project page.
- `src/server/` — thin `createServerFn` wrappers, one file per aggregate, mirroring `services/`. **Auth is attached via middleware** (`sessionMiddleware` / `orgMiddleware` / `orgAdminMiddleware` from `server/auth.ts`), read from the handler's `context` — never by calling `requireOrgContext()` inline, so the protection is part of the function's declared shape. `auth.ts` itself is the only place the bare helpers are called, because route `beforeLoad`s need them. `orgMiddleware` re-checks membership inside its `.server()` callback rather than in a shared helper: a top-level function body in `auth.ts` ships to the browser, so a deferred `import("@farmer/core/services")` there becomes a real client chunk.
- `src/queries/` — TanStack Query `queryOptions` factories, one per aggregate; loaders prefetch, components read via `useSuspenseQuery`. **Every key names its organization**: factories take the slug first (`timeEntriesRangeQuery(orgSlug, from, to)`) and spread their root from `queryKeys(orgSlug)` in `queries/keys.ts`; invalidations name the same root. Components get the slug from `useOrgSlug()`, loaders from `params.orgSlug`. Never write a bare `queryKey: ["…"]` literal and never drop the org — an org-blind key is an answer from the previous workspace. Server functions are deliberately NOT generated from a shared declaration — see `docs/adr/0001-no-server-function-generator.md`.
- `src/components/ui/` — shadcn on **Base UI** (`@base-ui/react`), not Radix (`components.json` style is `base-nova`). Composition uses the `render` prop, not `asChild`. The project picker (grouped by client) and task picker (grouped by `taskGroup`) are in `components/pickers/`.
- **An eyebrow carries live context or a way back** — a date, a period, a count, a return link (`SettingsEyebrow`, the project pages' back link). Never a static label that repeats the title or the page; on a `PageHeader`, leave `eyebrow` out instead.
- **Table search filters the view only.** `@farmer/core/lib/search` (`matchesSearch`: case- and accent-insensitive, any word in any field) and `components/ui/search-input.tsx` back every search box. **Totals and stats are computed over the full dataset, never over the filtered rows** — a total that tracked the search box is a wrong number, not a filtered one.
- **`lib/entry-options.ts` remembers per device** (localStorage) the last project and task per org and per dialog, and the `fillsDay`/`overtime` options per project and task. Repeat is deliberately not remembered.
- **The week starts on the organization's `weekStartsOn`** (`organization.week_starts_on`, 1 = Monday by default, 0 = Sunday; Settings → Organization). `startOfWeekKey` and `resolveReportPeriod` take it as a required argument, so a new caller cannot forget it silently. Pages read it from the `/$orgSlug` route context (`useWeekStartsOn`, `useWeekdays`), services from `ctxWeekStartsOn`, and the CLI from `whoami`. Stored weekday numbers stay `Date#getDay()`'s (Sunday = 0); only the order a week is drawn in changes.
- **Light/dark is `data-theme` on `<html>` and nothing else.** Both palettes are written out in `styles.css`; `lib/theme.ts` owns the attribute and the DOM is the state — no provider. `themeInitScript` runs inline in `<head>` (`__root.tsx`) before React exists, because the choice lives in localStorage and applying it on hydrate flashes the light palette; that mismatch is why `<html>` carries `suppressHydrationWarning`. No stored choice follows the OS. The calendar's category tints (`lib/category-colors.ts`) are light washes computed in JS and read bright in dark mode. **Preferences → Display is the same design**, per device and off by default: "Boring font" (`data-font="sans"`), "Less movement" (`data-motion="reduce"`) and "Compact tables" (`data-density="compact"`), all owned by `lib/display-prefs.ts` and set by `displayInitScript` in the same `<head>` script. Boring font re-points `--serif`, so a new display rule must read `var(--serif)`, never name Instrument Serif. Less movement ends every CSS animation and transition at once (`styles.css`) and sets Motion's `MotionGlobalConfig.instantAnimations`, so completion callbacks still fire but no animation is seen. Compact tables sets `--table-cell-py`, which only `TableCell`'s default padding reads — a cell with its own `py-*` keeps it.

**Critical, non-obvious rule:** never put a static top-level `import ... from "@farmer/core/db"` / `"/auth"` / `"/services"` in any route or `src/server/*.ts` file. `postgres` touches `Buffer` at module scope, which crashes hydration in the browser — silently: forms fall back to native submission instead of throwing. Always import inside the handler body:
```ts
export const createTimeEntry = createServerFn({ method: "POST" })
  .middleware([orgMiddleware])
  .validator(createTimeEntryInput)
  .handler(async ({ data, context }) => {
    const { timeEntriesService } = await import("@farmer/core/services");
    return timeEntriesService.create(context.ctx, data);
  });
```
This is also why `requireOrgAdmin` routes through the `getMyRole` server function instead of importing services directly — it's called from a route `beforeLoad`, which also runs client-side during SPA navigation.

### Authorization

**Three independent axes, and `services/access.service.ts` is the only place that knows the matrix.**

- **One org role:** Admin (better-auth's `member.role` = `owner` | `admin`, both mapping to the single Admin tier). There is deliberately no super-admin.
- **A per-assignment project role:** `member` | `team_lead` | `pm` on `projectMember`. The same person is PM on one project and a plain member on another, so a project role is never a property of the person. An inactive assignment (`active = false`) grants nothing.
- **A people list:** `team_lead_person` rows, edited by an Admin on the People page (`team-leads.service.ts`). Having people on your list is what makes you a Team Lead — there is no flag. A Team Lead sees everything about their people: their time on every project, Tracking, time off. `accessService.peopleScope` is the people-shaped scope (Tracking, Absence); `Access.canViewPerson` the per-person check.

**Rank on a project is `heldAs`, not the raw row.** `roleOn()` returns the assignment as stored — admins are not synthesised into a role, so a "your projects" filter still works — and `heldAs()` returns the effective role that screens and gates read. A Team Lead holds PM rank only on a project where their own assignment is `team_lead`; a `member` assignment never widens (`rankOf`), and `peopleScope` adds project rosters only from projects held at PM rank. **Role changes are capped at the caller's rank:** `Access.canActOnProjectRole(projectId, role)` lets a non-admin assign a role, or act on someone who holds it, only up to their own `heldAs` rank. `projectsService.assignMember`/`removeMember` enforce it and `apps/web/src/lib/project-access.ts` mirrors it for the UI. Managing project members and creating projects both need `team_lead` rank or above.

**A project can be open to the whole organization** (`project.openToOrg`, the switch on its Team page, PM or Admin). Every member may then track on it without an assignment — the org's Internal project, which a new hire should not wait to be added to. It grants Member rank and nothing else: `canTrackOn` and `scopeFor("member")` include it, while `roleOn`/`heldAs`/`assignments()` stay null for it, so a Member sees their own hours and no team, totals or money. Two assignment reads deliberately ignore it: `reposForUser` (GitHub commits are attribution, not access) and `projectIdsForUser` (a PM of an open project is not PM of everyone's absence).

**Membership is a precondition, not a capability.** `accessService.resolve` throws `NotAMemberError` when the caller has no membership row, rather than describing them as "nobody". A Ctx is built from `session.activeOrganizationId`, which is stamped when the workspace is entered and never revisited, so without this an ex-member's session still answered every org-wide read that filters only on `organizationId`. `orgMiddleware` and `resolveApiOrgContext` resolve `Access` at the boundary for the same reason, which also warms the request's memo.

`accessService.resolve(ctx)` returns an `Access` — four parallel queries (membership, assignments, lead list, open projects), then answered from memory. Resolve it **once per request** via `ctxAccess(ctx)` (`services/context.ts`), which memoizes it on the Ctx.

A Member sees strictly their own entries and gets every report scoped to themselves, so nobody is refused a report; on a project page a Member sees their own hours, never the project's totals or contributors. A PM adds project config and the two money fields on their projects. `scopeFor(role)` returns `null` for admins meaning "unscoped" — callers translate that into no project filter rather than a 200-id `IN` list, and an empty array is a real answer meaning "nothing".

`server/auth.ts`'s `getMyAccess` flattens this for the client to gate UI with. It is **not** authorization — every service re-resolves `Access` server-side and asserts.

Two gates that read as one and are not: `assertTaskAvailable` (guards.ts) asks whether a TASK may be used on a project; `assertCanTrackOn` asks whether this PERSON may write there. Anything that creates time entries needs both. `recurringBlockRulesService` runs both at create **and on every materializing pass** (plus project status and task archival), because a rule outlives the assignment, project and task that made it valid; a rule that no longer applies is skipped, not deleted.

### The ledger

`services/ledger.ts` is the one definition of what counts as logged time. What may vary between callers is the **projection** (columns, joins, grouping key). What must not vary is the **classification** and the tenancy/range predicate: `ledgerWhere` owns the predicate and `LedgerScope` the vocabulary — `worked`, `project`, `unfiled`, `absence`, `all`. A caller with a bespoke projection composes `ledgerWhere`; never hand-roll a `sum(durationSeconds) … groupBy` with its own predicate.

`LedgerFilter.visibleProjectIds` and `visibleUserIds` are ORed: a row passes if it is on a visible project OR belongs to a visible person. `null` means unscoped; both empty means nothing. `overtimeOnly` and `activeOnly` narrow further.

**A day holds at most 24 hours** (`MAX_DAY_SECONDS`, `lib/working-day.ts`). Every manual write that grows a day checks it and throws `DayCapacityError`: create, update, the week grid, copy day/week, day assembly and the PM absence writes. An edit that does not grow the day is allowed even on a day already over. The engines are exempt, since a fill block is sized from the remainder and a synced meeting mirrors the calendar.

**Unfiled** = worked time with no project yet (a synced meeting, a commit fill block, an accepted assembly suggestion) — real work, not yet attributed, therefore a to-do. Absence is not unfiled (it never carries a project by definition), and neither is a project-less **Break** — nobody bills a client for lunch, so counting it would nag people to file something unfileable.

**A task can require a note** — `assertDescribed` (guards.ts) on `descriptionRequiredFor` (`lib/task-rules.ts`). Absence, Break, fill blocks and the week grid (`setWeekCell`) are exempt.

### Targets and Tracking

`compliance.service.ts` turns logged time into the numbers people act on — the home page, the timesheet's targets strip, the Tracking report and the reminders all read it.

- **The target comes from the month's hour fund** (`monthlyHourFund`), prorated by working days: weekdays minus public holidays, so a day is 8h. Expected (`hour-fund.service.ts`) is the fund minus absence days × 8. There is no per-member weekly target (migration `0051` dropped it); working hours (`memberWorkingHoursDay`) only shape fill blocks, time-off spans and when a reminder reaches someone.
- **Total = work + time off**, compared against the target *so far*. Working days elapsed are counted strictly **before** today (the whole month once it is over), and the verdict reads `totalSoFarSeconds` through today, so the day in progress never counts against anyone.
- **Person type decides who has a target** (`memberType`, effective-dated through `memberTypeHistory`): hourly students and contractors have none without an override; overhead employees and archived people are never listed.
- **No hour fund means no verdict**, not "on track": the nudge sends nothing, and the digest and preview say no fund is set (`reminder-recipients.ts`).
- `complianceService.myTargets` returns week and month `PeriodTarget`s for `components/targets.tsx`. The service takes an optional `{ now }` so a test can pin the date — every figure is a fraction of the period elapsed.

### Tasks

One global list per org (`scope: "organization"`) plus **site-scoped built-ins** shared by every org: Vacation, Sick Leave and Paid Leave (absence), Meeting and Break. Every project offers every live task — there is deliberately no project scope and no per-project subset. Each task carries a `taskGroup` (`engineering`, `product`, `learning`, `general`, `time_off`); the standard org list, including Development and Code Review, is in `lib/task-taxonomy.ts`.

Engines resolve tasks by **`systemKey`**, never by name (`meeting`, `development`, `code_review`, `break`, `vacation`, `sick`, `paid_leave`). A name lookup switches an engine off silently when an org renames the task — no block, no error. Names stay freely editable.

`assertTaskAvailable` (guards.ts) lets any live non-absence task of the org, or any site task, go on any project. An absence task must carry no project; archived tasks and other orgs' tasks are refused.

### Automation

**`jobs/automation-sync.ts` is where every entry nobody typed comes from** — recurring blocks, calendar meetings, and GitHub work-time blocks. None of it runs on page load. The per-user pass is `timeEntriesService.runAutomationsForUser`, and its **order is load-bearing**: a commit fill block is sized from what the day already holds, so recurring blocks must materialize first. It reports `ran`, `skipped`, `failed` and `off` separately — an engine whose window came back null did nothing, and an engine the person never switched on is `off`, so "Sync now" can say so rather than claim a sync; a failed read of the lock or of integration settings comes back as `failed: ["org-settings"]` or `["integration-settings"]`. The sweep runs `AUTOMATION_SYNC_CONCURRENCY` people at a time behind a per-person timeout. Archived people are not swept, or their meetings would keep landing as unfiled time. "Sync now" shares the sweep's per-person guard and timeout, so the two never run one person twice at once.

**`lib/automation-window.ts` is the one window policy**, and the only place any engine may learn how far it reaches: `to` is today in the **org** timezone (never the future — a row on a day nobody has lived counts in reports and gets rewritten underneath them), **or yesterday under `completeDaysOnly`**; `from` is the latest of `today - AUTOMATION_GRACE_DAYS`, the day the switch was flipped, and the day after `orgSettings.automationLockedThrough`. Grace is a **downtime recovery budget**, not a backfill policy — every day inside the window is a day whose sync-owned rows can still be rewritten from the source. `completeDaysOnly` belongs to the commit engine alone: its block claims the rest of the working day and is sized from the day's *whole* target, so it must not run against a day still in progress.

**`automationLockedThrough` (org settings) locks the robots, not the people.** Entries stay hand-editable in reconciled months; this is the last day no *automation* may write to — needed because for the first days of every month the grace window reaches into the month just invoiced. A failed read of it fails the whole pass rather than defaulting to unlocked. The meeting engine honours the window in both directions: a synced row dated before the window is never moved or rewritten, even when Google now reports the event on a later day, and an event dated outside the window is not written at all. The commit engine drops any commit day outside its range, because GitHub filters on committer date while the engine buckets by author date, and a rebased branch carries old author dates.

**The commit engine attaches before it creates.** Commits are *evidence*: `syncCommitWorkTimeForRange` resolves a target per project (that project's work entry → the day's fill block → a project-less Development entry) and only files a rest-of-day block when the evidence found no home at all, so a person who already logged their day keeps it and gains the commits. Blank descriptions are backfilled from commit subjects; non-blank ones are never overwritten. When a fill block empties and is dropped (`recomputeDayFill` or `listRange`), `rehomeDroppedFillEvidence` (`day-fill.ts`) first moves its commits and PR events to the same fallback target, because the attachment rows would otherwise cascade away with the block.

**Pull request events are the engine's second body of evidence, under the same switch.** `githubSyncCommitsAsWorkTime` covers both; there is no PR toggle. The engine reads commits and PR events together (`pullRequestSource()` in `ports.ts`, beside `commitSource()`), and a day with only PR events — a day of reviews — is a worked day that finds a home or files the rest-of-day block exactly as commits do. The events are `opened` and `closed` (unmerged) for the author, `merged` for the author only (whoever pressed the button did not do the work), and one `reviewed` per submitted review — except on your own PR, where GitHub records every thread reply as a COMMENTED review. Each is dated by its own timestamp (`lib/github-activity.ts`), so this path needs no committer-date guard. They are read by **GraphQL search** (`author:` and `reviewed-by:` per linked repo), not REST: `/pulls` has no author filter, reviews are a call per PR, and REST search allows 30 requests a minute. `attachPullRequests` takes only a repo row and a PR number, reads the PR again, and keeps only the caller's own events on the entry's date.

**A reviewed pull request gets a Code Review block of its own.** Before the day's evidence is attached, `fileReviewBlocks` gives each PR reviewed that day one entry under the `code_review` task, on the repo's project, described "PR review: <title>", with its reviews attached. GitHub records when a review was submitted, not how long it took, so the block is a fixed `REVIEW_BLOCK_SECONDS` (30 minutes) the person edits; it is taken from the day's free time (the rest-of-day block shrinks by the same amount), and a day with less than a quarter hour free gets none. A review goes, best home first, to: the entry already holding that PR's reviews on the day (any task), a Code Review entry the person logged on that project (it takes every PR reviewed there that day), or a new block. No column marks a block: `isReviewBlock` (`services/pr-reviews.ts`) reads it as one PR's reviews under that PR's "PR review: <title>", so another PR's block is never a home and a renamed block becomes the person's own entry. A review that finds no home stays evidence on the day's work. Deleting a Code Review entry writes a `pullRequestReviewTombstone` per (day, PR) it held — read before the delete, because the attachments cascade — and taking a PR's last review off an entry writes the same tombstone. An org with no live `code_review` task gets no blocks (migration `0053` set the key on each org's live "Code Review" task by name, once). `dayAssemblyService.suggest` proposes the same blocks (kind `review`) from the same rules.

**`dayAssemblyService.suggest` takes `includeDismissed`** — the toggle that re-offers meetings and rest-of-day blocks the person deleted. Tombstones are what stop the engines rebuilding them, which is right by default and a dead end when the deletion was a mistake. Re-offered suggestions carry `dismissed: true` so the dialog renders them **unticked**.

**`filing-rules.service.ts` is the standing answer to "which project does this meeting belong to".** A synced meeting lands project-less on purpose and the File-your-time dialog is where it gets attributed; a recurring meeting would be the same answer fifty times a year. A rule is created by ticking "Always file these here" in that dialog, and `syncMeetingsForRange` applies it at write time so the occurrence never appears as unfiled at all.

A rule answers with a project and, optionally, a task (`targetTaskId`; null keeps Meeting), and both are editable under Settings → Preferences. Filing by hand can change the task as well (`fileTimeEntriesInput.taskId`), and Assemble my day has pickers per row. Rules apply in two places: the meeting sync (Meeting rules only), and `dayAssemblyService.suggest`, which applies any rule to each row it proposes without a project — so a rule remembered from a rest-of-day block files the next assembled one. A row whose project came from GitHub evidence is not overridden. The commit engine's own rest-of-day block does not read rules.

Four things about it are load-bearing. It is keyed on **(task, normalized title)** — not on the calendar event or series, because a series cancelled and recreated is a new event id but the same decision, and not on duration, because a stand-up that ran long once is still the stand-up. **An empty description cannot carry a rule**: the dialog falls back to the task name for display, so a rule keyed on `""` would claim every untitled meeting the sync imports. The rule is derived by `rememberFrom` from the entries `fileMany` actually filed, so the client cannot ask for a standing rule about time it did not just attribute. And `resolveForTask` **re-checks `canTrackOn` + `assertTaskAvailable` + project status on every pass**, because a rule outlives the assignment that made it valid — a rule that no longer applies is dropped silently and the entry lands unfiled, which is where it would have been anyway.

A rule-filed row stays `syncLocked = false`. The rule decides where the time goes, not who owns the row, so Google is still the source of truth for the meeting's title, length and existence and a cancelled one still disappears. Taking ownership is what filing **by hand** means (`file` sets `syncLocked`). Rules are listed and removed under Settings → Preferences; removing one leaves the entries it already filed alone.

Two engine details that differ and should stay differing: the MEETING path upserts with `onConflictDoUpdate … setWhere syncLocked = false AND date within the range` — that date check is what keeps a row before the window from moving; `onConflictDoNothing` guards the COMMIT path.

### The Harvest import

An admin drops the Harvest CSV exports on Settings → Import (`settings/import.tsx`); `harvest-import.service.ts` writes them. The design and the owner's decisions are in `docs/plans/harvest-import.md`.

- **Parsing and planning run in the browser, in a Web Worker** (`components/import/harvest.worker.ts`, on `packages/core/src/lib/harvest/`). A real export is ~240k rows: the Worker keeps the day chunks and the page holds only the review, because a structured clone of every row on each re-plan would freeze the tab. The server takes the plan in steps — `start` (clients, tasks, people, projects), `importDays` in chunks of `HARVEST_CHUNK_MAX_ROWS`, `removeDays`, `finish` — and every step is safe to repeat, so "Retry" continues from the cursor. `start` is made repeatable by a run id the browser generates once per attempt: a second `start` with the same id returns the run it already created.
- **The unit is a person-day, compared by digest.** A day already imported unchanged is skipped, a changed one replaced, and a day somebody edited here is **kept**, never overwritten. A day the file no longer has is removed only when the admin confirms the file is a full export. That is what makes dropping the same files twice a no-op.
- **`finish` moves `automationLockedThrough` to the day before the cutoff**, so no engine writes into imported history, and prefills the hour fund for every year with history, because Expected needs it.
- **A guessed email makes an archived person with `emailUnconfirmed`.** A Harvest person with no address gets `first.last@domain`; they cannot sign in until an admin confirms the address on People (Restore for an archived person, "Confirm email" for an active one), since a wrong guess is otherwise somebody else's login. An address the admin **typed** on the review screen is not a guess: it counts as confirmed (`emailConfirmed` on the person plan).
- **Undo removes exactly what `importMapping` says the run created** — and only for the latest run. It does not restore days the run replaced, does not move the lock back, and refuses outright once a created person has signed in or an entry made here uses a created row.
- **Two questions block the plan until the admin answers them on the review screen**, because neither has a safe default:
  - **Names that differ only in accents or punctuation** ("Ive Vasiljević" / "Ive Vasiljevic") — one person or different people (`choices.duplicates`, keyed on the ASCII fold). "One person" merges the spellings into the chosen one, and the other gets an `alias` person plan: `start` maps it to the same user, not `created`, so undo removes only the mapping. A group whose every spelling an earlier run mapped is not asked again — one user is one person, two users stay two.
  - **Negative correction rows** — `subtract` takes each off the row with the same person, day, project, task and overtime flag (an exact match first, then the largest), rounds the rest again and gives it a new `…:net` key; `leave_out` imports the other rows as they are. The keys differ, so changing the answer later replaces those days on the next run. A correction with no row big enough to take from stays under "needs attention" either way.
- Rows of two source people who are one user here (an alias, or two names matched to one member) are one person-day in the plan, as `importDays` groups them, so the digest covers the same rows as the stored one.

### Notifications

`services/notify.ts` — `notify(recipient, event)` is the single way anything tells a person anything. The recipient is always an `(organizationId, userId)` pair, so membership is checked on every channel; a `KINDS` table says which channels a kind uses and which `notificationSettings` column gates it. Adding a channel is one adapter plus one row in that table. Never throws — it returns which channels delivered. Substitutable via `setNotifyAdaptersForTests`. `notificationsService.sendPush` is the push *transport* and is not a call site: push subscriptions belong to a device, so nothing there can know which org is speaking.

**Reminders are configured per org on Settings → Reminders** (`reminderSettingsService`: `get`, `update`, `preview`; design in `docs/plans/reminder-settings.md`). A missing `reminderSettings` row is the defaults. Who gets a reminder is decided in one place, `services/reminder-recipients.ts`, which both jobs and the preview call — so the preview cannot disagree with what the job then sends.

- **`KINDS` rows carry a `reminder` flag, and `deliveryBlocks()` holds reminder kinds back** from, in order: non-members, archived people, people who have never signed in (no `account` row) and people who opted out. The never-signed-in gate is on by default; `reminderSettings.includeNeverSignedIn` turns it off. A test person therefore needs an `account` row unless the fixture sets that flag.
- **Both jobs read org-level state once per org**, not once per member, and both take `{ now }`. The Slack job ticks every 15 minutes, skips a kind that already ran today or is not due before any heavy query, and checks the delivery gates before it claims `slackReminderLog` — so a blocked person does not burn the day's claim. `forgetSlackReminderRunsForTests()` clears its in-memory record of the day's runs.
- **The Tracking rule is the reminders' rule.** `complianceService.trackingForReminderJob` is what the nudge, the month-end "only behind" option and the digest read; a person is nudged when the rule calls them *behind* (see Targets and Tracking) by more than `orgSettings.trackingTolerancePct` (default 5). Nothing on `reminderSettings` decides who is behind, and the nudge never goes out on a weekend or a public holiday.

### Ports and outbound calls

`services/ports.ts` — `calendarSource()`, `commitSource()` and `pullRequestSource()`, the substitutable seam the sync engines read through. The production adapter is the real service; tests install an in-memory one (`setCalendarSourceForTests`, `setCommitSourceForTests`, …).

**`lib/http.ts` (`externalFetch`) puts a deadline on every outbound call** (15s by default, `EXTERNAL_FETCH_TIMEOUT_MS`). `fetch` has no default timeout, and the sweep refuses a new tick while one is in flight, so one wedged socket would stop all syncing until a restart. `withTimeout` is the same idea one layer up.

### Authentication

**Google is the only identity in production, and there is no login page there.** `emailAndPassword` is off, so there is no form to render and nothing to choose — "log in" is a redirect.

- **`routes/api/login.ts` is the sign-in surface.** A server route: it asks better-auth for the Google authorize URL and re-shapes that 200-plus-`Location` response into a real 302, copying the OAuth state/PKCE cookie across, so an unauthenticated document request reaches Google without the app hydrating.
- **`routes/login.tsx` stays a *page* route on purpose**, even though it renders almost never. Every `redirect({ to: "/login" })` and sign-out points at it, and a page route's `beforeLoad` runs both server-side and in the browser; `redirect({ href, reloadDocument: true })` turns either into the full-page hop `/api/login` needs.
- **Two cases render instead of redirecting.** `?error=…` — better-auth's `errorCallbackURL`, most usefully the single-org invite-only gate; that branch must not redirect, or an uninvited visitor bounces between `/login` and Google forever. And development, below.
- **`lib/dev-auth.ts` turns email + password back on off-production.** The gate is `NODE_ENV !== "production"` and deliberately **not** an opt-in env var, which could be copied from a `.env` onto a server. The Dockerfile and `apps/web`'s `start` script pin `NODE_ENV=production`; any other way of hosting the app must set it too. Downstream nothing is special-cased — the same `databaseHooks.user.create` hooks bootstrap the org and seed its tasks, and single-org mode's invite gate still applies to a password signup. The client learns it from `getPublicAppConfig().devAuth`, which also hides Preferences → Sign-in methods in production.
- **`/` never redirects, in any mode.** The landing page renders for everyone and its CTA resolves the destination (workspace / `/no-access` / `/login`).
- **`prompt: "select_account"` on the google provider is deliberate.** With no login screen there is nowhere to offer "use a different account".
- `session.freshAge: 0` — better-auth 403s `SESSION_NOT_FRESH` on unlink-account once a session is older than a day, and this app has no step-up re-auth flow, so integration disconnects would break.
- Invite context rides through as query params and is rebuilt into the Google `callbackURL`. `redirect` is attacker-supplied in principle, so `api/login.ts` accepts only a same-site absolute path (`/…` but not `//…`).

### Integrations (GitHub + Google Calendar + Slack)

GitHub and Google Calendar are per-member and opt-in via `integrationSettings` (a missing row = every toggle off, so connecting an account never silently enables background sync); Slack is per-org and admin-only. All three live on `$orgSlug/settings/integrations`, which renders admin-only sections behind `role`. The GitHub and Calendar token helpers check the `account` table first and return null when nothing is linked, rather than letting better-auth throw.

- **GitHub uses two distinct credential types, don't conflate them.** The per-user OAuth account link (`socialProviders.github`) is used **only for identity** — `GET /user` (resolve the login, to filter activity by author) and `GET /user/installations` (enumerate installations the person may connect). All repo, commit and pull request reads go through a **per-org GitHub App installation token** (`orgGithubInstallation`), obtained after an admin installs the App and GitHub redirects to `api/github/setup.ts`, which re-verifies admin role and resolves the org from a signed `state` (`lib/oauth-state.ts`: org, user and issue time, expiring after 15 minutes). The Slack callback refuses any request without a valid state. GitHub setup falls back only when no state was sent at all, because an App installed from GitHub's own UI arrives that way, and that is safe because `connectInstallation` re-verifies the installation against the caller's own GitHub account. Repo reads are scoped to the caller: `attachCommits` requires an assignment on each repo's project and a hex `sha`, `attachPullRequests` holds the same assignment line before any GitHub call, and listing every repo the App reaches is admin-only. Env: `GITHUB_CLIENT_ID/SECRET` (OAuth) are separate from `GITHUB_APP_ID/SLUG/PRIVATE_KEY` (the App; private key is base64-encoded PEM).
- **The App needs "Contents: Read" and "Pull requests: Read".** Without the second, GitHub answers FORBIDDEN, which reads as "no activity" (as a 403 does on the commit path), so a missing permission is silent. Adding a permission to an existing App makes every installation owner accept it on GitHub.
- **The `repo` scope on the OAuth app looks removable and is not.** `GET /user/installations` works only for tokens carrying `repo`, and that call is the authorization gate in `connectInstallation`. Read the comment at the call site before touching the line.
- **Google Calendar** is a per-user grant scoped to `calendar.events`, on a **separate `genericOAuth` provider (`"google-calendar"`)** rather than the login provider — so signing in never demands calendar access, and a plain login row can't be mistaken for a live calendar connection. It needs `accessType: offline` + `prompt: consent` to get a refresh token, or reads break after the ~1h access token expires. `syncedMeetingTombstone` records meetings the user deleted post-sync; `commitFillTombstone` is the same idea per *day* for the rest-of-day block. Creating a fill block deliberately clears the tombstone, since that is a change of mind.
- **Slack** is one workspace per org (`slackInstallation`), installed by an admin through Slack's OAuth v2 flow. The bot token is written straight to the database — no client, form or validator ever handles it, and no server function returns it. The redirect URI is derived once in `slackRedirectUri()` because Slack byte-compares it across the two legs. Membership hooks (`afterAcceptInvitation`, `afterAddMember`) auto-match new people to Slack; `linkMember` swallows its own errors, so a Slack outage costs the match, not the membership. "Re-match people" (`syncIdentities`) skips archived people but keeps their existing match. An invitation also goes out as a Slack DM (`slackService.sendInvitation`, from `sendInvitationEmail` in `auth/index.ts`) when the address maps to a Slack user — not awaited, never throws, and not recorded on `invitationEmail`. Env: `SLACK_CLIENT_ID/SECRET`.

### The assistant

An OpenRouter-backed chat page (`$orgSlug/assistant`) that answers questions about tracked time and can log more of it. `services/assistant.service.ts` is the agent loop — up to `MAX_STEPS` billed model calls per turn, plus one to title a new thread; `services/assistant-tools.ts` is what it may do.

- **The step ceiling ends in an ANSWER, not an error.** `MAX_STEPS` (8) is a ceiling on model round-trips, and the number is in the system prompt so most turns never reach it. A turn that does gets one more call with the tools taken away (`OUT_OF_STEPS`) — the model cannot ask for a ninth step, so it terminates, and the person gets what the eight steps found plus what is missing from it. The nudge is not stored: it is the loop talking to the model about its own ceiling, not something anyone said. Only a closing answer that is empty falls back to an error (`NO_ANSWER`).
- **A step's independent reads run together.** `runClaimedBatch` claims the leading run of `read` tools in ONE transaction and awaits them with `Promise.all`, so four lists cost one round trip and not four. Writes stay strictly in order. `AssistantTool.serial` opts a read out — `list_time_entries` sets it, because `listRange` writes on read (see Gotchas) and two overlapping ranges would recompute a day's fill block at once. **A new read that reaches a service which writes must set `serial`**; nothing detects it, and the failure is a race.
- **A capped tool result is cut by ROW where the value is a list** (`MAX_TOOL_RESULT_CHARS`), never mid-object, and the note says how many rows were dropped and tells the model to narrow the call ITSELF rather than send the person back to re-ask.

- **Every tool is an adapter onto an existing service, called with the CALLER'S own `Ctx`.** That is the whole authorization story and it is deliberately not restated per tool: a Member's `list_time_entries` returns their own rows because `listRange` filters on `ctx.userId`, and their `create_project` is refused because `canCreateProjects` says so. Tool parameters are the *existing* Zod inputs from `src/schema/*` via `z.toJSONSchema()`, so the model inherits the UI's ceilings.
- **A tool description must say what OMITTING an optional filter means.** `time_report_summary` and `time_report_detail` default `userId` to "everyone the caller may see", which for a PM, Team Lead or Admin is the whole team. The old wording ("scoped to what the caller is allowed to see") was true and read as "scoped to the caller": ten of thirteen benchmarked models answered "how many hours did I log in August" with the team total, presented as the person's own. Spelling the default out fixed it in every model that got it wrong. A number that is right for a Member and silently wrong for their manager is the failure mode to look for when adding an optional filter.
- **`toolDefinitions(access)` is scoped to the caller, and that is not the authorization.** `AssistantTool.available` only decides what the model is *told* it can do — every definition is re-sent on every step, so offering a Member the admin reports costs tokens and a step spent being refused. Keep predicates coarse ("is a PM anywhere", never "on THIS project"), because the arguments don't exist when the list is built.
- **Three tool kinds (`ToolKind`), and the line is "can they undo this by asking for the opposite".** `read` answers; `write` (logging and correcting time, booking absence, creating clients/projects/tasks, unarchiving) runs inline; `destructive` (deleting an entry or a recurring rule, removing absence, archiving) suspends for approval.
- **A tool's arguments must be producible by some read, or it is uncallable** — hence `list_unfiled_entries` for `file_time_entries`, `list_commits` returning `projectGithubRepoId` + `sha` for `attach_commits`, and `list_tasks` including the absence tasks that `log_absence` needs.
- **`assistantSettings.systemPrompt` is house rules an admin appends**, fenced in `<house-rules>` and ranked below the built-in prompt, which encodes domain facts (quarter-hour granularity, ids are looked up not invented) that stay true whatever an org layers on.
- **Approval state lives on the message row** (`pendingApproval`, `approvalSummary`, `approvalPreview`), not on the SSE connection. Approving is a *second* `run` call, so a tab closed mid-approval leaves a card that still works on reload. The summary and preview are stored because they are what the person consented to, and because `assistant-tools.ts` imports the services barrel and can never reach the browser to rebuild them. `summarize` may look its argument up and must fall back rather than throw — a card that fails to render leaves a pending write nobody can answer.
- **A batch write suspends once and is approved row by row.** A tool with `preview` (`apply_day_assembly`, `file_time_entries`) stops the turn and shows a table; `withSelection` rebuilds the arguments from every row EXCEPT the unticked ones. Exclusion, because the card shows at most 25 rows — phrased as inclusion, approving a 40-row batch would write 25. An empty selection is a refusal, not a write of nothing.
- **Every `tool_calls` turn needs one `tool` result per call id, or the next request 400s.** So a rejection still writes a `tool` message, and a message typed past a pending card declines every unanswered call and clears `pendingApproval` BEFORE the user message is stored. `toWireMessages` repairs threads already stored in the wrong order. `claimCall` (a row lock plus a re-read) makes approval atomic, so two tabs approving one card run the tool once.
- **`components/assistant/answer.tsx` and the prompt's formatting rules change together.** The reader is hand-rolled markdown plus three directives the prompt describes verbatim: `[[YYYY-MM-DD]]` (a link to that day's timesheet), `farmer-chart` fences and `farmer-next` chips. A construct promised in the prompt and missing in the reader renders as its own syntax. It re-parses on every streamed delta, so half-arrived input must degrade, never throw. It also recovers from wrappers a small model adds — a fence whose body is only a pipe table is a table, a `json` or untagged fence that parses as a chart spec is a chart, `farmer-next` is read without its closing fence — but it never invents a directive the model did not write.
- **The composer clears on send and takes the draft back when the send never landed.** `useAssistantActions().send` resolves false when no `message` event arrived — the server's receipt, written before the model is called — and `PromptBar` restores the text and focuses it. A rate limit or a dead session used to cost the person everything they had typed, next to an error line telling them to try again. A turn that started and then failed keeps the message, because by then it is in the thread.
- **The tool trace names its subject** (`ToolTraceList`, `toolDetail` in `components/assistant/primitives.tsx`): `tool_start` carries the call's raw arguments and the CLIENT decides the wording, beside `toolLabel`. A column of four identical "Read time entries" says nothing about what was read. **The ids in those arguments are resolved to names client-side** — `userId` to a face and a name from `directoryQuery`, and `projectId`/`clientId`/`taskId` from their own lists — because a report filtered per person is otherwise six rows reading the same date range. Each list is fetched only once a trace row actually carries that kind of id, so an ordinary turn costs no extra request; an id whose name has not arrived is left out rather than printed raw.
- **A turn belongs to a THREAD, and the run store is keyed on the conversation** (`components/assistant/assistant-runs.tsx`, mounted by the `/$orgSlug` layout). The streamed text, the tool traces, the pending card and the error all live per conversation id, so opening a second thread does not show it the first one's answer, and two threads run side by side — one turn at a time PER CONVERSATION, not per person. It is above the route rather than on the page for two reasons that are one: the thread list is in the SIDEBAR, which the page does not contain, so nothing on the page could tell it a thread is working; and a turn then survives navigation, so asking a long question and going to look at your timesheet finds the answer waiting. Three contexts, not one — the rail reads `useAssistantRunning()` (the ids, which change twice a turn) rather than the run map (which changes per token).
- **An assistant turn with neither text nor a tool call is an error, not a `done`.** The blank row it used to store is one the transcript skips — an assistant row with no text is a pure tool turn, rendered as its trace — so the person was left looking at their own question with nothing under it and no explanation, which is how a short follow-up ("let me see it") read when a model returned an empty completion. It is answered with `NO_ANSWER`, the same words the out-of-steps path uses.
- **The model is told who it is talking to, before it reads anything** (`callerCard` in `assistant-tools.ts`: name, email, user id, organization and the caller's tier, in the system prompt). Told only the date and that `whoami` exists, asked for "Omar's notes" it read the member list, failed to find Omar in the first page of a 200-person roster, and reported that no such person works here — to Omar. Identity is needed to understand the QUESTION, so it cannot sit behind a tool call; `whoami` keeps the rest (working hours, member type, the project list), which is a real read and belongs behind one.
- **The turn streams over a server ROUTE** (`routes/api/assistant/stream.ts`), because a `createServerFn` resolves to one value. It is rate-limited per user (`server/assistant-rate-limit.ts`), since each turn spends the org's key; it stops the model loop when the client disconnects, sets `X-Accel-Buffering: no`, and passes only the app's own error classes to the browser. `lib/openrouter-client.ts` passes its own long timeout, because `externalFetch`'s 15s deadline covers the whole request and would cut a streamed answer mid-sentence.
- **Three switches, all different.** `ASSISTANT_ENABLED=false` (env, default on) takes the feature off the deployment: no nav row, no route, a 404 from the stream endpoint, and every service path refused — except `settings.disconnect`, so a key stays removable. `assistantSettings.enabled` is an admin pausing it for one org. A missing `assistantSettings` row is "never connected". `$orgSlug/route.tsx` resolves `assistantAvailable` from all three for both navs, so a paused org has no Chat tab leading to an explanation; the route still explains itself to someone who typed the URL.
- **Model choice is admin-only.** A conversation pins `assistantSettings.defaultModel` when it starts (`createConversationInput` carries no `model`), so changing the default never re-answers an old thread.
- The OpenRouter key is per-org, set by an admin in Settings → Integrations, and follows the Slack bot token's rule — written straight to the database, never returned. `settings.get` answers with a leading-characters hint, since the tail is the unguessable part.
- The transcript's swap, scroll pinning and wide-table bleed (`FadeSwap`, `PinToEnd`, `.answer-wide`) are explained at their call sites in `assistant.tsx` and `styles.css`.

### The MCP server

The same tool layer as the assistant, over Streamable HTTP, for Claude Code and any other MCP client (`apps/web/src/routes/api/mcp/$orgSlug.ts`). There is no second registry and no second authorization story: `assistant-tools.ts` is the surface, and each service re-resolves `Access` and asserts.

- **The organization is in the URL, and it has to be.** An access token resolves to a `userId` and scopes — there is no `session.activeOrganizationId` for it to carry, and every Ctx needs an organization. Somebody in two workspaces gets two connector entries rather than a mode they must remember they are in.
- **`orgContextService.resolveBySlug(userId, orgSlug)` is the only membership check in front of the whole surface** (tested in `services/org-context.test.ts`); the CLI's API asks it in the same words. A slug nobody owns and a slug the caller is not in give the same answer, so a valid token cannot enumerate workspaces. **An MCP token outlives a membership by much more than a session does** — it sits in a config file until somebody revokes it — which is why this check decides whether the URL still answers. `resolveMcpOrgContext` (`server/api-auth.ts`) accepts the session cookie first, then an MCP bearer token; that ordering is safe only while better-auth's `bearer` and `apiKey` plugins stay off.
- **Tool kinds become annotations** (`mcp-tools.ts`: `read` → `readOnlyHint`, `destructive` → `destructiveHint`) and the client decides what to prompt about. The approval cards do not survive the trip, so the two batch tools are all-or-nothing writes here. `toolsFor(access)` scopes the list, and `available` is re-checked on every call because clients cache tool lists. Results are not truncated (the assistant truncates at `MAX_TOOL_RESULT_CHARS`), and failures come back as `isError` tool results, not JSON-RPC errors.
- **Stateless:** one server per request (`sessionIdGenerator: undefined`, `enableJsonResponse: true`).
- **`packages/core` holds no MCP SDK import**, and the route defers the SDK inside its handler — `routeTree.gen.ts` imports every route module statically, so a top-level SDK import would ship to the browser.
- **Its own switch, deliberately not the assistant's.** `MCP_ENABLED=false` (env, default on, `lib/mcp-flag.ts`) 404s the endpoint — 404, not 403, since there is nothing to be authorized for — but leaves the OAuth server mounted, so issued tokens stay revocable. The three feature flags are independent of each other. Settings → Integrations shows the connection URL to everyone, since a connection is a person's own.
- **better-auth is the authorization server** (`mcp({ loginPage: "/api/mcp-login" })`), with no consent screen (the client is the person's own editor, and the token grants exactly what they can already do) and dynamic client registration. The two discovery documents are real routes under `routes/[.]well-known/`, not handlers in `server.ts` — `vite dev` never loads `server.ts`. A client finds them through the 401's `WWW-Authenticate` header, whose origin must come from `BETTER_AUTH_URL`, not the request, to match what the documents publish. `routes/api/mcp-login.ts` rebuilds the authorize URL and hands it to `/api/login?redirect=…`, so neither login route has to widen its search schema; getting it wrong fails as an infinite redirect rather than an error.
- **In-memory rate limits, per process, in two layers** (`server/api-rate-limit.ts`, one set of buckets per surface — `"mcp"` and `"cli"`): per user (requests, and calls that are not `read`), and per caller address — counted by `admitCaller`/`recordAuthFailure` **before** any session or token lookup, so an unauthenticated flood costs no queries. The address comes from proxy headers (`cf-connecting-ip`, `x-real-ip`, then the first `x-forwarded-for` hop), so behind a proxy that does not overwrite them it is a per-*claimed*-address limit, with the per-user one still behind it. Per-process is correct only because this deployment is one instance. An agent loop re-reads far harder than a person does — see the `listRange` gotcha.

### The CLI

`farmer`, a command-line tool to log and read your own time (`apps/cli`, package `@farmer/cli`). A real CLI over a REST API, not an MCP client: tool results are shaped for a model and change with the prompt, and a binary installed on somebody's laptop cannot follow them. The spec and the owner's decisions are issue #36; `apps/cli/README.md` is the user-facing half.

- **Login is the device authorization flow** — better-auth's `deviceAuthorization` plugin, client id `farmer-cli`, 10-minute codes. `farmer login` shows a code and opens `/device` (`routes/device.tsx`), where the signed-in person approves it. **Opening the page is what binds the code to that person** (better-auth's `GET /device` claims it, and approve refuses an unclaimed code), so the page makes that call on mount, client-side, before Approve can work. It reads `user_code` from the raw query string, because the router `JSON.parse`s search values and `2E345678` comes back a number.
- **The token is a better-auth session token, and the `bearer` plugin stays off.** With that plugin every server function would accept an `Authorization` header and `resolveMcpOrgContext`'s credential order would stop being safe. `resolveCliUser` (`server/api-auth.ts`) is the only reader: `internalAdapter.findSession`, then the sliding refresh `getSession` does, copied by hand because `findSession` does not slide — without it a token used every day dies seven days after login. The CLI keeps the token in the OS keyring (`Bun.secrets`), or a 0600 `credentials.json` where there is none.
- **Every route runs one pipeline, `server/api-route.ts`** (`apiRoute` for `api/v1/orgs/$orgSlug/*`, `userApiRoute` for `me` and `session`), in a fixed order: `CLI_ENABLED`, the per-address limit before any read, the `x-farmer-cli-version` check (426), the credential, the per-user and write limits, the Zod parse with the `src/schema/*` input, the service call. The organization is in the URL for MCP's reason, checked by the same `orgContextService.resolveBySlug`.
- **A session cookie counts only on a GET.** A signed-in browser can read the URLs the CLI calls, which is how the answers get looked at in development; a write that took the cookie would be CSRF, since a cross-site form can POST `text/plain` with no preflight. A request that sent `Authorization` never falls back to the cookie, so a dead token always gets the 401 that sends the CLI to `farmer login`.
- **Errors map by class, and one rule is only a convention.** `ZodError` and `DayCapacityError` are 422, `AccessError` 403. An error whose constructor is exactly `Error` is taken as a sentence a service threw on purpose and its message goes to the terminal (404 when it says "not found"); anything else is logged and answered 500. **Throw a subclass for anything that is not a sentence for the person** — `lib/github-client.ts` throws bare `Error`s carrying URLs, and is safe today only because no route reaches it.
- **Routes answer projections, never rows** (`src/api/`). A new column must not become a field an installed binary depends on. Raise `MIN_CLI_VERSION` (`api/meta.ts`) when a shape changes in a way an old binary cannot read; `GET /api/v1/meta` hands it out unauthenticated and the pipeline enforces it on every request.
- **Repository defaults are ids in a `.farmer.jsonc` the repository commits** (`apps/cli/src/repository-defaults.ts`, `farmer init`; the design is ADR 0002). The nearest file up to the git root names the `org` slug every command runs in, and the `project` and `task` ids `farmer log` uses when `-p`/`-t` are missing — never codes or names, which drift onto another project silently. A flag wins and `--org` turns the file off; each value taken is announced on stderr; a broken or stale file stops the command rather than falling back to the personal default organization. The MCP server cannot read the file, so its `instructions` (`routes/api/mcp/$orgSlug.ts`) teach the agent the same rules, and `list_projects` returns `code` for it. `farmer init` suggests projects from the git remote through `api/v1/orgs/$orgSlug/repository-projects` — a route, not a field on `ApiProject`, so an older server's 404 means "no suggestion".
- **The CLI's import boundary is linted.** At runtime `apps/cli` may import only `@farmer/core/schema`, `/lib/time`, `/lib/search` and `/api`; `import type` from services is fine. The `no-restricted-imports` override in `oxlint.config.ts` fails the build on a runtime `@farmer/core/services|db|auth|jobs` import — that is what keeps the server graph out of a binary anyone can download.
- **Install is one command from the app; the binaries live on GitHub Releases.** `curl -fsSL <origin>/cli | sh`, or `irm <origin>/cli | iex` on Windows (`routes/cli/`, both scripts in `server/cli-install.ts`; `/cli` picks one by User-Agent, `/cli/install.sh` and `/cli/install.ps1` name them). The repository is private, so a script cannot read releases itself: `/cli/download/<asset>` finds the newest `cli-v*` release through the same GitHub App the commit sync uses, and 302s to GitHub's signed asset URL (`server/cli-releases.ts`). The App needs Contents: read and an installation that includes the releases repository (`CLI_RELEASES_REPO`, default `profico/farmer`); `getRepoContentsReadToken` (`lib/github-client.ts`) narrows each token it mints to that repository and permission, with a cache deliberately separate from `getInstallationToken`'s. The token never leaves the server and the binary never passes through it. The scripts download the `.gz` copy first (a Bun binary is mostly its runtime, and it compresses to less than half), fall back to the plain binary for a release without copies, verify the binary against `SHA256SUMS` and fail closed.
- **`farmer update` runs the server's install script over the running binary** (`commands/update.ts`), with `FARMER_INSTALL_DIR` set to the binary's directory and `FARMER_UPDATE=1`, rather than downloading a release itself — a second copy of the asset choice and checksum logic would drift. On Windows the script renames the running `farmer.exe` to `farmer.exe.old` first, because Windows refuses to overwrite a running exe and allows a rename. From source (`Bun.main` outside `/$bunfs/`) there is nothing to replace, and the command says so.
- **Releasing is a tag.** Bump `apps/cli/package.json`, push `cli-vX.Y.Z`, and `.github/workflows/cli-release.yml` cross-compiles the seven targets on Linux (`bun run build:release`), runs every binary on its own OS and CPU, and only then publishes, with a `.gz` copy of each binary written after the macOS re-sign. A pull request that touches `apps/cli` runs the same build and runs, without publishing. A deployment serves the new release within the five-minute release-lookup cache.
- **A Bun cross-compile leaves the macOS binaries with a code signature that does not match the file** (checked on 1.3.14 and 1.4.0), and Apple silicon kills such a binary. The workflow re-signs both ad hoc with `codesign` on a Mac runner and writes `SHA256SUMS` after that, so the sums `build:release` writes locally are not the release's. Do not "simplify" the workflow back to one Linux job.
- **The musl binaries need `libstdc++` and `libgcc`**, which Alpine's base image leaves out. The install script checks for both before it downloads, and the Alpine run in the workflow installs them.
- **Signed-in devices is the lost-laptop answer.** Preferences lists the person's sessions (`sessionsService`), labels a CLI one from `CLI_USER_AGENT_PREFIX` in its user agent, and deleting the row is the revocation — the CLI's next request gets a 401 and drops its token. Revoking the session you are using is refused: that is signing out.
- **`CLI_ENABLED=false`** (env, default on, `lib/cli-flag.ts`) 404s `api/v1/orgs/*`, `me`, `session`, the device endpoints (gated in `routes/api/auth/$.ts`), `/device` and `/cli`; `meta` answers `cliEnabled: false`.

### Uploads

An S3-compatible object store holds the images people upload: a project's icon (beside the emoji) and an organization's logo (beside the pasted URL). Deployments run Garage; `docker compose up -d` starts one from `docker/garage/garage.toml` with the credentials in `.env.example`. User avatars are not uploads — they come from the identity provider.

- **Optional, per deployment.** `objectStore()` (`lib/storage.ts`) is null unless `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` are all set (`S3_REGION` is optional, defaults to `us-east-1`, and must match the store's), and the client learns `uploadsEnabled` from `getPublicAppConfig`, so no upload control renders without a store. Signed with `aws4fetch`, not `Bun.S3Client`, because `vite dev` runs server functions under Node.
- **The stored value is a path, `/api/files/orgs/<orgId>/<purpose>/<uuid>.<ext>`, never a bucket URL** (`lib/uploads.ts`, browser-safe). The bucket stays private and `routes/api/files/$.ts` serves it: unauthenticated (the login screen shows the single-org logo), cached as immutable (a new upload is a new key), and with `Content-Security-Policy: sandbox` plus `nosniff`, because an SVG from the app's own origin would otherwise run script with the session cookie in reach. The same column still holds an emoji or a URL — `isUploadedFile` tells them apart, and `ProjectIcon` and the project picker render an `<img>` for it.
- **The type is sniffed from the bytes** (PNG, JPEG, GIF, WebP, SVG; 1 MB), never taken from the file name or the browser's claim, and the served Content-Type follows the extension the sniff chose.
- **Uploading saves nothing.** `uploadsService.uploadImage` returns the path and the ordinary project or org update saves it, so the picker treats a file exactly as it treats an emoji. Who may upload follows who may set it: `org-logo` is Admin, `project-icon` is `canCreateProjects`. A schema can check a path's shape and nothing else, so `projectsService.create`/`update` and `organizationService.updateSettings` call `assertOwnUpload`, which refuses a path uploaded under another organization.
- **Nothing is deleted on replace; a daily sweep deletes what nothing uses** (`jobs/upload-sweep.ts`, `UPLOAD_SWEEP_ENABLED`). Two projects may wear one file, so a replace cannot know the file is free — the sweep asks whether ANY `project.icon` or `organization.logo` still points at it, and those are the only two columns that may hold a path. **A new column that stores an upload path must be added to `referencedKeys` there, or the sweep deletes its files.** It keeps anything under a day old (the upload and the save are two requests), anything not of the upload key shape, and anything under an organization this database does not have — which is what stops a dev database pointed at a shared bucket from wiping production's files. The dev worker leaves it off for the same reason.
- **The bucket has a quota on deployments** (Garage `bucket set-quotas`). A write refused for it surfaces as `ObjectStoreFullError`, which `uploadImage` turns into an `UploadRejectedError` the person can read.

### Single-organization mode

Setting `SINGLE_ORG_SLUG=<slug>` turns a deployment into a one-workspace, invite-only instance. Unset (the default) is the normal multi-tenant product, and every code path below is a no-op. It is a slug rather than a boolean so "which organization?" is never implicit.

- **The switch is `packages/core/src/lib/single-org.ts`** — server-only. The client never reads the env var: `apps/web/src/server/config.ts` (`getPublicAppConfig`) hands it the mode plus the org's name/logo/slug.
- **The signup gate is a `databaseHooks.user.create.before` hook, not a screen.** Signing in with Google *is* the signup, and the user is created mid-OAuth-callback. The hook throws an `APIError` carrying a `code` (`INVITE_ONLY`) — that field is load-bearing, since better-auth's OAuth callback only turns a thrown error into a redirect back to `errorCallbackURL` when one is set, and otherwise surfaces a raw 403 mid-round-trip.
- **Bootstrap: the first person to sign in on an unclaimed instance creates the org and owns it.** The race is settled by the unique index on `organization.slug`, not a read-then-write check.
- **`allowUserToCreateOrganization: false` + `disableOrganizationDeletion: true`** are what actually close those endpoints; hiding the switcher's "New organization" item is presentation.
- **URLs keep the `/$orgSlug` prefix.** Tenancy stays an explicit parameter, matching the service-layer rule.
- **`/no-access` exists to break a redirect loop.** A signed-in user with no membership would otherwise bounce `/` → workspace → `/` forever. It lists their live invitations through a local server fn, because better-auth's `listUserInvitations` rejects any caller whose email isn't verified, and this app has no verification flow.

### Production

Dev is `vite dev`. **Production is a Bun-native host, not Nitro/srvx**: `vite build` emits a web-standard `{ fetch }` handler with nothing to serve it, so `apps/web/server.ts` (TanStack's start-bun reference) brings its own `Bun.serve` — static-asset preloading plus the in-process schedulers.

The `Dockerfile` bundles with `bun build` into `app.js` (better-auth, framer-motion and the `#tanstack-*` entries stay external), `migrate.js` and `seed-tasks.js`, and installs runtime dependencies from `docker/runtime.package.json` + `docker/bun.lock`. `docker-entrypoint.sh` applies migrations under an advisory lock (`RUN_MIGRATIONS`), seeds tasks (`RUN_SEED`), then starts `app.js`. CI (`.github/workflows/ci.yml`) runs check, typecheck, test and build, then builds the image, pushes it to GHCR and triggers a Coolify deploy. The CLI has its own release workflow (see The CLI).

**`Bun.serve` carries `idleTimeout: 255`, Bun's maximum, and it is load-bearing.** The default is 10 seconds, and Bun enforces it by closing the socket with an empty reply while the handler keeps running. A server function that works longer than that — "Re-match people" on Slack, a Harvest import step — then succeeds on the server while the browser gets an unreadable reply, which TanStack Start reports as the bare "Invariant failed". `vite dev` does not run `server.ts`, so this never reproduces locally. Work that can outlast 255 seconds belongs in a job, not a request.

**This backend is a long-lived process, not a serverless function — background work goes in a job, never in a request handler.** There are four jobs: the automation sweep, log reminders, Slack reminders and the upload sweep. The scheduler lives in `@farmer/core/jobs/scheduler.ts` rather than in `server.ts` so it can run three ways off one implementation:

| Where | How | Why |
|---|---|---|
| Production web host | `startSchedulers()` in `server.ts` | default; single instance |
| Development | `vite dev` spawns `packages/core/src/jobs/worker.ts` (the `farmer:dev-worker` plugin) | `vite dev` never loads `server.ts`, and nothing syncs on page load. Runs the **automation sweep only**: the other jobs message real people or delete files, and dev usually points at a shared database. `DEV_WORKER=false` to opt out |
| Separate worker container | `bun run worker` from `packages/core` | set every `<NAME>_ENABLED=false` on the web host; run exactly one worker |

Each job is env-gated by `<NAME>_ENABLED` / `<NAME>_INTERVAL_MINUTES`; the full list, with `AUTOMATION_SYNC_CONCURRENCY`, `AUTOMATION_SYNC_USER_TIMEOUT_MS`, `EXTERNAL_FETCH_TIMEOUT_MS` and `SCHEDULER_STARTUP_DELAY_MS`, is in the `scheduler.ts` header, and `.env.example` documents the rest. All of it assumes a single instance; the jobs are idempotent, so a second replica is redundant rather than harmful. The tables in `scheduler.ts` are built by hoisted **functions**, not module-scope `const`s — that is load-bearing in the bundled image, and the header explains why.

`ASSISTANT_ENABLED`, `MCP_ENABLED`, `CLI_ENABLED` and `SINGLE_ORG_SLUG` are plain env vars rather than `VITE_` ones, because `VITE_` values bake at build time and the Dockerfile builds one image for several environments.

## Testing

`bun test` from `packages/core` (or `bun run test` from the root). Test files sit beside the code as `*.test.ts`. `apps/cli` has its own `bun test` (the duration and date parsers, the table format, the device flow and the API client against an injected `fetch`). `apps/web` has none, so `api-route.ts` and the routes are untested — which is why everything testable about the CLI's API (the membership check, the projections, the version compare, the flag) lives in `packages/core`.

`createTestDb()` (`src/test/harness.ts`) gives each test file an empty, freshly migrated **PGLite** (real Postgres, in-process WASM) and points the `db` proxy at it for the file's duration — no DATABASE_URL, no container, no cleanup. `src/db/index.ts` resolves its handle lazily for this reason. **One engine is shared for the whole run and re-schema'd per file**, because a `WebAssembly.Memory` never shrinks: per-file engines made the suite's footprint the sum of every database it had opened (~11GB), which a 7GB CI runner answers with SIGKILL. `bunfig.toml` preloads `src/test/preload.ts` to close that engine at the end — a live handle at exit is exit code 99 and a red CI for a suite where nothing failed.

Fixture rules:
- The harness runs the migrations but **not** `db/seed-tasks.ts`, so Vacation and Sick Leave don't exist unless you insert them. Migrations already seed **Meeting** and **Break** (`0024`) and **Paid Leave** (`0038`); inserting those again violates `task_site_name_uidx` — look them up by `systemKey`.
- Site-scoped tasks are unique on both name and `systemKey`, so seed Vacation once in `beforeAll`, not per test.
- A single multi-row insert of a few thousand rows overruns PGLite's bind-parameter handling and kills the instance for the rest of the FILE. Chunk at ~500.
- A person needs an `account` row to receive a reminder (see Notifications).
- Pin the clock with `{ now }` where a service takes it (`compliance`, both reminder jobs, `runAutomationsForUser`) rather than depending on today's date.

The services that turn logged time into a number somebody acts on — `reports`, `compliance`, `hour-fund` — are pinned on properties rather than outputs: a detail's total stays whole when its rows hit the cap, Team Lead scoping holds on every tab, a null fund is not zero, `prefillYear` never clobbers a hand-entered figure.

**Not covered at all**, so the suite cannot tell you whether you broke them: the `google-calendar` **service** (its `lib/` client is tested); the `slack` service beyond `syncIdentities` and `sendInvitation`; the GitHub installation flows (`connectInstallation` and the setup callback); `notificationsService.sendPush` (it reads VAPID keys from the environment); member role changes (better-auth's `updateMemberRole`, which has no service function); and everything in `apps/web`.

## Gotchas

- **Never read the org roster through better-auth's `auth.api.listMembers`.** It throws in an organization over 100 people, which a Harvest import makes routine — archived people count towards the total. `membersService.roster` (`members.service.ts`) queries the tables directly and is what `server/members.ts`'s `listMembers` server fn calls; `auth/index.ts` also raises `membershipLimit` to 10,000 for the paths that still go through better-auth. Don't confuse either with `projectsService.listMembers`, which is a per-project assignment read.
- Bun does not walk up parent directories for `.env` in a workspace — `bun run` inside `packages/core` or `apps/web` won't see the root `.env`. Each workspace package has a symlink to the root `.env`; do the same for any new workspace that reads the environment.
- **`vite build` can emit server code into `dist/client`, and `server.ts` serves everything it finds there.** A deferred `await import("@farmer/core/…")` in a client-reachable module is chunked by rolldown *before* the server-fn transform strips the handler, which leaves an orphan island (better-auth's config, the drizzle schema, services) published at `/assets/<hash>.js`. `apps/web/scripts/prune-client-assets.ts` runs as the second half of `bun run build`, deletes the island and prints what it removed. It currently prunes nothing; keep it anyway, because it is the detector. It computes reachability from what the server build can name and aborts rather than guess — don't "simplify" it into an unconditional delete, and don't drop it from the `build` script.
- `timeEntriesService.listRange` still performs writes on read — it recomputes (and drops) each day's fill block against the rows just read, bounded to the automation window. That is deliberate and commented, but a GET is not idempotent, including through `api/v1`, `farmer today` and the MCP server's `list_time_entries`. **The MCP case is the one to watch**: an agent loop re-reads a range far harder than a person opens a screen.
- Base UI shadcn components have runtime-only failure modes that typecheck/build/lint all miss: `<Button render={<Link/>}>` to a non-`<button>` element needs `nativeButton={false}` or it throws in the console; `<Select>` needs an `items={[{value, label}]}` prop or the trigger displays the raw value instead of the resolved label.
- Always verify interactive changes in a real browser, not curl/SSR output — the hydration crash described above passed every curl-based check while silently breaking every form in the app. No browser automation package is installed in the repo.
