# The REST API pipeline

`apps/web/src/server/api-route.ts` runs each `api/v1` route that is built with `apiRoute` or `userApiRoute`. Some `api/v1` routes do not use it, for example `meta`, `openapi[.]json` and `me/devices`. Read this before you change `api-route.ts`, `api-auth.ts`, `lib/posthog-api.ts` or an `api/v1` route. The credentials are in `docs/domains/api-tokens.md`.

- **Every route runs one pipeline, `server/api-route.ts`** (`apiRoute` for `api/v1/orgs/$orgSlug/*`, `userApiRoute` for `me` and `session`), in a fixed order: `CLI_ENABLED`, the per-address limit before any read, the `x-farmer-cli-version` check (426), the credential, the per-user and write limits, the Zod parse with the `src/schema/*` input, the service call. The organization is in the URL for MCP's reason, checked by the same `orgContextService.resolveBySlug`.
- **The pipeline is also where this surface is REPORTED** (`lib/posthog-api.ts`, deferred inside `serve` for the client-bundle rule in `apps/web/CLAUDE.md`). Every exit runs through one `finish`, so a request refused by the flag, the rate limiter, the version check or the credential is counted exactly like one that was served — a CLI being turned away is what a per-route capture would miss, and there are nineteen routes that would each have to remember. One `api_request` event carries the route TEMPLATE (`/api/v1/orgs/:orgSlug/time-entries/:id`, never the slug or the row id), the method, the status, the duration and `api_caller` — `cli` or `browser`, taken from the version header rather than guessed from the user agent. A generic 500 also raises an `$exception`; a 403, a 404 and a 422 are answers this pipeline gives on purpose and are not faults. A request that resolved no person rides `$process_person_profile: false`, so a refused flood stays countable without minting people. The CLI BINARY stays uninstrumented on purpose: a tool installed on somebody's laptop cannot be asked to report truthfully, and an old binary would report nothing at all.
- **A session cookie counts on a GET, and on a write only with proof of the same origin** (`cookieUser` and `provesSameOrigin`, `server/api-route.ts`). A signed-in browser can read the URLs the CLI calls, which is how the answers get looked at in development. A write takes the cookie only when it carries `x-farmer-session: 1` (`lib/api-session-header.ts`) and, when the browser sends one, `Sec-Fetch-Site: same-origin` — that is what lets the API reference at `/api-docs` send requests as the reader. A cross-site form can POST `text/plain` with no preflight, but it cannot set a custom header, and a cross-site `fetch` that sets one needs a CORS preflight that nothing under `api/v1` answers. **Never add CORS headers to `api/v1`**: that is the whole defence. `DELETE /session` never takes the cookie (`userApiRoute` passes `writes: false`), since it revokes the credential it was sent. A request that sent `Authorization` never falls back to the cookie, so a dead token always gets the 401 that sends the CLI to `farmer login`.
- **Errors map by class, and one rule is only a convention.** `ZodError` and `DayCapacityError` are 422, `AccessError` 403. An error whose constructor is exactly `Error` is taken as a sentence a service threw on purpose and its message goes to the terminal (404 when it says "not found"); anything else is logged and answered 500. **Throw a subclass for anything that is not a sentence for the person** — `packages/core/src/lib/github-client.ts` throws bare `Error`s carrying URLs, and is safe today only because no route reaches it.
