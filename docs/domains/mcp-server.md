# The MCP server

The same tool layer as the assistant, over Streamable HTTP, for Claude Code and any other MCP client (`apps/web/src/routes/api/mcp/$orgSlug.ts`). There is no second registry and no second authorization story: `assistant-tools.ts` is the surface, and each service re-resolves `Access` and asserts.

- **The organization is in the URL, and it has to be.** An access token resolves to a `userId` and scopes — there is no `session.activeOrganizationId` for it to carry, and every Ctx needs an organization. Somebody in two workspaces gets two connector entries rather than a mode they must remember they are in.
- **`orgContextService.resolveBySlug(userId, orgSlug)` is the only membership check in front of the whole surface** (tested in `services/org-context.test.ts`); the CLI's API asks it in the same words. A slug nobody owns and a slug the caller is not in give the same answer, so a valid token cannot enumerate workspaces. **An MCP token outlives a membership by much more than a session does** — it sits in a config file until somebody revokes it — which is why this check decides whether the URL still answers. `resolveMcpOrgContext` (`server/api-auth.ts`) accepts the session cookie first, then an MCP bearer token; that ordering is safe only while better-auth's `bearer` and `apiKey` plugins stay off.
- **Tool kinds become annotations** (`mcp-tools.ts`: `read` → `readOnlyHint`, `destructive` → `destructiveHint`) and the client decides what to prompt about. The approval cards do not survive the trip, so the two batch tools are all-or-nothing writes here. `toolsFor(access)` scopes the list, and `available` is re-checked on every call because clients cache tool lists. Results are not truncated (the assistant truncates at `MAX_TOOL_RESULT_CHARS`), and failures come back as `isError` tool results, not JSON-RPC errors. A failure's message passes only when `classifyServiceError` (`services/error-message.ts`, shared with the CLI's API and the assistant's tool results) says a person may read it; anything else — a `DrizzleQueryError` carries its SQL and parameters — is logged and answered with a generic line. `agentErrorMessage` (`services/error-message.ts`) wraps that check and adds a recovery hint to a refused task (`Task not available`) or project (`Project not found`): which tool to call for the current ids. The assistant's tool results use the same function, because both readers are a model. The hint is not in the guard, so the web app, the REST API and the CLI keep the short guard message. The hint is the same for a missing id and for another organization's id, so it leaks nothing.
- **Stateless:** one server per request (`sessionIdGenerator: undefined`, `enableJsonResponse: true`).
- **A request body over 1MB is a 413** (`MAX_MCP_BODY_BYTES`), because the SDK's transport calls `request.json()` with no limit. A `Content-Length` over it is refused before the credential is resolved; a chunked body is read with a ceiling (`lib/request-body.ts`) after auth and handed to the transport as a fresh `Request`. The host's global body cap (`server.ts`) is the backstop.
- **`packages/core` holds no MCP SDK import**, and the route defers the SDK inside its handler — `routeTree.gen.ts` imports every route module statically, so a top-level SDK import would ship to the browser.
- **Its own switch, deliberately not the assistant's.** `MCP_ENABLED=false` (env, default on, `lib/mcp-flag.ts`) 404s the endpoint — 404, not 403, since there is nothing to be authorized for — but leaves the OAuth server mounted, so issued tokens stay revocable. The three feature flags are independent of each other. Settings → Account → Integrations shows the connection URL to everyone, since a connection is a person's own.
- **better-auth is the authorization server** (`mcp({ loginPage: "/api/mcp-login", oidcConfig: { consentPage: "/mcp-consent" } })`), with dynamic client registration and **a consent screen on every authorization** (`routes/mcp-consent.tsx`). There used to be none, on the reasoning that the client is the person's own editor; but registration is open to anybody with any redirect, so an authorize link from a stranger sent the person's code to the stranger's server without a prompt. better-auth shows the page only when the client sends `prompt=consent`, so `hooks.before` in `auth/index.ts` forces it, and `auth/mcp-consent.ts` holds the two endpoints behind it to the answer: `/oauth2/consent` takes a consent code only from the account it was made for, and `/mcp/token` spends no code that is still pending or whose client this person never approved. The token check reads a request exactly as the plugin's handler does (a refresh passes straight through; `null` or `""` is no code; anything else is `String(code)`), so it refuses nothing the handler would have taken. A signed-out request comes back to the same screen after sign-in, because the plugin replays it from a cookie that already carries the forced prompt. The screen shows the client's own name and, the part it cannot fake, the redirect's scheme and host. It appears again on every re-authorization, even for a client the person approved before. The two discovery documents are real routes under `routes/[.]well-known/`, not handlers in `server.ts` — `vite dev` never loads `server.ts`. A client finds them through the 401's `WWW-Authenticate` header, whose origin must come from `BETTER_AUTH_URL`, not the request, to match what the documents publish. `routes/api/mcp-login.ts` rebuilds the authorize URL and hands it to `/api/login?redirect=…`, so neither login route has to widen its search schema; getting it wrong fails as an infinite redirect rather than an error.
- **In-memory rate limits, per process, in two layers** (`server/api-rate-limit.ts`, one set of buckets per surface — `"mcp"` and `"cli"`): per user (requests, and calls that are not `read`), and per caller address — counted by `admitCaller`/`recordAuthFailure` **before** any session or token lookup, so an unauthenticated flood costs no queries. The address comes from the ONE header `TRUSTED_IP_HEADER` names (default `cf-connecting-ip`, see `docs/domains/deployment.md`), else the socket address `server.ts` records (`lib/client-address.ts`). If that header can reach the origin without the proxy overwriting it, it is a per-*claimed*-address limit, with the per-user one still behind it. Per-process is correct only because this deployment is one instance. An agent loop re-reads far harder than a person does — see the `listRange` gotcha.
- **Every request is instrumented for PostHog** (`lib/posthog-mcp.ts`, deferred inside the handler with the SDK for the same reason). `instrument()` patches `setRequestHandler`, so it runs BEFORE the handlers are registered or it wraps nothing, and it gives `$mcp_tool_call`, `$mcp_tools_list`, `$mcp_initialize` and an `$exception` per failed call. Identity is static — the route resolved the credential and the membership before it built anything, so there is nothing for the SDK's per-request `identify` to learn. **Two of its options are deliberately off, because both rewrite the tool SCHEMAS**: `context` (on by default) adds a required narration argument to every tool and captures it as `$mcp_intent`, and `captureModel` adds an `llm_model` argument for a value the SDK itself calls unverified. Turning either on is a product decision about a 52-tool contract, not an analytics one. With no protocol session to anchor to (stateless), `$session_id` is one per request; `enableConversationId` is the SDK's fix and injects an argument of its own.
- **An empty answer is not an error, and nothing else catches it.** `beforeSend` in `posthog-mcp.ts` puts `mcp_result_rows` and `mcp_result_empty` on every `$mcp_tool_call`, as METADATA rather than as something read back off `$mcp_response` later: the response is content, so it is `[redacted]` wherever `POSTHOG_AI_CAPTURE_CONTENT` is off, and a monitor built on it would go quiet at exactly the moment somebody tightened privacy. The row count is parsed, not measured — every tool answers with `JSON.stringify`, so a list tool's body really is a JSON array, and an object or a sentence reports `null` rather than being counted as zero rows. `$mcp_is_error` stays false for a tool that worked and matched nothing, so a broken filter, a lost assignment or an agent calling a tool wrongly is invisible without the flag.
