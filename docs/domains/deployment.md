# Production

Dev is `vite dev`. **Production is a Bun-native host, not Nitro/srvx** — `apps/web/server.ts` brings its own `Bun.serve`, with static-asset preloading and the in-process schedulers. That host, and its load-bearing `idleTimeout`, are documented in `apps/web/CLAUDE.md`.

The `Dockerfile` bundles with `bun build` into `app.js` (better-auth, framer-motion and the `#tanstack-*` entries stay external), `migrate.js` and `seed-tasks.js`, and installs runtime dependencies from `docker/runtime.package.json` + `docker/bun.lock`. `docker-entrypoint.sh` applies migrations under an advisory lock (`RUN_MIGRATIONS`), seeds tasks (`RUN_SEED`), then starts `app.js`. CI (`.github/workflows/ci.yml`) runs check, typecheck, test and build, then builds the image, pushes it to GHCR and triggers a Coolify deploy. The CLI has its own release workflow (see `apps/cli/CLAUDE.md`).

**This backend is a long-lived process, not a serverless function — background work goes in a job, never in a request handler.** There are seven jobs: the automation sweep, log reminders, Slack reminders, the timer sweep (`docs/domains/timer.md`), the upload sweep, the audit sweep (`docs/domains/audit-log.md`) and webhook delivery (`docs/domains/webhooks.md`). The scheduler lives in `@farmer/core/jobs/scheduler.ts` rather than in `server.ts` so it can run three ways off one implementation:

| Where | How | Why |
|---|---|---|
| Production web host | `startSchedulers()` in `server.ts` | default; single instance |
| Development | `vite dev` spawns `packages/core/src/jobs/worker.ts` (the `farmer:dev-worker` plugin) | `vite dev` never loads `server.ts`, and nothing syncs on page load. Runs the **automation sweep only**: the other jobs message real people, delete files or drop a running timer, and dev usually points at a shared database. `DEV_WORKER=false` to opt out |
| Separate worker container | `bun run worker` from `packages/core` | set every `<NAME>_ENABLED=false` on the web host; run exactly one worker |

Each job is env-gated by `<NAME>_ENABLED` / `<NAME>_INTERVAL_MINUTES`; the full list, with `AUTOMATION_SYNC_CONCURRENCY`, `AUTOMATION_SYNC_USER_TIMEOUT_MS`, `EXTERNAL_FETCH_TIMEOUT_MS`, `WEBHOOK_DELIVERY_TIMEOUT_MS`, `WEBHOOK_ALLOW_PRIVATE_HOSTS` and `SCHEDULER_STARTUP_DELAY_MS`, is in the `scheduler.ts` header, and `.env.example` documents the rest. All of it assumes a single instance; the jobs are idempotent, so a second replica is redundant rather than harmful. The tables in `scheduler.ts` are built by hoisted **functions**, not module-scope `const`s — that is load-bearing in the bundled image, and the header explains why.

**Request bodies are capped at 32MB** (`MAX_REQUEST_BODY_BYTES`, `server.ts`), because TanStack Start reads a server function's body before any middleware checks the session, and Bun's own default is 128MB. The largest legitimate body is a Harvest import step, a few MB; the constant's comment has the measurement. `vite dev` has no such cap.

**The client address is read from one header, `TRUSTED_IP_HEADER`** (default `cf-connecting-ip`, because Cloudflare fronts this deployment and overwrites it on every request). Only the per-address rate limits of the MCP server and the CLI's API read it (`lib/client-address.ts`). No other header is consulted: a caller can send `x-real-ip` or `x-forwarded-for` too, and the old first-one-wins order let it pick its own bucket. When the header is missing, the socket address that `server.ts` records is used, and under `vite dev`, which has none, one shared bucket. Set it to `x-real-ip` for a proxy that overwrites that one, to `x-forwarded-for` to read the LAST entry (the one the nearest proxy appended), or to `none` to use the socket address only. A trusted header is only as good as the one way in: an origin that also answers on its public address lets a caller set `cf-connecting-ip` itself, so restrict the origin to Cloudflare's address ranges.

**The instance's configuration is a set of instance settings, not only environment variables** (issue #75, `docs/adr/0004-environment-overrides-the-database.md`). Email, the S3 store, the GitHub, Slack and Google credentials, web push, PostHog, `HOMEPAGE_ENABLED`, `ASSISTANT_ENABLED`, `MCP_ENABLED`, `CLI_ENABLED`, `SINGLE_ORG_SLUG` and `CLI_RELEASES_REPO` are listed in `INSTANCE_SETTINGS` (`packages/core/src/lib/instance-settings.ts`), and every reader goes through `setting(name)` or `settingEnabled(name)`. A non-empty environment variable of the same name wins and locks the field on the Infrastructure page; else the `instance_setting` row answers; else the default. An empty variable counts as unset, so `CLI_ENABLED=` now leaves the CLI on. The reads are synchronous from a snapshot that `refreshInstanceSettings()` fills, at most every five seconds, from the global request middleware (`apps/web/src/start.ts`) and each scheduler tick. **A script or a one-off job that is neither must await `refreshInstanceSettings()` before it reads a setting**, or it sees the environment and the defaults only. A change on the page reaches another process (the worker, a second web host) within those five seconds. The operational values (the job switches and intervals, timeouts, `PORT`, `TRUSTED_IP_HEADER`) and `DATABASE_URL`, `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` stay environment-only. None of the settings is a `VITE_` variable, because `VITE_` values bake at build time and the Dockerfile builds one image for several environments.

**Impersonation is not configured here.** The platform admin role — who may become any user in any workspace — is a database value, granted to the instance's first account and passed on from inside the product. There is no environment variable for it, deliberately; see `docs/domains/authentication.md`.

**PostHog's BROWSER half is the part that catches people out.** `POSTHOG_PROJECT_TOKEN` and `POSTHOG_HOST` are instance settings, not `VITE_` variables: `vite build` runs inside the Docker image, so a `VITE_` value could only ever be what CI was given. The server reads them per request (`lib/posthog-server.ts`, one client kept per token and host and rebuilt when either changes, null when either is missing) and `routes/__root.tsx` writes the pair into the inline `<head>` script beside the theme, for the browser to read back off `window`. Not through `getPublicAppConfig`, which is a server FUNCTION: the root route has no loader to call one from, and `RootDocument` is the `shellComponent`, which renders on the error and not-found paths where no loader has run. `POSTHOG_AI_CAPTURE_CONTENT` (default `false`) is the one switch for whether an agent's content — the assistant's prompts and answers, and the MCP server's tool arguments and results — leaves the process at all. The metadata goes either way and is what the dashboards are built on; the content is a customer's timesheet, so on a multi-tenant deployment sending it is a decision an operator makes rather than inherits. Five adapters read that one client and nothing else does: `lib/posthog-ai.ts` (the assistant's turns), `lib/posthog-mcp.ts` (the MCP server's requests), `lib/posthog-api.ts` (the REST API's requests and failures), `lib/posthog-impersonation.ts` (the impersonation ledger, see `docs/domains/authentication.md`) and the `capture` calls in `server/*.ts` (what a person did in the browser).

**Development sends nothing, in either half.** Both `lib/posthog-server.ts` and the browser's config in `routes/__root.tsx` answer null unless `NODE_ENV=production`, so a developer's `.env` — a copy of a real deployment's, token included — cannot put reloads, test clicks and seeded rows into the project the dashboards are built on. It is deliberately not an opt-in variable, which can be copied onto a server. `lib/dev-auth.ts` reads the same variable from the other side (password sign-in only under `development` or `test`), so both fail safe when it is unset. `vite dev` sets `development`, never `production`; the Dockerfile and `apps/web`'s `start` script both pin it. One consequence to know before debugging: a local run cannot exercise the analytics path at all, however the variables are set.

**Rotate the secret with `BETTER_AUTH_SECRETS`, never by changing `BETTER_AUTH_SECRET`.** Every stored credential is encrypted with a key from it (better-auth's OAuth tokens, and `lib/secret-box.ts` for the Slack bot token, the OpenRouter key and the instance's secret settings), so a changed value makes all of them unreadable. `BETTER_AUTH_SECRETS` is better-auth's own rotation set, and `secret-box.ts` reads it the same way, so there is one thing to configure:

1. Set `BETTER_AUTH_SECRETS=2:<new secret>,1:<old secret>` — the new version FIRST, because the first entry is the one that encrypts; the rest only decrypt. Versions are non-negative integers and must be unique. Leave `BETTER_AUTH_SECRET` set to what it was: it still opens every value written before the rotation set existed (`enc:v1:…` here, bare hex in better-auth).
2. Restart. New writes use version 2. The GitHub and Slack install `state` (`lib/oauth-state.ts`) is signed and checked with version 2 only, so a leaked old secret cannot forge one; an install begun in the 15 minutes before the restart fails and is started again. Nothing needs a migration: a value under an older key heals on its next read — the Slack token on the next reminder tick, the OpenRouter key when the assistant next loads it, the instance settings on the next refresh (enabled OAuth sources only) — and on its next write. better-auth's OAuth tokens only move when the provider issues a new token, which for a GitHub OAuth token or a Google refresh token may be never.
3. Drop version 1 only when nothing still carries it: no `enc:v2:1:…` in `slack_installation.bot_token`, `assistant_settings.api_key`, `instance_setting.value` or `instance_oauth_provider.client_secret`, and no `$ba$1$…` in `account.access_token` / `account.refresh_token`. A value under a dropped version is refused like one under a wrong secret. Do not remove `BETTER_AUTH_SECRET` while any `enc:v1:…` or bare-hex value remains.

Without `BETTER_AUTH_SECRETS`, nothing changes: `secret-box.ts` seals `enc:v1:…` from `BETTER_AUTH_SECRET` and `oauth-state.ts` signs with it, as they always did.
