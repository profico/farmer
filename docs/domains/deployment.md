# Production

Dev is `vite dev`. **Production is a Bun-native host, not Nitro/srvx** — `apps/web/server.ts` brings its own `Bun.serve`, with static-asset preloading and the in-process schedulers. That host, and its load-bearing `idleTimeout`, are documented in `apps/web/CLAUDE.md`.

The `Dockerfile` bundles with `bun build` into `app.js` (better-auth, framer-motion and the `#tanstack-*` entries stay external), `migrate.js` and `seed-tasks.js`, and installs runtime dependencies from `docker/runtime.package.json` + `docker/bun.lock`. `docker-entrypoint.sh` applies migrations under an advisory lock (`RUN_MIGRATIONS`), seeds tasks (`RUN_SEED`), then starts `app.js`. CI (`.github/workflows/ci.yml`) runs check, typecheck, test and build, then builds the image, pushes it to GHCR and triggers a Coolify deploy. The CLI has its own release workflow (see `apps/cli/CLAUDE.md`). The push relay (`apps/push-relay`, ADR 0006) has its own image, built from `apps/push-relay/Dockerfile` with the repo root as context. The `push-relay-image` job in `ci.yml` pushes it to `ghcr.io/<owner>/farmer-push-relay` on a push to `main` only, under the same secret check as the web image, and it does not trigger a deploy. Each Dockerfile copies the manifest of every workspace before its frozen install, so a new workspace needs a line in both. The relay's environment is in `apps/push-relay/README.md`. The relay trusts no client-address header unless `TRUSTED_IP_HEADER` names one, and in production (`NODE_ENV=production`, which the image sets) it refuses to start when that variable is unset. `TRUSTED_IP_HEADER=none` means the socket address only, for a relay with no proxy in front. **The relay's Coolify resource must set `TRUSTED_IP_HEADER=cf-connecting-ip`** (Cloudflare fronts it), or every caller shares one rate-limit bucket. `RELAY_MAX_DEVICES` (default 100,000) caps the registrations.

**The image tags depend on the trigger** (`.github/workflows/ci.yml`, job `deploy`). A push to `main` pushes `nightly` and `sha-<long sha>`, then calls the Coolify webhook. Our instance runs `nightly`. A `v*` tag (for example `v1.2.3`) pushes `1.2.3`, `1.2`, `1` and `latest`, and calls no webhook. A pre-release tag (`v1.2.3-rc.1`) pushes only its own version. `cli-v*` and `mobile-v*` tags do not match `v*`. A release tag needs no `COOLIFY_WEBHOOK_URL`, so a fork can publish its own release. `latest` is a release: it does not move on a push to `main`. CI passes the version of a `v*` tag as the build argument `SERVER_VERSION` (the Dockerfile turns it into an environment variable). A nightly image has none. `readServerVersion` (`apps/web/src/server/deployment-info.ts`) reads it, drops a value that is not `major.minor.patch`, and gives `serverVersion` in `GET /api/v1/meta` (null when unset) and the "Version" line in the contributors popover.

**This backend is a long-lived process, not a serverless function — background work goes in a job, never in a request handler.** There are seven jobs: the automation sweep, log reminders, Slack reminders, the timer sweep (`docs/domains/timer.md`), the upload sweep, the audit sweep (`docs/domains/audit-log.md`) and webhook delivery (`docs/domains/webhooks.md`). The scheduler lives in `@farmer/core/jobs/scheduler.ts` rather than in `server.ts` so it can run three ways off one implementation:

| Where | How | Why |
|---|---|---|
| Production web host | `startSchedulers()` in `server.ts` | default; single instance |
| Development | `vite dev` spawns `packages/core/src/jobs/worker.ts` (the `farmer:dev-worker` plugin) | `vite dev` never loads `server.ts`, and nothing syncs on page load. Runs the **automation sweep only**: the other jobs message real people, delete files or drop a running timer, and dev usually points at a shared database. `DEV_WORKER=false` to opt out |
| Separate worker container | `bun run worker` from `packages/core` | set every `<NAME>_ENABLED=false` on the web host; run exactly one worker |

Each job is env-gated by `<NAME>_ENABLED` / `<NAME>_INTERVAL_MINUTES`; the full list, with `AUTOMATION_SYNC_CONCURRENCY`, `AUTOMATION_SYNC_USER_TIMEOUT_MS`, `EXTERNAL_FETCH_TIMEOUT_MS`, `WEBHOOK_DELIVERY_TIMEOUT_MS`, `WEBHOOK_ALLOW_PRIVATE_HOSTS` and `SCHEDULER_STARTUP_DELAY_MS`, is in the `scheduler.ts` header, and `.env.example` documents the rest. Several replicas of the web container are safe. Each tick takes a Postgres advisory lock for its job (`jobs/job-lock.ts`, one key per job name, held on a connection reserved for the tick). The replica that does not get the lock skips that tick. Webhook delivery and Slack reminders take no lock, because they claim each row before they send it. The lock frees itself if the process or the connection dies. The `<NAME>_ENABLED` switches still let you move the jobs to one worker container. A database behind a transaction-mode pooler cannot hold a session lock: use a direct connection for the jobs. The tables in `scheduler.ts` are built by hoisted **functions**, not module-scope `const`s — that is load-bearing in the bundled image, and the header explains why.

**The assistant has two operational flags for a slow model call, both environment-only.** `OPENROUTER_STREAM_TIMEOUT_MS` (default 180000) is the outer limit for the whole call. `OPENROUTER_STALL_TIMEOUT_MS` (default 60000) limits a gap with no progress, not the whole call. The slowest successful calls in production took 80.3 s, 54.3 s and 49.8 s in total. The time to the first progress of those calls was not recorded, so it is not known how close they came to the limit. If a model that thinks long with no reasoning delta shows stalls, raise the value. Set it to 0 to turn the watchdog off. These two and `EXTERNAL_FETCH_TIMEOUT_MS` are read by `durationFromEnv` (`lib/http.ts`): an unset, empty, negative or invalid value gives the default, so an empty line copied from `.env.example` does not set a deadline of 0 ms. 0 is a value only for the stall limit, where it means off, and for `SHUTDOWN_GRACE_MS`, where it means stop at once. For the two deadlines, 0 also gives the default. `ASSISTANT_FALLBACK_MODEL` (default: unset) names the model for the one retry. When it is unset or empty, the retry asks the conversation's own model again, so no conversation goes to a model that its admin did not choose. If you set it, use a pinned id (a `~...-latest` id moves to a new version without notice), and change the privacy text in `apps/web/src/components/site/legal.tsx` to name that model. See `docs/domains/assistant.md`.

**Request bodies are capped at 32MB** (`MAX_REQUEST_BODY_BYTES`, `server.ts`), because TanStack Start reads a server function's body before any middleware checks the session, and Bun's own default is 128MB. The largest legitimate body is a Harvest import step, a few MB; the constant's comment has the measurement. `vite dev` has no such cap.

**The client address is read from one header, `TRUSTED_IP_HEADER`** (default `none`: the socket address, because a caller can send any header and no header is safe until the operator names one). Production sits behind the Coolify proxy and sets `TRUSTED_IP_HEADER=x-forwarded-for`. Only the per-address rate limits of the MCP server and the CLI's API read it (`lib/client-address.ts`). No other header is consulted: a caller can send `x-real-ip` or `x-forwarded-for` too, and the old first-one-wins order let it pick its own bucket. When the header is missing, the socket address that `server.ts` records is used, and under `vite dev`, which has none, one shared bucket. Set it to `x-forwarded-for` to read the LAST entry (the one the nearest proxy appended), to `x-real-ip` or `cf-connecting-ip` for a proxy that overwrites that one, or leave it as `none` to use the socket address only. `server.ts` deletes a caller's copy of its internal socket-address header before it writes the real one, so a caller cannot forge that path. With the default behind a proxy, every caller shares the proxy's address, and the server logs one warning when it sees a forwarding header. A trusted header is only as good as the one way in: an origin that also answers on its public address lets a caller set the header itself, so keep the origin reachable only through the proxy.

**The instance's configuration is a set of instance settings, not only environment variables** (issue #75, `docs/adr/0004-environment-overrides-the-database.md`). Email, the S3 store, the GitHub, Slack and Google credentials, web push, the push relay, PostHog, `HOMEPAGE_ENABLED`, `ASSISTANT_ENABLED`, `MCP_ENABLED`, `CLI_ENABLED`, `SINGLE_ORG_SLUG` and `CLI_RELEASES_REPO` are listed in `INSTANCE_SETTINGS` (`packages/core/src/lib/instance-settings.ts`), and every reader goes through `setting(name)` or `settingEnabled(name)`. A non-empty environment variable of the same name wins and locks the field on the Infrastructure page; else the `instance_setting` row answers; else the default. An empty variable counts as unset, so `CLI_ENABLED=` now leaves the CLI on. The reads are synchronous from a snapshot that `refreshInstanceSettings()` fills, at most every five seconds, from the global request middleware (`apps/web/src/start.ts`) and each scheduler tick. **A script or a one-off job that is neither must await `refreshInstanceSettings()` before it reads a setting**, or it sees the environment and the defaults only. A change on the page reaches another process (the worker, a second web host) within those five seconds. The operational values (the job switches and intervals, timeouts, `PORT`, `TRUSTED_IP_HEADER`) and `DATABASE_URL`, `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` stay environment-only. None of the settings is a `VITE_` variable, because `VITE_` values bake at build time and the Dockerfile builds one image for several environments.

**Native push to the mobile app is off until an operator turns it on.** `PUSH_RELAY_ENABLED` (default `false`) and `PUSH_RELAY_URL` (default `https://push.farmer.profi.co`) are instance settings in the Features section. With push on, the server seals each push for the phone and sends it through Profico's relay (ADR 0006), which forwards it to APNs or FCM and cannot read it. An operator who does not want a third party in the path leaves it off. The mobile app then works, but gets no native push: no log reminder and no "timer dropped" on the phone, no Live Activity updates from the browser or the CLI, and the Slack kinds stay on Slack. `GET /api/v1/meta` tells the app which case applies. See `docs/domains/mobile.md`.

**Impersonation is not configured here.** The platform admin role — who may become any user in any workspace — is a database value, granted to the instance's first account and passed on from inside the product. There is no environment variable for it, deliberately; see `docs/domains/authentication.md`.

**PostHog's BROWSER half is the part that catches people out.** `POSTHOG_PROJECT_TOKEN` and `POSTHOG_HOST` are instance settings, not `VITE_` variables: `vite build` runs inside the Docker image, so a `VITE_` value could only ever be what CI was given. The server reads them per request (`lib/posthog-server.ts`, one client kept per token and host and rebuilt when either changes, null when either is missing) and `routes/__root.tsx` writes the pair into the inline `<head>` script beside the theme, for the browser to read back off `window`. Not through `getPublicAppConfig`, which is a server FUNCTION: the root route has no loader to call one from, and `RootDocument` is the `shellComponent`, which renders on the error and not-found paths where no loader has run. `POSTHOG_AI_CAPTURE_CONTENT` (default `false`) is the one switch for whether an agent's content — the assistant's prompts and answers, and the MCP server's tool arguments and results — leaves the process at all. The metadata goes either way and is what the dashboards are built on; the content is a customer's timesheet, so on a multi-tenant deployment sending it is a decision an operator makes rather than inherits. Six adapters read that one client and nothing else does: `lib/posthog-ai.ts` (the assistant's turns), `lib/posthog-mcp.ts` (the MCP server's requests), `lib/posthog-api.ts` (the REST API's requests and failures, and the faults of server functions), `lib/posthog-jobs.ts` (a failure a background job caught and went on from, through `jobs/job-failures.ts`; the standalone worker installs no sink), `lib/posthog-impersonation.ts` (the impersonation ledger, see `docs/domains/authentication.md`) and the `capture` calls in `server/*.ts` (what a person did in the browser).

**The browser does not talk to PostHog directly.** It sends its events to `/api/k7v2q9` on the app's own origin. The server route `routes/api/k7v2q9/$.ts` forwards them to `POSTHOG_HOST`, and forwards `/static/` and `/array/` paths to the PostHog assets host. An ad blocker that blocks the PostHog domains then does not drop the events. The prefix is a fixed random word on purpose: block lists match words such as "ingest". The proxy is a route, not code in `server.ts`, so it reads fresh instance settings. It forwards only the paths that posthog-js requests, with a 10 second timeout and a 5 MB body limit, because a self-hosted `POSTHOG_HOST` can be on a private network. PostHog takes the GeoIP address from the request, so the route sends the client address as `X-Forwarded-For`. Set `TRUSTED_IP_HEADER`, or every event has the address of the proxy in front of the app.

**Development sends nothing, in either half.** Both `lib/posthog-server.ts` and the browser's config in `routes/__root.tsx` answer null unless `NODE_ENV=production`, so a developer's `.env` — a copy of a real deployment's, token included — cannot put reloads, test clicks and seeded rows into the project the dashboards are built on. It is deliberately not an opt-in variable, which can be copied onto a server. `lib/dev-auth.ts` reads the same variable from the other side (password sign-in only under `development` or `test`), so both fail safe when it is unset. `vite dev` sets `development`, never `production`; the Dockerfile and `apps/web`'s `start` script both pin it. One consequence to know before debugging: a local run cannot exercise the analytics path at all, however the variables are set.

**Rotate the secret with `BETTER_AUTH_SECRETS`, never by changing `BETTER_AUTH_SECRET`.** Every stored credential is encrypted with a key from it (better-auth's OAuth tokens, and `lib/secret-box.ts` for the Slack bot token, the OpenRouter key and the instance's secret settings), so a changed value makes all of them unreadable. `BETTER_AUTH_SECRETS` is better-auth's own rotation set, and `secret-box.ts` reads it the same way, so there is one thing to configure:

1. Set `BETTER_AUTH_SECRETS=2:<new secret>,1:<old secret>` — the new version FIRST, because the first entry is the one that encrypts; the rest only decrypt. Versions are non-negative integers and must be unique. Leave `BETTER_AUTH_SECRET` set to what it was: it still opens every value written before the rotation set existed (`enc:v1:…` here, bare hex in better-auth).
2. Restart. New writes use version 2. The GitHub and Slack install `state` (`lib/oauth-state.ts`) is signed and checked with version 2 only, so a leaked old secret cannot forge one; an install begun in the 15 minutes before the restart fails and is started again. Nothing needs a migration: a value under an older key heals on its next read — the Slack token on the next reminder tick, the OpenRouter key when the assistant next loads it, the instance settings on the next refresh (enabled OAuth sources only) — and on its next write. better-auth's OAuth tokens only move when the provider issues a new token, which for a GitHub OAuth token or a Google refresh token may be never.
3. Drop version 1 only when nothing still carries it: no `enc:v2:1:…` in `slack_installation.bot_token`, `assistant_settings.api_key`, `instance_setting.value` or `instance_oauth_provider.client_secret`, and no `$ba$1$…` in `account.access_token` / `account.refresh_token`. A value under a dropped version is refused like one under a wrong secret. Do not remove `BETTER_AUTH_SECRET` while any `enc:v1:…` or bare-hex value remains.

Without `BETTER_AUTH_SECRETS`, nothing changes: `secret-box.ts` seals `enc:v1:…` from `BETTER_AUTH_SECRET` and `oauth-state.ts` signs with it, as they always did.
