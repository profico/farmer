# The assistant

An OpenRouter-backed chat page (`$orgSlug/assistant`) that answers questions about tracked time and can log more of it. `services/assistant.service.ts` is the agent loop — up to `MAX_STEPS` billed model calls per turn, plus one to title a new thread; `services/assistant-tools.ts` is what it may do.

- **The step ceiling ends in an ANSWER, not an error.** `MAX_STEPS` (8) is a ceiling on model round-trips, and the number is in the system prompt so most turns never reach it. A turn that does gets one more call with the tools taken away (`OUT_OF_STEPS`) — the model cannot ask for a ninth step, so it terminates, and the person gets what the eight steps found plus what is missing from it. The nudge is not stored: it is the loop talking to the model about its own ceiling, not something anyone said. Only a closing answer that is empty falls back to an error (`NO_ANSWER`).
- **A step's independent reads run together.** `runClaimedBatch` claims the leading run of `read` tools in ONE transaction and awaits them with `Promise.all`, so four lists cost one round trip and not four. Writes stay strictly in order. `AssistantTool.serial` opts a read out — `list_time_entries` sets it, because `listRange` writes on read (see the `listRange` gotcha in the root `CLAUDE.md`) and two overlapping ranges would recompute a day's fill block at once. **A new read that reaches a service which writes must set `serial`**; nothing detects it, and the failure is a race.
- **A capped tool result is cut by ROW where the value is a list** (`MAX_TOOL_RESULT_CHARS`), never mid-object, and the note says how many rows were dropped and tells the model to narrow the call ITSELF rather than send the person back to re-ask.
- **A tool that throws tells the model only what a person may read.** The tool result goes to the model provider, so `executeTool` passes a failure's message only when `classifyServiceError` (`services/error-message.ts`) says so — a validation failure, or a class that extends `UserFacingError` (`lib/user-facing-error.ts`: an `AccessError`, a full day, a GitHub rate limit or dead installation, a refused upload, the assistant's own errors), or a bare `Error` sentence a service threw on purpose. Exposure is a property of the class, so a new error a person should read extends the base; one that can carry an address, a URL or a provider's body (`WebhookUrlRefusedError`, `OpenRouterError`, `ObjectStoreError`) does not. A database error, which carries its SQL and parameters, is logged and becomes a generic line. `executeTool` calls `agentErrorMessage`, which adds a recovery hint (`list_tasks`, `list_projects`) to a refused task or project id, as the MCP server does.

- **Every tool is an adapter onto an existing service, called with the CALLER'S own `Ctx`.** That is the whole authorization story and it is deliberately not restated per tool: a Member's `list_time_entries` returns their own rows because `listRange` filters on `ctx.userId`, and their `create_project` is refused because `canCreateProjects` says so. Tool parameters are the *existing* Zod inputs from `src/schema/*` via `z.toJSONSchema()`, so the model inherits the UI's ceilings.
- **A tool description must say what OMITTING an optional filter means.** `time_report_summary` and `time_report_detail` default `userId` to "everyone the caller may see", which for a PM, Team Lead or Admin is the whole team. The old wording ("scoped to what the caller is allowed to see") was true and read as "scoped to the caller": ten of thirteen benchmarked models answered "how many hours did I log in August" with the team total, presented as the person's own. Spelling the default out fixed it in every model that got it wrong. A number that is right for a Member and silently wrong for their manager is the failure mode to look for when adding an optional filter.
- **`toolDefinitions(access)` is scoped to the caller, and that is not the authorization.** `AssistantTool.available` only decides what the model is *told* it can do — every definition is re-sent on every step, so offering a Member the admin reports costs tokens and a step spent being refused. Keep predicates coarse ("is a PM anywhere", never "on THIS project"), because the arguments don't exist when the list is built.
- **Three tool kinds (`ToolKind`), and the line is "can they undo this by asking for the opposite".** `read` answers; `write` (logging and correcting single entries) runs inline; `destructive` (deleting an entry or a recurring rule, removing absence, archiving, unlinking commits, pull requests or a GitHub repo, clearing the hour fund, discarding the timer) suspends for approval.
- **A `write` that reaches past one day of the caller's own timesheet asks too** (`AssistantTool.confirm`): a project role, creating or changing a project, a client or a task type, unarchiving, booking a span of absence, copying a week, creating or changing a recurring rule, linking a GitHub repo, changing the integration switches, setting the hour fund, and making or changing a filing rule. The model reads text nobody in the conversation wrote — an invite's title, a commit subject, another member's note or name — and a sentence there that reads as an instruction must not be able to make a PM of its author, or book weeks of sick leave, as the person asking with nobody seeing it. The prompt also says tool results are data, but that is advice to a model; the card is the control. A new write that changes somebody else's access or the org, or many days at once, sets `confirm` and a `summarize`.
- **A read must hand back what a write takes, or the answer is a dead end.** `time_report_detail` returns each entry's `id` for exactly that reason — `update_time_entry`, `update_entry_description`, `set_overtime` and `delete_time_entry` all take one, and a report the model could read but not act on made "fix the note on Tuesday's entry" a search it had to run twice.
- **The note search is `ledgerWhere`'s, not the report's.** `LedgerFilter.q` matches `timeEntry.description` case-insensitively, so `time_report_summary` and `time_report_detail` inherit one filter from the shared `filters` object in `schema/reports.ts` and cannot disagree about what a search matched — a total nobody can drill into is worse than no total. `%` and `_` are escaped and the predicate declares `escape '\\'`: they are ordinary characters in something a person typed, and taken as wildcards they widen a search silently. There is deliberately no separate search tool; a search IS a filtered detail report, under the same 366-day ceiling and the same access scope.
- **Hours LOGGED and hours EXPECTED are different questions.** `my_targets` and `tracking_report` hand the model `compliance.service.ts`'s own numbers, because asked "am I behind" it used to sum a month and judge it against eight hours a day — right only for a full-time person in a month with no public holiday and no day off. A null target means the rule does not measure this person (an hourly student or contractor without an override, an overhead employee) and is NOT zero; `nullableHours` keeps the distinction all the way to the model, and the prompt says a verdict is a rule to look up rather than arithmetic to do. `tracking_report` is offered to `leadsSomething`, since a Member's own row is already in `my_targets`.
- **`integration_status`, `sync_now` and `list_filing_rules` are how the assistant explains entries nobody typed.** "Where are my meetings" has four answers — the switch is off, the token was refused, the engine has not reached that day, the month is locked to automations — and every one of them is a setting rather than a mistake. `sync_now` goes through `runAutomationSyncForCtx` (`jobs/automation-sync.ts`) and not straight at the service, so it shares the sweep's per-person guard: an agent loop presses that button far harder than a person does. It reports `off` separately from `ran`, because an engine nobody switched on is not a sync that worked. A filing rule is derived from what was filed, never typed from nothing. `file_time_entries` with `remember` makes one as it files. `remember_filing_rule` makes rules from entries that are already filed: it takes entry ids only, and the project, task and title come from each entry (`filingRulesService.rememberFromEntries`, which checks that the project is live and that the caller may work on it, because `rememberFrom` trusts its target). `update_filing_rule` changes the project or task of a rule, and both of them `confirm`, because the sync files future meetings by itself. `list_filing_rules` and `delete_filing_rule` read and remove.
- **The GitHub, timer, calendar, hour fund, filing rule and project tools** are adapters over the existing services, called as the caller, and each description says whose data it returns. The list:
  - **GitHub.** `list_linked_github_repos` (read, one project) and `list_available_github_repos` (read, Admin) take `githubService.listLinkedRepos` and `listAvailableRepos`; the second is cut at 100 rows with `truncated` and takes `query` and `onlyUnlinked`. `link_github_repo` (write, `confirm`, Admin) and `unlink_github_repo` (destructive, Admin) take `linkRepo` and `unlinkRepo`. The unlink names the project as well as the repo row and refuses a row that is not on that project, because `unlinkRepo` deletes by id and an id that matches nothing is no error; it now returns the rows it removed. `update_integration_settings` (write, `confirm`) changes the caller's own switches through `integrationSettingsService.update`. A switch that goes on starts from today and never backfills, and the description says so. `suggest_commits` and `suggest_pull_requests` (read, `serial`, because the account token refresh writes) read one project on one day, capped at 50 rows. `list_attached_commits` and `list_attached_pull_requests` take an optional `timeEntryId` for the evidence of one entry.
  - **Timer.** `get_timer` (read), `start_timer`, `pause_timer`, `resume_timer` and `stop_timer` (write, no `confirm`, as `create_time_entry`) and `discard_timer` (destructive). The timer is one per person across workspaces, and the results say `thisOrganization`. When the timer runs in another workspace, the result keeps the `timerId`, the state, the workspace name, `startedAt` and the hours (`elapsedHours` and `willLogHours`). Its task and project (the names and the ids), its note, `needsNote` and `continuesEntryId` are null, because they belong to that workspace and this workspace's model provider must not read them. `discard_timer` takes the `timerId` that `get_timer` shows, and refuses a call when the timer now is not that one, because an approval can come after the person stopped that timer and started another. It also refuses a timer that runs in another workspace, because `timersService.discard` deletes by person. `stop_timer` leaves `durationSeconds` out unless the person gave a figure, so the server snaps the measured time.
  - **Calendar.** `list_calendar_events` (read, `serial`) reads `listEventsForRange` through the calendar port, at most 31 days, capped at 100 events. A calendar that is not connected is `connected: false` with no events, not an error. `listEventsForDay` is not used: it throws.
  - **Hour fund.** `get_hour_fund` (read), `set_hour_fund` (write, `confirm`) and `clear_hour_fund` (destructive), all Admin. The service reads have no role check and the Settings page is for Admins, so the read tool calls `requireAdmin` itself. A month with no fund is null, not zero. `getMany` is not used: `listForYear` covers a year.
  - **Filing rules.** `update_filing_rule` and `remember_filing_rule`, see above.
  - **Projects.** `project_overview` (read, `leadsSomething`) is the all-time figures for everyone on the project. `list_assignable_people` (read, `leadsSomething`) keeps an email only where two people share a name. `listTasks` is not a tool: every project offers every live task, so `list_tasks` answers it.
- **A tool's arguments must be producible by some read, or it is uncallable** — hence `list_unfiled_entries` for `file_time_entries`, `list_commits` returning `projectGithubRepoId` + `sha` for `attach_commits`, and `list_tasks` including the absence tasks that `log_absence` needs.
- **Unlinking evidence is a pair of reads and a pair of destructive writes.** `list_commits` and `list_pull_requests` read GitHub and have no attachment id, so they cannot feed an unlink. `list_attached_commits` and `list_attached_pull_requests` read the database only. They take entry dates (max 31 days) and an optional `owner/name` repository, and they return `attachmentId` / `activityId`. `unlink_commits` and `unlink_pull_requests` take up to 25 of those ids (`MAX_UNLINK_PER_CALL`). That is the number of rows the approval card shows (`MAX_PREVIEW_ROWS`): a row past the card is never shown, so the person cannot untick it. A longer session takes a second call. Each is `destructive`, with a checklist `preview` and `withSelection`, so the person may untick rows. Each id goes through `detachCommit` / `detachPullRequestActivity`, which scope by organization and owner. A missing id, a malformed id, a colleague's id and another organization's id give the same "not found" line in `results`, and the other ids still run. The schema takes any string for that reason, and `listAttached*ByIds` drops a string that is not a uuid before the query, so the approval card still shows the good rows. The entry stays. `detachCommit` and `detachPullRequestActivity` are exempt from the audit log (`audit-coverage.test.ts`), because they change a person's own entry. Both detach functions also write a detach tombstone (see `docs/domains/automation.md`), so an unlink is permanent for the sync. Attaching the commit or pull request again by hand (`attach_commits`, `attach_pull_requests`) puts it on the entry that the person names, and only there: the tombstone stays, so the sync keeps it off every other entry. The tool descriptions and the result `note` say so.
- **`list_members` carries no email, except where two names collide.** Every tool result goes to the org's model provider, and the whole roster's addresses on every "who is on my team" is a mailing list handed to a third party. A name two members share (compared case-, accent- and space-insensitively, through `foldForSearch`) keeps the email on both rows (everyone else gets `null`), because that is what lets the person asking say which one they meant. The MCP server serves the same tool, so it gets the same rows. The caller's own email still rides in `callerCard`.
- **`assistantSettings.systemPrompt` is house rules an admin appends**, fenced in `<house-rules>` and ranked below the built-in prompt, which encodes domain facts (quarter-hour granularity, ids are looked up not invented) that stay true whatever an org layers on.
- **Approval state lives on the message row** (`pendingApproval`, `approvalSummary`, `approvalPreview`), not on the SSE connection. Approving is a *second* `run` call, so a tab closed mid-approval leaves a card that still works on reload. The summary and preview are stored because they are what the person consented to, and because `assistant-tools.ts` imports the services barrel and can never reach the browser to rebuild them. `summarize` may look its argument up and must fall back rather than throw — a card that fails to render leaves a pending write nobody can answer.
- **A batch write suspends once and is approved row by row.** A tool with `preview` (`apply_day_assembly`, `file_time_entries`) stops the turn and shows a table; `withSelection` rebuilds the arguments from every row EXCEPT the unticked ones. Exclusion, because the card shows at most 25 rows — phrased as inclusion, approving a 40-row batch would write 25. An empty selection is a refusal, not a write of nothing.
- **Every `tool_calls` turn needs one `tool` result per call id, or the next request 400s.** So a rejection still writes a `tool` message, and a message typed past a pending card declines every unanswered call and clears `pendingApproval` BEFORE the user message is stored. `toWireMessages` repairs threads already stored in the wrong order. `claimCall` (a row lock plus a re-read) makes approval atomic, so two tabs approving one card run the tool once.
- **The cadence an answer is READ at is this app's, not the provider's** (`components/assistant/typeset.ts`, `StreamingAnswer` and `.answer-word` in `styles.css`). A `delta` is whatever the model's provider decided to flush, so the same question answered twice arrived once as a typewriter and once as a paragraph landing whole — the difference was on screen. `useTypeset` makes the arrived text the TARGET and chases it: the speed is proportional to the backlog, which is a first-order settle and the text form of the spring in `lib/motion.ts`, so a burst drains fast and eases out while a trickle is never held back. `MAX_LAG` caps how far behind it may fall, because a provider that hands over half an answer at once would otherwise still be reading it out after the turn ended. The word still arriving is held back, and the reason is the other half of the effect: each word blurs in as it MOUNTS, and a word that grows a character at a time inside that span reads as a glitch. **That reveal is why the inline keys are positional.** The key in `renderInline` carries the part's own text, so a growing part changes its own key for its first eight characters and React remounts it — which restarts a CSS animation every character. Under `reveal` the key is a cumulative WORD count instead, stable because a closing `**` re-splits a line without changing how many words are on it. Both halves stop under `prefers-reduced-motion` AND under Preferences → Display → "Less movement"; the hook reads both, because the CSS rule behind the second one cannot reach a loop that runs in JS.
- **A directive fence that is still open is a sized box, not its own syntax.** A chart cannot be drawn from half a JSON object, so what the reader got until the closing fence landed was the raw object in a code block, replaced by the chart on the last token; the chips grew one character at a time beside it. Both now render through `FadeSwap` — the placeholder out, the real block in, the same crossfade every panel change in the app uses — and `outlineChart` reads the row count, the orientation and whether there is a title off the JSON that has arrived, so the box lands at the chart's own height and the text under it does not step down at the swap. **It is `streaming` and not `closed` that chooses**, which is what keeps the two fallbacks for a turn that stopped a token early: a stored answer holding an unclosed fence still renders its chips, and still shows a half-written chart's numbers as code. The untagged-fence chart recovery gets no placeholder and cannot — what identifies a chart there is that the body parses as one, which half an object never does.
- **`components/assistant/answer.tsx` and the prompt's formatting rules change together.** The reader is hand-rolled markdown plus three directives the prompt describes verbatim: `[[YYYY-MM-DD]]` (a link to that day's timesheet), `farmer-chart` fences and `farmer-next` chips. A construct promised in the prompt and missing in the reader renders as its own syntax. It re-parses on every streamed delta, so half-arrived input must degrade, never throw. It also recovers from wrappers a small model adds — a fence whose body is only a pipe table is a table, a `json` or untagged fence that parses as a chart spec is a chart, `farmer-next` is read without its closing fence — but it never invents a directive the model did not write.
- **The composer clears on send and takes the draft back when the send never landed.** `useAssistantActions().send` resolves false when no `message` event arrived — the server's receipt, written before the model is called — and `PromptBar` restores the text and focuses it. A rate limit or a dead session used to cost the person everything they had typed, next to an error line telling them to try again. A turn that started and then failed keeps the message, because by then it is in the thread.
- **The tool trace names its subject** (`ToolTraceList`, `toolDetail` in `components/assistant/primitives.tsx`): `tool_start` carries the call's raw arguments and the CLIENT decides the wording, beside `toolLabel`. A column of four identical "Read time entries" says nothing about what was read. **The ids in those arguments are resolved to names client-side** — `userId` to a face and a name from `directoryQuery`, and `projectId`/`clientId`/`taskId` from their own lists — because a report filtered per person is otherwise six rows reading the same date range. Each list is fetched only once a trace row actually carries that kind of id, so an ordinary turn costs no extra request; an id whose name has not arrived is left out rather than printed raw.
- **A turn the person stops keeps what it already wrote.** The read loop in `lib/openrouter-client.ts` had a `finally` and no `catch`, so the rejection `read()` raises when the signal fires carried every token of a half-written answer out with it — Stop, or navigating away, threw away work the org had paid for and left the thread looking as though nothing had been asked. It now returns the partial turn under `finishReason: ABORTED`, and `assistant.service.ts` stores the text **with `toolCalls` set to null**: a stored `tool_calls` row with no `tool` result under it 400s every later request in that thread, and the calls were never run. An empty partial stores nothing and reports nothing — a cancelled turn is not a failure to explain. The client settles the same way it settles a finished turn (`settle` in `assistant-runs.tsx`), or the live half-answer would sit beside the stored one.
- **A turn belongs to a THREAD, and the run store is keyed on the conversation** (`components/assistant/assistant-runs.tsx`, mounted by the `/$orgSlug` layout). The streamed text, the tool traces, the pending card and the error all live per conversation id, so opening a second thread does not show it the first one's answer, and two threads run side by side — one turn at a time PER CONVERSATION, not per person. It is above the route rather than on the page for two reasons that are one: the thread list is in the SIDEBAR, which the page does not contain, so nothing on the page could tell it a thread is working; and a turn then survives navigation, so asking a long question and going to look at your timesheet finds the answer waiting. Three contexts, not one — the rail reads `useAssistantRunning()` (the ids, which change twice a turn) rather than the run map (which changes per token).
- **A stream that ends with no finish reason, or with an error frame, is a failed call, not an answer.** After the 200 is committed, OpenRouter reports an upstream failure as an SSE frame with a top-level `error: { code, message }` and `finish_reason: "error"`, then ends the stream. The parser reads that object and carries it on `OpenRouterStreamCutError.upstream`, and the error message holds the code and the text, for the log and PostHog only. The finish reason `"error"` with no object fails the same way. An upstream can also close a slow call with no frame and no `finish_reason`. In production two calls ran for 120 s, carried no tokens and were reported as a success. `streamChatCompletion` now throws `OpenRouterStreamCutError` when the stream ends, the signal has not fired and no finish reason came. The error carries `partial`, the `ChatTurn` that arrived. A close with the signal already fired is still `ABORTED`. `generate` reports the call with the error message (for example `"stream ended without a finish reason"`) plus the tokens, cost and text that arrived, so PostHog shows `$ai_is_error`. The loop keeps the partial TEXT under the rule for a stop (`keepPartial`) and drops the partial tool calls, which never ran and would leave a `tool_calls` row with no result. The person gets `STREAM_CUT`, not `done` and not `NO_ANSWER`, and never the provider's text. The loop does not retry the call: a retry bills the same prompt again. Tool calls that look whole are not trusted, because the close can come before the last argument fragment. The 180 s timeout is unchanged, and it is a cut too: when it fires mid-body, the body read rejects with a `TimeoutError`, not an `AbortError`. If the caller's signal has not fired, that throws `OpenRouterStreamCutError` with the partial turn and the message `stream timed out before a finish reason`. A deadline that fires before the headers throws the same error with an empty partial turn and the message `request timed out before the response headers`. The person gets `TIMED_OUT` ("took too long ... try a narrower question") in place of `STREAM_CUT`, because a retry of the same prompt likely times out again. `generate` writes every cut to the server log as `[assistant] stream cut`, with the trace id, conversation id, model and step. Before this change an empty cut ended in `NO_ANSWER`, and a cut with text or tool calls was stored and run as a normal turn.
- **An assistant turn with neither text nor a tool call is an error, not a `done`.** The blank row it used to store is one the transcript skips — an assistant row with no text is a pure tool turn, rendered as its trace — so the person was left looking at their own question with nothing under it and no explanation, which is how a short follow-up ("let me see it") read when a model returned an empty completion. It is answered with `NO_ANSWER`, the same words the out-of-steps path uses.
- **The prompt carries a GLOSSARY, because the reader's words and the schema's words differ where it matters.** A "note" is an entry's `description` — the field the UI labels Note and every entry read returns. Asked whose notes were most interesting, the model answered that it had no access to a notes system: a missing synonym does not read as a missing synonym, it reads as a missing feature. Same for "block" (a time entry) and "time off" (absence). A new word on a screen that has no counterpart in a tool name belongs here.
- **Three facts go in the prompt because no tool's arguments show them**: the org's week start (the model resolves "last week" itself, and `copy_week` takes the START of a week — a Sunday-start org that was never told has every weekly figure a day out, silently), `MAX_DAY_SECONDS`, and that the sync engines write rows nobody typed, so a description may be a commit subject rather than something the person wrote.
- **The model is told who it is talking to, before it reads anything** (`callerCard` in `assistant-tools.ts`: name, email, user id, organization and the caller's tier, in the system prompt). Told only the date and that `whoami` exists, asked for "Omar's notes" it read the member list, failed to find Omar in the first page of a 200-person roster, and reported that no such person works here — to Omar. Identity is needed to understand the QUESTION, so it cannot sit behind a tool call; `whoami` keeps the rest (working hours, member type, the project list), which is a real read and belongs behind one.
- **One model call is retried once, when it made no output.** A call can stall: the connection stays open and no token arrives. In production, `~deepseek/deepseek-flash-latest` stalled twice for 180 s, and each turn died. A retry by the person a few minutes later worked. The loop now guards against this in two parts.
  - **The watchdog is in `streamChatCompletion`.** It aborts the call when no progress arrives for `OPENROUTER_STALL_TIMEOUT_MS` (default 60 s). Progress is a content delta, a reasoning delta, a tool-call delta, a finish reason or a usage row. An SSE comment line (`: OPENROUTER PROCESSING`) is not progress, and neither is an empty delta. OpenRouter sends the comment while an upstream is stuck, so counting it would hide the stall. The 180 s limit stays as the outer bound. A stall throws `OpenRouterStreamCutError` with `stalled` set and `timedOut` not set. The message is `stream stalled: no progress before the stall limit`, so a log line shows the difference.
  - **The retry is in `generate`.** It runs one time, in the same step, on the model that the next item names. `retryableBeforeOutput` (`lib/openrouter-client.ts`) decides. A retry happens only when no content, reasoning or tool-call delta arrived (`outputStarted` is false) and the failure is one of these: a stall, a network or TLS fault before the response headers or in the body before any output (`OpenRouterNetworkError`), an HTTP 408 or 5xx, an error frame (not a 4xx other than 408 and 429), or a stream that closed empty. An HTTP 429 is not retried: it can come from the limits of OpenRouter or from the provider, and the fallback routing of OpenRouter already tried the other providers of the same model, so a retry at once by the app adds load and rarely helps. A 429 in an error frame is retried, because the provider refused after the stream started and the retry can go to another provider. The 180 s total timeout is not retried, because it already cost three minutes. A Stop is never retried. After partial output the turn fails as before, with `STREAM_CUT`. This includes a body-read fault (a reset or a closed socket) after output: it is a cut with the fault in `cause`, never a raw error. A body fault after a finish reason does not fail the call, because the answer is whole. An error that `onDelta` throws is not a network fault and travels unchanged. An empty `OPENROUTER_STALL_TIMEOUT_MS` gives the default, and only an explicit `0` turns the watchdog off. The retry repeats only the model call. The tools of earlier steps do not run again.
  - **The retry model** is the model of the conversation, unless `ASSISTANT_FALLBACK_MODEL` names another. An admin chose the conversation's model, and the privacy text (`apps/web/src/components/site/legal.tsx`, "The assistant") tells people that their data goes to the company that makes the chosen model. So the retry must not send the conversation to a model that nobody in the organization chose. OpenRouter can route the same model to another provider, so a retry on the same model still has a chance. An empty value counts as unset. The variable is an environment flag and not an organization setting, and it applies to every organization on the instance. **An operator who sets it must also change the privacy text in `legal.tsx`**, because the conversations of every organization can then go to a model that their admin did not choose. Use a pinned id: a `~...-latest` id moves to a new version without notice. The request does not send OpenRouter's `models: [...]` list. That list falls back only on an error before the stream starts, and never on a silent stall, so the loop must retry on its own in any case.
  - **Telemetry.** Each attempt is its own `AiGeneration` (and its own `$ai_generation`), because each is billed. `$ai_model` stays the requested id, which is the fallback on a retry. The new properties are `ai_served_model` and `ai_provider_served` (from the response chunks), `ai_first_progress_ms`, `ai_attempt` (1 or 2) and `ai_retry_reason` (`stall`, `network`, `http_<status>`, `upstream_error` or `empty_stream`). The `[assistant] stream cut` log line carries the same values. A failure that is not a cut is logged as `[assistant] model call failed`. The title call is never retried. **The cost of a stalled attempt is not known.** OpenRouter sends the usage row last, and a stalled call never gets to it, so that attempt's `AiGeneration` has `costUsd` null (and no token counts). The provider can still bill it, so the PostHog cost of a turn with a retry can be lower than the real cost.
  - **Known limit.** A model that thinks for more than 60 s and sends no reasoning delta looks like a stall. Raise `OPENROUTER_STALL_TIMEOUT_MS` for such a model.
- **The turn streams over a server ROUTE** (`routes/api/assistant/stream.ts`), because a `createServerFn` resolves to one value. It is rate-limited per user (`server/assistant-rate-limit.ts`), since each turn spends the org's key; it stops the model loop when the client disconnects, sets `X-Accel-Buffering: no`, and passes only the app's own error classes to the browser. While a turn runs, it sends an SSE comment line (`: heartbeat`, `lib/sse-heartbeat.ts`) every 20 s, because a turn can be silent for longer than the host's `idleTimeout` (255 s, `server.ts`) when a model thinks, a call stalls and is retried, and a tool is slow. The client reads only `data:` lines, so the comment is not an event. The `finally` of the stream stops the timer on every exit path, and a client abort stops it too. `lib/openrouter-client.ts` passes its own long timeout, because `externalFetch`'s 15s deadline covers the whole request and would cut a streamed answer mid-sentence.
- **Three switches, all different.** `ASSISTANT_ENABLED=false` (env, default on) takes the feature off the deployment: no nav row, no route, a 404 from the stream endpoint, and every service path refused — except `settings.disconnect`, so a key stays removable. `assistantSettings.enabled` is an admin pausing it for one org. A missing `assistantSettings` row is "never connected". `$orgSlug/route.tsx` resolves `assistantAvailable` from all three for both navs, so a paused org has no Chat tab leading to an explanation; the route still explains itself to someone who typed the URL.
- **Model choice is admin-only.** A conversation pins `assistantSettings.defaultModel` when it starts (`createConversationInput` carries no `model`), so changing the default never re-answers an old thread.
- The OpenRouter key is per-org, set by an admin under Settings → Workspace → Integrations, and follows the Slack bot token's rule — sealed at rest (`lib/secret-box.ts`), opened only in `loadSettings`, never returned. A key that does not decrypt (a changed `BETTER_AUTH_SECRET`) is its own state, not "never connected": `settings.get` answers `configured: false` with `keyUnreadable: true`, so the nav drops the Chat tab, the assistant page says the key must be pasted again rather than offering a composer whose every message throws, and Settings → Workspace → Integrations badges the row "Connect again" and says why. Saving a key again is the fix. `settings.get` answers with a leading-characters hint, since the tail is the unguessable part.
- **What a turn cost is reported through a seam, not to a vendor** — `services/ai-telemetry.ts`, beside `ports.ts` and `notify.ts` and for the same reason: `packages/core` must stay runnable from a process with no analytics in it, so the default sink drops every event and the worker, the CLI's API and the test suite run the identical loop. `apps/web/src/lib/posthog-ai.ts` is the only adapter, installed once by the stream route, and it renames a generation to `$ai_generation` and a tool run to `$ai_span`. **Nothing in there may throw or wait**: an answer somebody is waiting for does not get slower because a metric is in flight. Core hands the content over whole and the ADAPTER decides what leaves the process, because that is a deployment's decision and belongs next to the credentials it is made with.
- **A generation's `tool_calls` are what PostHog counts as tool usage, not the `$ai_span` events beside it.** PostHog extracts the tool names from the RESPONSE at ingestion time and writes `$ai_tools_called` and `$ai_tool_call_count` on the generation; `$ai_tools` is only what the model was OFFERED. So `AiGeneration` carries the whole `toolCalls` array rather than a list of names, and `posthog-ai.ts` puts it on `$ai_output_choices` in the OpenAI shape. Without it the Tools tab reads empty on an app that calls tools constantly — the spans are there, and nothing aggregates them. The tool NAME rides either way, as this app's own vocabulary; `arguments` goes behind `POSTHOG_AI_CAPTURE_CONTENT` with the rest of the content.
- The transcript's swap, scroll pinning and wide-table bleed (`FadeSwap`, `PinToEnd`, `.answer-wide`) are explained at their call sites in `assistant.tsx` and `styles.css`.
