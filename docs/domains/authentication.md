# Authentication

**Google is the only identity in production, and there is no login page there.** `emailAndPassword` is off, so there is no form to render and nothing to choose — "log in" is a redirect.

- **`routes/api/login.ts` is the sign-in surface.** A server route: it asks better-auth for the Google authorize URL and re-shapes that 200-plus-`Location` response into a real 302, copying the OAuth state/PKCE cookie across, so an unauthenticated document request reaches Google without the app hydrating.
- **`routes/login.tsx` stays a *page* route on purpose**, even though it renders almost never. Every `redirect({ to: "/login" })` and sign-out points at it, and a page route's `beforeLoad` runs both server-side and in the browser; `redirect({ href, reloadDocument: true })` turns either into the full-page hop `/api/login` needs.
- **Two cases render instead of redirecting.** `?error=…` — better-auth's `errorCallbackURL`, most usefully the single-org invite-only gate; that branch must not redirect, or an uninvited visitor bounces between `/login` and Google forever. And development, below.
- **`lib/dev-auth.ts` turns email + password back on off-production.** The gate is `NODE_ENV !== "production"` and deliberately **not** an opt-in env var, which could be copied from a `.env` onto a server. The Dockerfile and `apps/web`'s `start` script pin `NODE_ENV=production`; any other way of hosting the app must set it too. Downstream nothing is special-cased — the same `databaseHooks.user.create` hooks bootstrap the org and seed its tasks, and single-org mode's invite gate still applies to a password signup. The client learns it from `getPublicAppConfig().devAuth`, which also hides Preferences → Sign-in methods in production.
- **`/` never redirects, in any mode.** The landing page renders for everyone and its CTA resolves the destination (workspace / `/no-access` / `/login`).
- **`prompt: "select_account"` on the google provider is deliberate.** With no login screen there is nowhere to offer "use a different account".
- `session.freshAge: 0` — better-auth 403s `SESSION_NOT_FRESH` on unlink-account once a session is older than a day, and this app has no step-up re-auth flow, so integration disconnects would break.
- Invite context rides through as query params and is rebuilt into the Google `callbackURL`. `redirect` is attacker-supplied in principle, so `api/login.ts` accepts only a same-site absolute path (`/…` but not `//…`).


## Single-organization mode

Setting `SINGLE_ORG_SLUG=<slug>` turns a deployment into a one-workspace, invite-only instance. Unset (the default) is the normal multi-tenant product, and every code path below is a no-op. It is a slug rather than a boolean so "which organization?" is never implicit.

- **The switch is `packages/core/src/lib/single-org.ts`** — server-only. The client never reads the env var: `apps/web/src/server/config.ts` (`getPublicAppConfig`) hands it the mode plus the org's name/logo/slug.
- **The signup gate is a `databaseHooks.user.create.before` hook, not a screen.** Signing in with Google *is* the signup, and the user is created mid-OAuth-callback. The hook throws an `APIError` carrying a `code` (`INVITE_ONLY`) — that field is load-bearing, since better-auth's OAuth callback only turns a thrown error into a redirect back to `errorCallbackURL` when one is set, and otherwise surfaces a raw 403 mid-round-trip.
- **Bootstrap: the first person to sign in on an unclaimed instance creates the org and owns it.** The race is settled by the unique index on `organization.slug`, not a read-then-write check.
- **`allowUserToCreateOrganization: false` + `disableOrganizationDeletion: true`** are what actually close those endpoints; hiding the switcher's "New organization" item is presentation.
- **URLs keep the `/$orgSlug` prefix.** Tenancy stays an explicit parameter, matching the service-layer rule.
- **`/no-access` exists to break a redirect loop.** A signed-in user with no membership would otherwise bounce `/` → workspace → `/` forever. It lists their live invitations through a local server fn, because better-auth's `listUserInvitations` rejects any caller whose email isn't verified, and this app has no verification flow.

## Platform admins and impersonation

**A platform admin operates the deployment. An org admin administers one workspace. They are different people, different columns and different grants, and nothing in the product turns one into the other.**

- **`user.role` vs `member.role`.** An org admin is a `member` row — one per person per organization, granted from Settings → People by anybody who already administers that workspace. A platform admin is `user.role = 'platform_admin'`, one value per person for the whole instance. The role string is not better-auth's default `admin` precisely because `member.role === "admin"` already exists in this codebase.
- **The only grant is `PLATFORM_ADMIN_EMAILS`**, a comma-separated list. No screen, no server function and no service writes that column from a request. That is the point: the capability is impersonation — becoming any user in any workspace — so it must not be reachable by anybody who has talked their way into administering one organization.
- **It is applied at sign-in, in both directions** (`databaseHooks.session.create.before` → `reconcilePlatformRole`). A sign-in is the only moment the app is holding a user row and has a reason to look at it, and an env var only changes when the deployment restarts anyway. Two consequences: a newly listed address gets the role on its owner's next sign-in, and a newly *unlisted* one keeps it until theirs. To revoke now, delete that user's `session` rows.
- **better-auth's `admin` plugin provides the endpoints** (`packages/core/src/auth/index.ts`). Its `roles` map must name `platform_admin` explicitly — `adminRoles` alone only says which roles may not be impersonated, and a role missing from `roles` fails every permission check closed, so the endpoint would 403 for exactly the people it was added for. The plugin's other endpoints (ban, set-role, create-user, list-users) are mounted too and cannot be dropped individually; nothing in the UI calls them, and none of them is an escalation past impersonation.
- **Starting it swaps the session cookie and keeps the operator's own in a second one.** `admin/impersonate-user` writes an `admin_session` cookie holding the original token; `admin/stop-impersonating` reads it back, deletes the borrowed session and restores the original. So there is no impersonating from inside an impersonation — a second hop would overwrite the way back — and Settings → People hides the button while one is live.
- **Both ends do a full document load** (`apps/web/src/lib/impersonation.ts`), never a router invalidation. The organization, the role, `myAccess` and the assistant flag are resolved once in `/$orgSlug`'s `beforeLoad`, and the query cache is keyed by org slug rather than by person, so a soft refresh would draw the previous person's cached timesheet under the new name.
- **The sidebar says so, on every route, and cannot be dismissed** (`ImpersonationRow` in `app-sidebar.tsx`). Nothing else about the app changes while impersonating — looking at exactly what that person sees is the whole reason the feature exists.
- The impersonated session is a real `session` row with an hour's expiry and `impersonatedBy` set to the operator's user id. `enterOrganization` turns that into the `impersonating` route-context value.
- **PostHog identifies the impersonated person, not the operator**, because the session is theirs — so without help, an operator's clicks land on somebody else's analytics profile and read as their own work. Two things fix that, and neither is a person property: a person property persists, so the first impersonation would mark the real user as impersonated for good.
  - **Every browser event carries `impersonated` and `impersonated_by`** while one is live — super properties registered in `PostHogIdentity` (`routes/__root.tsx`) and unregistered when it ends. Attached to the events rather than to the person, which is the shape of the fact.
  - **The ledger is `impersonation_started` and `impersonation_stopped`**, captured on the server in `routes/api/auth/$.ts` through `lib/posthog-impersonation.ts`. That route is the only mount of `auth.handler`, so every impersonation passes through it whoever called it; the ids come from the session row and from better-auth's own answer, never from what the browser said. Both entries go on the OPERATOR's distinct id, with `impersonated_user_id` as a property — an audit trail answers "what has this administrator done", and the operator is the one identity that is the same person before, during and after.
  - The `capture` calls in `server/*.ts` are the gap: they name the impersonated person and carry no tag, because `orgMiddleware` hands a handler the service `ctx` and not the session. They sit between two ledger entries on the same user, so the question is still answerable, by a time window rather than by a filter.
