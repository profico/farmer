# Authentication

**Sign-in is Google, the OpenID Connect sources on Infrastructure → Sign-in, and a password for one person only.** All of it comes from the instance settings (ADR 0004): `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, the `instance_oauth_provider` rows, `REGISTRATION_OPEN` and `SINGLE_ORG_SLUG`. The environment still wins over the page.

- **`packages/core/src/auth/sign-in-methods.ts` is the one answer to "what is configured".** `signInProviders()` is Google when both halves are set, then each enabled OIDC source. The auth instance, `getPublicAppConfig().signInProviders` and the password gates all read it, so they cannot disagree.
- **A provider is registered only when it is configured.** Google, GitHub and the `google-calendar` grant used to be registered with `process.env.X!` whether or not X was set.
- **An OIDC source is a `genericOAuth` entry** (`oidcProvider` in `auth/index.ts`): `discoveryUrl` is the base URL plus `/.well-known/openid-configuration` unless it already ends with that path, the scopes default to `openid email profile`, and PKCE is on. The provider registers `{origin}/api/auth/oauth2/callback/{providerId}` (better-auth 1.6.23, `plugins/generic-oauth/routes.mjs`). It is not a trusted provider for account linking, so a sign-in links to an existing account by email only when the source says the email is verified. The source's "verifies email addresses" switch (`trustsEmail`, off by default) is for an identity provider that leaves the `email_verified` claim out, such as Entra ID: `mapProfileToUser` then marks every address it hands out as verified.
- **A source's issuer is fixed while accounts are linked through it.** An account is found by the provider's subject and `providerId`, and a subject is only unique inside one issuer, so `updateOAuthProvider` refuses a new base URL while `account` rows carry its `providerId`. Deleting a source deletes those rows, and a source added again links each person again by a verified address.

## The instance is rebuilt, not restarted

**Saving a provider needs no restart** (the open question in issue #75). better-auth takes its providers once, when the instance is built, so `auth/index.ts` builds it in `buildAuth()` and rebuilds it when an input changes.

- **The exported `auth` is an object of getters**, one per key of the better-auth type (`handler`, `api`, `options`, `$context`, `$ERROR_CODES`, `$Infer`), each reading the current build. The type is the inferred better-auth type, so no caller changed. Not a Proxy: a Proxy trap needs `Reflect.get` or a cast, and this way a key better-auth adds later is a compile error here.
- **In the process that saves the change, the rebuild is immediate:** the write forces a settings refresh, and `onInstanceSettingsChanged` rebuilds. **Another process** (the worker, a second replica) rebuilds at its next refresh, within the refresh interval (five seconds).
- **Each read also compares the inputs** (`liveAuth()`), because the first settings load fires no listener and the module can be imported before it.
- **Do not keep `auth.api` in a variable.** Read it through `auth` each time, or you hold the build of that moment.
- `bun run auth:generate` imports the module with no settings loaded, so it builds from the environment only. No provider changes the schema, so the output does not change.

## Registration closes after the first account

**Issue #75, decision 3: the first account configures the instance, then registration closes.** The gate is `assertMayRegister` (`auth/registration.ts`), called from `databaseHooks.user.create.before`, because signing in with a provider IS the signup: the user row is made in the middle of the OAuth callback. In order:

1. Single-org mode with its organization claimed: an invitation to that organization, or `INVITE_ONLY`. `REGISTRATION_OPEN` does not widen it.
2. A password signup outside development: the first account only.
3. No `user` row yet: allowed. The account becomes the platform admin (`claimPlatformAdmin`).
4. A pending invitation in any organization (matched without case), for a verified address: allowed.
5. `REGISTRATION_OPEN`: allowed.
6. Otherwise `REGISTRATION_CLOSED`.

- **The `code` on the thrown `APIError` is load-bearing.** Both OAuth callbacks (the social one and genericOAuth's) turn a thrown `APIError` into a redirect to `errorCallbackURL` only when it has a `code`, with the message as `error_description`. Without it the visitor gets a raw 403 in the middle of the round trip. `/login` has a title and a sentence for `REGISTRATION_CLOSED`, `INVITE_ONLY`, better-auth's `account_not_linked` and the admin plugin's `BANNED_USER`, and a generic sentence for any other code. It never shows `error_description`: anybody can put one in a link to `/login`, and the page would show it as its own text.
- **An invitation needs a verified address** (`mayClaimInvitation`). It is matched by address alone, and an OIDC source with open self-registration hands out any address unverified. The same rule guards accepting one (`requireEmailVerificationOnInvitation`) and listing one on `/no-access`. Development is the exception: no password account there is ever verified.
- **The gate applies in development too.** A second password account on a checkout needs an invitation or `REGISTRATION_OPEN=true`.
- "No user yet" is a read before a write. Two first signups in the same instant can both pass; the second is an ordinary account, because the admin role goes to the oldest row only.

## The first account, with no provider configured

**A new deployment has no provider, so the first account signs up with a password.** This is the only way a password account is made outside development.

- **`emailAndPassword` is on in every environment, and two gates close it in production** (the comment on `emailAndPassword` in `auth/index.ts`):
  - `/sign-up/email` works only while the `user` table is empty. `hooks.before` refuses it earlier than better-auth's "user already exists" check, so a visitor cannot find out which addresses have an account.
  - `/sign-in/email` works only for a **platform admin who has no configured provider connected** (`mayUsePassword`). It is checked in `databaseHooks.session.create.before`, after the password is verified, so a wrong password gets better-auth's usual answer and only the holder of the right one learns that the door is closed.
- **So the password is not a second way in.** Nobody after the first account gets a password. The first account's password closes when it connects a provider that is configured. The restriction to platform admins stops a database copied from development, full of password accounts, from opening a door for each of them.
- **Why the password does not close when a provider is saved.** A provider with a wrong secret would then lock out the only administrator, and the way back would be SQL. It closes when the administrator proves a provider works for them by connecting it.
- **Why the administrator connects it in Preferences, not by signing in.** better-auth links a provider sign-in to an existing account by email only when the local email is verified (`requireLocalEmailVerified`), and a password signup is not. Turning that off would let a provider that vouches for any address take over an account. So Preferences → Sign-in methods now renders for every account that holds a password, with a Connect button for Google and each OIDC source. A provider sign-in before that fails with `account_not_linked`, and `/login` says what to do.
- **`/login` in production:** no user → "Set up Farmer" and the first-account form; no provider and an administrator with a password → "Sign-in is not configured yet" and the sign-in form; providers and such an administrator → the buttons and an "Administrator: sign in with your password" link; providers only → the buttons. `getPasswordSignIn` (`server/config.ts`) answers which, apart from `getPublicAppConfig` because it reads the database.

## The login routes

- **`routes/login.tsx` bounces straight to Google when Google is the only way in** and there is no password form, as it always did. Otherwise it renders: a button per provider, Google as an anchor to `/api/login`, an OIDC source through the client's `signIn.oauth2({ providerId, callbackURL, errorCallbackURL: "/login" })`. A page route on purpose: every `redirect({ to: "/login" })` and sign-out points at it, and its `beforeLoad` runs server-side and in the browser.
- **`routes/api/login.ts` is the Google leg.** It asks better-auth for the Google authorize URL and re-shapes that 200-plus-`Location` response into a real 302, copying the OAuth state/PKCE cookie across, so an unauthenticated document request reaches Google without the app hydrating. Without Google it sends the visitor to `/login` with the same parameters; `/login` sends a visitor here only when Google is configured, so the two cannot loop.
- **`?error=…` always renders.** It is better-auth's `errorCallbackURL`; redirecting would bounce a refused visitor between `/login` and the provider forever.
- **`api/mcp-login.ts` hands the MCP authorize request to `/login`**, not `/api/login`, so a person can choose a provider.
- **`lib/dev-auth.ts` turns the full email + password form on in development.** The gate is `NODE_ENV` being `development` or `test`, and deliberately **not** an opt-in env var, which could be copied from a `.env` onto a server. It fails closed: `vite dev` sets `development` itself and `bun test` sets `test`, and anything else — including an unset `NODE_ENV` on a hand-started server — leaves only the production gates above. The Dockerfile and `apps/web`'s `start` script still pin `NODE_ENV=production`, which the PostHog gate needs (see `docs/domains/deployment.md`). The client learns it from `getPublicAppConfig().devAuth`.
- **`HOMEPAGE_ENABLED` decides what `/` is, in every mode — not single-org mode.** On, `/` renders the product page for everyone, and its CTA resolves the destination (workspace / `/no-access` / `/login`). Off (the default), `/` redirects: to the one workspace in single-org mode, else to the `_` placeholder, which the `/$orgSlug` guard below resolves. A signed-out visitor on a Google-only instance therefore goes from `/` straight to Google. `/privacy`, `/terms` and the other public pages render in every mode. The reader is `getHomeRedirect` in `apps/web/src/server/config.ts`.
- **`prompt: "select_account"` on the google provider is deliberate.** When Google is the only way in there is no login screen, so there is nowhere else to offer "use a different account".
- `session.freshAge: 0` — better-auth 403s `SESSION_NOT_FRESH` on unlink-account once a session is older than a day, and this app has no step-up re-auth flow, so integration disconnects would break.
- Invite context rides through as query params and is rebuilt into the Google `callbackURL`. `redirect` is attacker-supplied in principle, so `api/login.ts` and `login.tsx` accept only a same-site absolute path (`safeRedirectPath` in `lib/org-redirect.ts`: `/…` but not `//…` or `/\…`).

## Links that name no workspace

**`/:org/settings` (or `/_/settings`) opens the settings page in whichever workspace the reader works in.** `lib/org-redirect.ts` owns the placeholders; neither can be a real slug, because the server refuses any slug that `slugify` would not make (only `[a-z0-9-]`).

- **A slug is never a page of the app.** `/<slug>` shares the first path segment with `/about`, `/login`, `/api` and the rest, and the router prefers the static route, so an organization called "About" would never reach its own workspace. `RESERVED_SLUGS` (`packages/core/src/lib/slug.ts`) lists every top-level route, the directories under `public/` and a few names kept free for later. `apps/web/src/lib/reserved-slugs.test.ts` fails when a new top-level route is missing from it. better-auth's `beforeCreateOrganization` hook moves a reserved slug to the next free one (`about-1`), the same as signup's `uniqueSlugFor`, and refuses a malformed one; `beforeUpdateOrganization` refuses both. Infrastructure → Sign-in refuses a reserved `SINGLE_ORG_SLUG`, but a value from the environment is not checked, so the operator must not set one there.

- **`/$orgSlug`'s guard resolves it**, from the answer `enterOrganization` gives: `signed-out` goes to `/login?redirect=<the page>`, so the link survives the Google round trip; `elsewhere` resolves a placeholder straight to the reader's only workspace with the rest of the path kept, and sends everything else to `/choose-organization` — a real slug the reader cannot open goes there even with one workspace, so the page can say why instead of rewriting the link in silence. With no workspace it goes to `/no-access?redirect=<the page>`, whose sign-out keeps the link. In single-org mode `enterOrganization` reports no other workspace, so a non-member always lands on `/no-access` (an `onlySlug` pointing outside the one workspace looped between the two slugs).
- **A slug the reader cannot open takes the same path as a placeholder.** No such workspace and not a member are still one answer, so this is not a way to probe which slugs are taken. The chooser says which slug did not open.
- **`enterOrganization` uses `optionalSessionMiddleware`, not `sessionMiddleware`.** `requireSession` redirects to `/login` with no `redirect`, because a server function cannot see the page that called it. That is what used to send a shared workspace link to the workspace's home after sign-in.
- **`/choose-organization` sits outside `/$orgSlug`** (`docs/images/workspace-chooser.png`): the frame and the field with one island in it, and no sidebar, because there is no workspace yet. It lists `orgContextService.organizationsFor`, adds a search box above three workspaces, and skips itself when there is only one.


## Single-organization mode

Setting `SINGLE_ORG_SLUG=<slug>` (in the environment or on Infrastructure → Sign-in) turns a deployment into a one-workspace, invite-only instance. Unset (the default) is the normal multi-tenant product, and every code path below is a no-op. It is a slug rather than a boolean so "which organization?" is never implicit.

- **The switch is `packages/core/src/lib/single-org.ts`** — server-only, and read per call through `setting("SINGLE_ORG_SLUG")`. The client never reads the setting: `apps/web/src/server/config.ts` (`getPublicAppConfig`) hands it the mode plus the org's name/logo/slug.
- **The signup gate is step 1 of the registration gate above.** Once the organization exists, only an invitation to it lets a new account in (`INVITE_ONLY`).
- **Bootstrap: the first account on an unclaimed instance creates the org and owns it.** The race is settled by the unique index on `organization.slug`, not a read-then-write check. An unclaimed organization no longer means "open to anybody": on a populated instance the general gate applies, so the mode switched on later cannot hand the organization to a stranger.
- **`allowUserToCreateOrganization: false` + `disableOrganizationDeletion: true`** are what actually close those endpoints; hiding the switcher's "New organization" item is presentation.
- **URLs keep the `/$orgSlug` prefix.** Tenancy stays an explicit parameter, matching the service-layer rule.
- **`/no-access` exists to break a redirect loop.** A signed-in user with no membership would otherwise bounce `/` → workspace → `/` forever. It lists their live invitations through a local server fn, because better-auth's `listUserInvitations` rejects any caller whose email isn't verified, and a development password account never is. The server fn still asks for a verified address outside development.

## A Harvest import's pending claims

**In multi-org mode, a membership that a Harvest import made is a pending claim until the person accepts it.** For a person whose address has no account yet, usually a former employee, the import creates a placeholder `user` (never a row that holds the address, see `docs/domains/harvest-import.md`) and a `member` row. The owner of that address signs in as a new user, and the claim below moves the history to them. For an address that has an account, the import attaches that user, so without a claim they were a member of the importing organization and nobody had asked them.
- **A placeholder claim needs a verified address** (`mayClaimInvitation`). `importClaimsService.pendingFor` lists it, `accept` moves the rows to the caller and `decline` keeps the history under the placeholder (`declinedAt`). A caller who is a member already merges: their membership stays, and the day cap does not refuse the moved entries.

- **The organization sees nothing different.** People, the reports and the archived former employees read the row as before.
- **The person cannot open the organization.** `memberProfile.claimPendingSince` is the one fact. `accessService.resolve` throws `NotAMemberError`, `membersService.getRole` answers null (the `/$orgSlug` guard), `orgContextService.organizationsFor` leaves it out (the chooser, the sidebar switcher, `farmer login`), and the session hook and `getDefaultOrgSlugForSession` never pick it. Reminders hold it back (`claim-pending` in `deliveryBlocks`).
- **`/no-access` offers Join and Decline** (`importClaimsService`, through `server/organization.ts`). Join clears the column and runs `memberJoined`: the `member.joined` audit row, the Slack match and `member.added` that accepting an invitation runs. Decline deletes the `member` row and clears the column: the profile and the time entries stay as the organization's history.
- **The sidebar switcher reads `listMyOrganizations`, not better-auth's `organization.list`.** That endpoint lists every `member` row, so it offered a pending organization only for the guard to send the person away from it.
- **The organization still sees the person.** People lists them with "Not joined yet" (`PersonRow.claimPending`), and reports count their imported hours.
- A person who has another workspace lands there, and sees the claim only on `/no-access`. Nothing links there from inside a workspace yet.

## Platform admins and impersonation

**A platform admin operates the deployment. An org admin administers one workspace. They are different people, different columns and different grants, and nothing an org admin can reach turns one into the other.**

- **`user.role` vs `member.role`.** An org admin is a `member` row — one per person per organization, granted from Settings → People by anybody who already administers that workspace. A platform admin is `user.role = 'platform_admin'`, one value per person for the whole instance. The role string is not better-auth's default `admin` precisely because `member.role === "admin"` already exists in this codebase.
- **The instance's first account holds it, and a platform admin grants it to anybody else.** On a new deployment that first account is usually the password account above. Coolify's model, and the one issue #75 records for this repository: a person who deploys Farmer should be able to run it without being told to edit an environment variable and restart. There is no environment variable — the grant is a database value, so it survives a redeploy.
- **The bootstrap is `claimPlatformAdmin`** (`databaseHooks.user.create.after`). The rule is "the oldest `user` row, and only while nobody holds the role", which is not the same as "nobody holds the role": an open deployment accepts a Google sign-up from anybody, so granting it to whoever signs in next when the role is vacant hands the instance to a stranger the moment its one admin is deleted. Being the oldest row is something a later signup can never become. It runs after the insert, inside a `pg_advisory_xact_lock`, so two first signups a millisecond apart cannot both read an empty table and both grant. Existing deployments got the same rule once, from migration `0059`.
- **Promotion is better-auth's `admin/set-role`**, which itself needs the role it grants. The screen for it is Infrastructure → Platform admins (`apps/web/src/routes/infrastructure/`), reached from the Instance section of the settings hub and gated on `platformAdminMiddleware`. `setPlatformAdmin` (`server/platform-admins.ts`) routes the write through the plugin rather than writing the column, so the app never has two writers with two ideas of who may write, and adds two refusals the plugin does not make: nobody demotes themselves, and the instance never reaches zero platform admins.
- **The page lists the admins and finds everybody else by search.** On a multi-tenant instance the `user` table is every customer's staff directory, so rendering it to fill in a promote screen turns one grant into a readable roster of the whole deployment. `platformAdminsService.search` answers a name somebody already has: two characters minimum, ten results, enforced server-side so an empty box cannot be made to mean "everybody".
- **It is a settings page like every other one**, at `/$orgSlug/settings/platform-admins`, under a third group called Infrastructure beside Account and Workspace. The data is the instance's rather than the workspace's, but that is a fact about the data and not a reason for its own chrome: somebody looking for it goes to Settings. The group is one row in `SETTINGS_ENTRIES` (`components/settings-nav.tsx`), so the hub, the sidebar's sub-menu and the phone's More sheet all draw it from the one catalogue — that file exists precisely so a new page cannot reach one surface and miss the others. Issue #75's further entries (email, S3, the OAuth sources) join the same group.
- **The trade this makes.** The database is now the root of trust, not the deployment's environment. A compromised platform admin can promote an accomplice and demote you, and the way back is SQL against the `user` table. An org admin still cannot escalate — nothing a workspace's owner can reach writes that column.
- **better-auth's `admin` plugin provides the endpoints** (`packages/core/src/auth/index.ts`). Its `roles` map must name `platform_admin` explicitly — `adminRoles` alone only says which roles may not be impersonated, and a role missing from `roles` fails every permission check closed, so the endpoint would 403 for exactly the people it was added for. The plugin's other endpoints (ban, set-role, create-user, list-users) are mounted too and cannot be dropped individually; nothing in the UI calls them, and none of them is an escalation past impersonation.
- **Starting it swaps the session cookie and keeps the operator's own in a second one.** `admin/impersonate-user` writes an `admin_session` cookie holding the original token; `admin/stop-impersonating` reads it back, deletes the borrowed session and restores the original. So there is no impersonating from inside an impersonation — a second hop would overwrite the way back — and Settings → People hides the button while one is live.
- **Both ends do a full document load** (`apps/web/src/lib/impersonation.ts`), never a router invalidation. The organization, the role, `myAccess` and the assistant flag are resolved once in `/$orgSlug`'s `beforeLoad`, and the query cache is keyed by org slug rather than by person, so a soft refresh would draw the previous person's cached timesheet under the new name.
- **The sidebar says so, on every route, and cannot be dismissed** (`ImpersonationRow` in `app-sidebar.tsx`). Nothing else about the app changes while impersonating — looking at exactly what that person sees is the whole reason the feature exists.
- The impersonated session is a real `session` row with an hour's expiry and `impersonatedBy` set to the operator's user id. `enterOrganization` turns that into the `impersonating` route-context value.
- **PostHog identifies the impersonated person, not the operator**, because the session is theirs — so without help, an operator's clicks land on somebody else's analytics profile and read as their own work. Two things fix that, and neither is a person property: a person property persists, so the first impersonation would mark the real user as impersonated for good.
  - **Every browser event carries `impersonated` and `impersonated_by`** while one is live — super properties registered in `PostHogIdentity` (`routes/__root.tsx`) and unregistered when it ends. Attached to the events rather than to the person, which is the shape of the fact.
  - **The ledger is `impersonation_started` and `impersonation_stopped`**, captured on the server in `routes/api/auth/$.ts` through `lib/posthog-impersonation.ts`. That route is the only mount of `auth.handler`, so every impersonation passes through it whoever called it; the ids come from the session row and from better-auth's own answer, never from what the browser said. Both entries go on the OPERATOR's distinct id, with `impersonated_user_id` as a property — an audit trail answers "what has this administrator done", and the operator is the one identity that is the same person before, during and after.
  - The `capture` calls in `server/*.ts` are the gap: they name the impersonated person and carry no tag, because `orgMiddleware` hands a handler the service `ctx` and not the session. They sit between two ledger entries on the same user, so the question is still answerable, by a time window rather than by a filter.

## Mobile sign-in exchange

The mobile app's provider sign-in redirects to `farmer://auth-callback`. The
redirect carries a one-time code bound to a PKCE challenge, never the
session cookie. `auth/mobile-exchange.ts` is a better-auth plugin that must
stay after `expo()` in the plugin list of `buildAuth()`: it rewrites the link
that `expo()` wrote. The callback first sends the browser to a confirmation
page (`auth/mobile-confirm.ts`), and the code comes only after the person
continues there. The code, the endpoints and the limits are in
`docs/domains/mobile.md` (the sign-in exchange) and ADR 0005. The rows are in
the `verification` table with the identifier prefixes `mobile-exchange:`,
`mobile-confirm:` and `mobile-proxy:`.
