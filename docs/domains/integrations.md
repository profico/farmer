# Integrations (GitHub + Google Calendar + Slack)

GitHub and Google Calendar are per-member and opt-in via `integrationSettings` (a missing row = every toggle off, so connecting an account never silently enables background sync); Slack is per-org and admin-only. A person's own connections live on `$orgSlug/settings/integrations` (Account → Integrations, beside the MCP and CLI instructions); the workspace's GitHub App installations and Slack live on `$orgSlug/settings/workspace-integrations` (Workspace → Integrations, admin-only through `requireOrgAdmin`); the assistant's OpenRouter key lives on `$orgSlug/settings/ai` (Settings → AI). The two are split by scope, the same split the settings hub draws for every other page. The GitHub and Calendar token helpers check the `account` table first and return null when nothing is linked, rather than letting better-auth throw.

- **GitHub uses two distinct credential types, don't conflate them.** The per-user OAuth account link (`socialProviders.github`) is used **only for identity** — `GET /user` (resolve the login, to filter activity by author) and `GET /user/installations` (enumerate installations the person may connect). All repo, commit and pull request reads go through a **per-org GitHub App installation token** (`orgGithubInstallation`), obtained after an admin installs the App and GitHub redirects to `api/github/setup.ts`, which re-verifies admin role and resolves the org from a signed `state` (`lib/oauth-state.ts`: org, user and issue time, expiring after 15 minutes). The Slack callback refuses any request without a valid state. GitHub setup reads the active org only when no state was sent at all, because an App installed from GitHub's own UI arrives that way — and then connects nothing: a crafted link arrives the same way, so the installation id only goes on to Workspace → Integrations (`?githubInstallation=`), where the admin confirms it through the `connectGithubInstallation` POST server function, which names the workspace the page showed and is refused when the session's active one has moved. `connectInstallation` still re-verifies that the caller owns the installation's GitHub account (see the next point). Repo reads are scoped to the caller: `attachCommits` requires an assignment on each repo's project and a hex `sha`, `attachPullRequests` holds the same assignment line before any GitHub call, `suggestCommits` and `suggestPullRequests` read only the repos of projects the caller is assigned to, `listLinkedRepos` needs `canTrackOn` on the project and answers an empty list to a non-admin with no assignment on it (so the entry dialog never offers a commit picker that cannot fill), and listing every repo the App reaches, linking a repo and unlinking one are admin-only in the service itself. Settings: `GITHUB_CLIENT_ID/SECRET` (OAuth) are separate from `GITHUB_APP_ID/SLUG/PRIVATE_KEY` (the App). The private key is the PEM or its base64; `appPrivateKeyPem` tells them apart by the `-----BEGIN` line, because the environment has always held the base64 and the Infrastructure page takes the file as pasted. The cached App JWT is keyed by the App ID and the key, so a change on the page is not answered with a token of the App before it.
- **Only the owner of a GitHub account can connect its installation.** `connectInstallation` checks two things. First, the installation must be in `GET /user/installations`. GitHub lists an installation there for anybody with explicit read access to one repo it covers, so this check proves only that the caller can see it. Second, the caller must own the account the installation is on (`assertControlsAccount`): a personal account must be the caller, compared by GitHub's numeric user id, and an organization must answer `GET /orgs/{org}/memberships/{login}` with `state: "active"`, `role: "admin"` (an organization owner) and the caller's own numeric id. The user token only says who the caller is (`GET /user`); the membership is read with the installation's own token, so the check does not depend on what `GITHUB_CLIENT_ID` is, an OAuth app or a GitHub App. Any failure of that membership read is a refusal, and each kind (no permission or not a member, not an owner, a pending invitation, GitHub unreachable) has its own sentence. Without the second check, an outside collaborator could bind a company's installation to a workspace of their own and list every private repo it covers through the installation token. An organization member who is not an owner cannot connect, so an owner must do it.
- **Disconnecting is two acts, and the second is opt-in.** `disconnectInstallation` takes `uninstall`; ticked, it calls `DELETE /app/installations/:id` with the App JWT (`deleteInstallation`, `lib/github-client.ts`) after the row is gone. It is **refused when another workspace on the deployment still holds the same installation** — `ogi_org_installation_unq` is per org, so one GitHub account can be connected to several — and the outcome is REPORTED (`UninstallOutcome`), never thrown: a refused uninstall must not leave the admin still connected to something they just disconnected. GitHub's own settings page is always the other way to do it.
- **`api/github/webhook.ts` is the reverse direction, and the signature is the whole authorization.** The route is public — no session, no org, no CSRF token — so `verifyWebhookSignature` (HMAC-SHA256 over the **raw** body, constant-time compare) decides everything, and nothing in the handler reads an id from outside the verified payload. `installation.deleted` and `installation.suspend` call `githubService.forgetInstallation`, which drops **every** workspace's row for that installation: without it the row outlives the installation and every read fails against a dead id, while Integrations still shows the account as connected. `installation_repositories` only drops the repo-list cache. `forgetInstallation` and `forgetRepoList` take no `Ctx` on purpose — a webhook has no caller, and which orgs connected the installation is what they look up rather than what they are told. A deployment with no `GITHUB_WEBHOOK_SECRET` answers 503 (not 404, which reads as a wrong URL in GitHub's delivery log) and the feature is simply off. **Setup is a Webhook URL and a secret on the App, and nothing else** — both events are sent to every App and cannot be subscribed to, so an empty "Subscribe to events" list is not the fault when deliveries stop. GitHub's App settings → Advanced → Recent Deliveries is where a failing one is read: 503 is a missing secret on the server, 401 a mismatched one, 404 a deployment without this route.
- **The App needs "Contents: Read" and "Pull requests: Read", and the organization permission "Members: read".** Without the second, GitHub answers FORBIDDEN, which reads as "no activity" (as a 403 does on the commit path), so a missing permission is silent. The third is what lets `connectInstallation` read the caller's organization membership with the installation token. Without it GitHub answers 403, and connecting an installation on an organization is refused for everybody, owners included; installations on personal accounts do not need it. Adding a permission to an existing App makes every installation owner accept it on GitHub, and until an organization accepts "Members: read", nobody can connect its installation again.
- **The `repo` scope on the OAuth app looks removable and is not.** `GET /user/installations` works only for tokens carrying `repo`, and that call is the first half of the authorization gate in `connectInstallation`. Read the comment at the call site before touching the line.
- **The user token lives 8 hours, and its refresh token is single use.** `GITHUB_CLIENT_ID` is a GitHub App client id, so the account link holds a user-to-server token; each refresh spends the refresh token and returns a new pair. GitHub refuses a spent one with HTTP **200** and an `error` body (`bad_refresh_token`), which better-auth's default refresh reads as a success — so `refreshGithubToken` (`auth/index.ts`) overrides it, throws on a missing access token (the stored row stays as it was), logs `[github] GitHub refused the refresh token` with GitHub's `error` code, and stores the new refresh-token expiry. Two callers at the 8-hour boundary would still both spend the same token, so `getAccessToken` in `github.service.ts` shares one read per user. **That lock is per process**: with a separate worker container (`deployment.md`), the sweep and the web host can still race. The row stays safe, but the loser costs one refused refresh and the reconnect banner on that one request.
- **Google Calendar** is a per-user, read-only grant scoped to `calendar.events.readonly`, on a **separate `genericOAuth` provider (`"google-calendar"`)** rather than the login provider — so signing in never demands calendar access, and a plain login row can't be mistaken for a live calendar connection. It needs `accessType: offline` + `prompt: consent` to get a refresh token, or reads break after the ~1h access token expires. The client's `getCalendarEvent` (one event by id; 404/410 and `cancelled` are `absent`, any other non-answer `unreadable`, never a throw) is what the meeting engine calls before deleting a row whose event left the list — see `docs/domains/automation.md`. `syncedMeetingTombstone` records meetings the user deleted post-sync; `commitFillTombstone` is the same idea per *day and project* for the commit engine's blocks (no project means the whole day). Creating a fill block or Development time on that project deliberately clears the tombstone, since that is a change of mind. **Nothing writes to a calendar**, which is why the scope is read-only; a connection made before the scope narrowed keeps its wider grant until the person disconnects and connects again.
- **Slack** is one workspace per org (`slackInstallation`), installed by an admin through Slack's OAuth v2 flow. The bot token goes straight from Slack's answer to the database, sealed (`lib/secret-box.ts`, below) — no client, form or validator ever handles it, and no server function returns it. The redirect URI is derived once in `slackRedirectUri()` because Slack byte-compares it across the two legs. Membership hooks (`afterAcceptInvitation`, `afterAddMember`) auto-match new people to Slack; `linkMember` swallows its own errors, so a Slack outage costs the match, not the membership. "Re-match people" (`syncIdentities`) skips archived people but keeps their existing match. An invitation also goes out as a Slack DM (`slackService.sendInvitation`, from `sendInvitationEmail` in `auth/index.ts`) when the address maps to a Slack user — not awaited, never throws, and not recorded on `invitationEmail`. A `chat.postMessage` refusal is sorted by who it is about (`lib/slack-client.ts`): a recipient code (`user_not_found`, `channel_not_found`) makes that person unreachable for the day, and a credential code (`token_revoked`, `invalid_auth`, `not_authed`, `account_inactive`) sets `slackInstallation.tokenRejectedAt` through `slackService.rejectToken`. `installationFor` then reads the org as having no Slack, the reminder job ends the org's pass and counts the send as failed, and `status` answers `needsReconnect` with `reason: "rejected"`. An install clears the mark. A manager pings a person who is behind from the Tracking report: `slackService.pingBehind` sends a DM through `notify` (kind `ping`, which skips the reminder opt-out because a person chose to send it) and records `slack.pinged`. The `slack_ping` table holds the last ping for each person, and one conditional insert enforces the 24-hour cooldown, and `pingBehind` releases it when nothing was sent, also when the send throws. `slackService.pingStates` returns who the caller may ping (never a person that `deliveryBlocks` holds back, for example a pending import claim) and the org's current month, the only month `pingBehind` judges, so the screen shows the button for that month only. Settings: `SLACK_CLIENT_ID/SECRET`.
- **The app-level credentials are instance settings** (`lib/instance-settings.ts`, ADR 0004): each one is its environment variable when that is set, else the value a platform admin saved on the Infrastructure page. Read them with `setting(name)`, never `process.env`, or the page shows a value the process does not use. `GITHUB_WEBHOOK_SECRET` is one of them, so the 503 above also means nothing on the page.
- **Every stored credential is encrypted at rest, keyed from `BETTER_AUTH_SECRET`** (or from the current entry of `BETTER_AUTH_SECRETS`, when a rotation set is configured — see `docs/domains/deployment.md`). The GitHub and Calendar OAuth tokens through better-auth's `account.encryptOAuthTokens`; the Slack bot token, the assistant's OpenRouter key and every secret instance setting through `lib/secret-box.ts` (AES-256-GCM, stored as `enc:v1:…`, or `enc:v2:<version>:…` under a rotation set; `openAndHeal` reseals a value under an older version on its next read). Neither needed a migration, and both heal rows written before they existed: better-auth passes a value that does not look encrypted through as it is and `sealLegacyOAuthTokens` (`auth/legacy-tokens.ts`) encrypts it when the token helper next reads it; `openAndHeal` does the same for the other two in `slackService.installationFor` and the assistant's `loadSettings`. **Changing `BETTER_AUTH_SECRET` makes every stored credential unreadable** (rotate through `BETTER_AUTH_SECRETS` instead) — an OAuth link then reads as a refused token, and the Slack install and the OpenRouter key read as unusable until each is connected again. Both say so rather than reading as never connected: `slackService.status` goes through `installationFor` and answers `needsReconnect` (Workspace → Integrations badges it "Connect again" and offers "Add to Slack again"), and the assistant's `settings.get` answers `keyUnreadable`. A Settings tab that read only the row said "Connected" while every DM failed and the reminder job skipped the org.
