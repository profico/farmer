# Integrations (GitHub + Google Calendar + Slack)

GitHub and Google Calendar are per-member and opt-in via `integrationSettings` (a missing row = every toggle off, so connecting an account never silently enables background sync); Slack is per-org and admin-only. A person's own connections live on `$orgSlug/settings/integrations` (Account → Integrations, beside the MCP and CLI instructions); the workspace's GitHub App installations, Slack and the assistant's key live on `$orgSlug/settings/workspace-integrations` (Workspace → Integrations, admin-only through `requireOrgAdmin`). The two are split by scope, the same split the settings hub draws for every other page. The GitHub and Calendar token helpers check the `account` table first and return null when nothing is linked, rather than letting better-auth throw.

- **GitHub uses two distinct credential types, don't conflate them.** The per-user OAuth account link (`socialProviders.github`) is used **only for identity** — `GET /user` (resolve the login, to filter activity by author) and `GET /user/installations` (enumerate installations the person may connect). All repo, commit and pull request reads go through a **per-org GitHub App installation token** (`orgGithubInstallation`), obtained after an admin installs the App and GitHub redirects to `api/github/setup.ts`, which re-verifies admin role and resolves the org from a signed `state` (`lib/oauth-state.ts`: org, user and issue time, expiring after 15 minutes). The Slack callback refuses any request without a valid state. GitHub setup falls back only when no state was sent at all, because an App installed from GitHub's own UI arrives that way, and that is safe because `connectInstallation` re-verifies the installation against the caller's own GitHub account. Repo reads are scoped to the caller: `attachCommits` requires an assignment on each repo's project and a hex `sha`, `attachPullRequests` holds the same assignment line before any GitHub call, `suggestCommits` and `suggestPullRequests` read only the repos of projects the caller is assigned to, `listLinkedRepos` needs `canTrackOn` on the project, and listing every repo the App reaches, linking a repo and unlinking one are admin-only in the service itself. Env: `GITHUB_CLIENT_ID/SECRET` (OAuth) are separate from `GITHUB_APP_ID/SLUG/PRIVATE_KEY` (the App; private key is base64-encoded PEM).
- **Disconnecting is two acts, and the second is opt-in.** `disconnectInstallation` takes `uninstall`; ticked, it calls `DELETE /app/installations/:id` with the App JWT (`deleteInstallation`, `lib/github-client.ts`) after the row is gone. It is **refused when another workspace on the deployment still holds the same installation** — `ogi_org_installation_unq` is per org, so one GitHub account can be connected to several — and the outcome is REPORTED (`UninstallOutcome`), never thrown: a refused uninstall must not leave the admin still connected to something they just disconnected. GitHub's own settings page is always the other way to do it.
- **`api/github/webhook.ts` is the reverse direction, and the signature is the whole authorization.** The route is public — no session, no org, no CSRF token — so `verifyWebhookSignature` (HMAC-SHA256 over the **raw** body, constant-time compare) decides everything, and nothing in the handler reads an id from outside the verified payload. `installation.deleted` and `installation.suspend` call `githubService.forgetInstallation`, which drops **every** workspace's row for that installation: without it the row outlives the installation and every read fails against a dead id, while Integrations still shows the account as connected. `installation_repositories` only drops the repo-list cache. `forgetInstallation` and `forgetRepoList` take no `Ctx` on purpose — a webhook has no caller, and which orgs connected the installation is what they look up rather than what they are told. A deployment with no `GITHUB_WEBHOOK_SECRET` answers 503 (not 404, which reads as a wrong URL in GitHub's delivery log) and the feature is simply off. **Setup is a Webhook URL and a secret on the App, and nothing else** — both events are sent to every App and cannot be subscribed to, so an empty "Subscribe to events" list is not the fault when deliveries stop. GitHub's App settings → Advanced → Recent Deliveries is where a failing one is read: 503 is a missing secret on the server, 401 a mismatched one, 404 a deployment without this route.
- **The App needs "Contents: Read" and "Pull requests: Read".** Without the second, GitHub answers FORBIDDEN, which reads as "no activity" (as a 403 does on the commit path), so a missing permission is silent. Adding a permission to an existing App makes every installation owner accept it on GitHub.
- **The `repo` scope on the OAuth app looks removable and is not.** `GET /user/installations` works only for tokens carrying `repo`, and that call is the authorization gate in `connectInstallation`. Read the comment at the call site before touching the line.
- **Google Calendar** is a per-user, read-only grant scoped to `calendar.events.readonly`, on a **separate `genericOAuth` provider (`"google-calendar"`)** rather than the login provider — so signing in never demands calendar access, and a plain login row can't be mistaken for a live calendar connection. It needs `accessType: offline` + `prompt: consent` to get a refresh token, or reads break after the ~1h access token expires. The client's `getCalendarEvent` (one event by id; 404/410 and `cancelled` are `absent`, any other non-answer `unreadable`, never a throw) is what the meeting engine calls before deleting a row whose event left the list — see `docs/domains/automation.md`. `syncedMeetingTombstone` records meetings the user deleted post-sync; `commitFillTombstone` is the same idea per *day* for the rest-of-day block. Creating a fill block deliberately clears the tombstone, since that is a change of mind. **Nothing writes to a calendar**, which is why the scope is read-only; a connection made before the scope narrowed keeps its wider grant until the person disconnects and connects again.
- **Slack** is one workspace per org (`slackInstallation`), installed by an admin through Slack's OAuth v2 flow. The bot token goes straight from Slack's answer to the database, sealed (`lib/secret-box.ts`, below) — no client, form or validator ever handles it, and no server function returns it. The redirect URI is derived once in `slackRedirectUri()` because Slack byte-compares it across the two legs. Membership hooks (`afterAcceptInvitation`, `afterAddMember`) auto-match new people to Slack; `linkMember` swallows its own errors, so a Slack outage costs the match, not the membership. "Re-match people" (`syncIdentities`) skips archived people but keeps their existing match. An invitation also goes out as a Slack DM (`slackService.sendInvitation`, from `sendInvitationEmail` in `auth/index.ts`) when the address maps to a Slack user — not awaited, never throws, and not recorded on `invitationEmail`. Env: `SLACK_CLIENT_ID/SECRET`.
- **Every stored credential is encrypted at rest, keyed from `BETTER_AUTH_SECRET`.** The GitHub and Calendar OAuth tokens through better-auth's `account.encryptOAuthTokens`; the Slack bot token and the assistant's OpenRouter key through `lib/secret-box.ts` (AES-256-GCM, stored as `enc:v1:…`). Neither needed a migration, and both heal rows written before they existed: better-auth passes a value that does not look encrypted through as it is and `sealLegacyOAuthTokens` (`auth/legacy-tokens.ts`) encrypts it when the token helper next reads it; `openAndHeal` does the same for the other two in `slackService.installationFor` and the assistant's `loadSettings`. **Changing `BETTER_AUTH_SECRET` makes every stored credential unreadable** — an OAuth link then reads as a refused token, and the Slack install and the OpenRouter key read as unusable until each is connected again. Both say so rather than reading as never connected: `slackService.status` goes through `installationFor` and answers `needsReconnect` (Workspace → Integrations badges it "Connect again" and offers "Add to Slack again"), and the assistant's `settings.get` answers `keyUnreadable`. A Settings tab that read only the row said "Connected" while every DM failed and the reminder job skipped the org.
