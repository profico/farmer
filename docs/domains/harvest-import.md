# The Harvest import

An admin drops the Harvest CSV exports on Settings → Import (`settings/import.tsx`); `harvest-import.service.ts` writes them.
- **Parsing and planning run in the browser, in a Web Worker** (`components/import/harvest.worker.ts`, on `packages/core/src/lib/harvest/`). A real export is ~240k rows: the Worker keeps the day chunks and the page holds only the review, because a structured clone of every row on each re-plan would freeze the tab. The server takes the plan in steps — `start` (clients, tasks, people, projects), `importDays` in chunks of `HARVEST_CHUNK_MAX_ROWS`, `removeDays`, `finish` — and every step is safe to repeat, so "Retry" continues from the cursor. `start` is made repeatable by a run id the browser generates once per attempt: a second `start` with the same id returns the run it already created.
- **The unit is a person-day, compared by digest.** A day already imported unchanged is skipped, a changed one replaced, and a day somebody edited here is **kept**, never overwritten. A day the file no longer has is removed only when the admin confirms the file is a full export. That is what makes dropping the same files twice a no-op.
- **`finish` moves `automationLockedThrough` to the day before the cutoff**, so no engine writes into imported history, and prefills the hour fund for every year with history, because Expected needs it.
- **A guessed email makes an archived person with `emailUnconfirmed`.** A Harvest person with no address gets `first.last@domain`; they cannot sign in until an admin confirms the address on People (Restore for an archived person, "Confirm email" for an active one), since a wrong guess is otherwise somebody else's login. An address the admin **typed** on the review screen is not a guess: it counts as confirmed (`emailConfirmed` on the person plan).
- **With several organizations, an import never writes a real address into `user` (issue #162).** For an address with no account, `start` makes a placeholder `user` (`import-<id>@import.invalid`, `emailVerified` false, `lib/import-placeholder.ts`) and keeps the address in `import_pending_person`. The client's `emailConfirmed` reaches no user row there. better-auth 1.6.23 refuses an OAuth link to an unverified local row (`requireLocalEmailVerified`, one static boolean per deployment), so a real unverified row would refuse the owner's first sign-in (`account_not_linked`). The placeholder matches no sign-in, so it blocks nobody. Every read the org sees uses `shownEmail()` (`services/claim-name.ts`) in place of `user.email`. `sendMail` and the Slack lookup refuse a placeholder address. The owner claims the history on `/no-access` with a verified address (`importClaimsService`): every row the org wrote for the placeholder moves to the owner's own user, and the placeholder goes. The list of moved tables, and why the others are not moved, is in `import-claims.service.ts`. Single-org mode keeps the old path: the instance owner controls every user. Rows an earlier version made with a real address and `emailVerified` false are not repaired yet (follow-up).
- **With several organizations, `start` gives the same answer for an address with an account and for one without.** Any workspace admin may call it, and the `user` table holds the people of every workspace, so an answer that depends on whether the user exists lets an admin probe addresses (issue #158). A people-list address, a typed address and a guess all take one path: the existing user, or a new one, gets a `member` row with `memberProfile.claimPendingSince`, plus a profile, a type history, assignments and hours. No invitation is written and no email goes out, `start` returns no `invited` list, and the snapshot reports `hasAccount: false` for a pending claim. Only single-org mode refuses an address that is not on the people list when a user holds it (`takenEmails` answers there for the same reason, and stays empty elsewhere). While the claim is pending, every read the org sees shows `memberProfile.claimName` (the name the import gave) in place of the global `user.name`, no image, and a fixed `emailUnconfirmed` (`shownName` and `shownImage` in `services/claim-name.ts`; use them in a new read). Confirming the address of a pending person gives one refusal. After the person accepts, the org sees the real values.
- **With several organizations, a person the import adds must accept the workspace.** Their membership carries `memberProfile.claimPendingSince`: the org sees them as usual, but the person cannot use the org until they choose Join on `/no-access`, or Decline, which removes the membership and leaves the hours as the org's history. Single-org mode attaches a listed address's user directly, because every user there came in through an invitation to the one organization.
- **Undo removes exactly what `importMapping` says the run created** — and only for the latest run. A user row the run made goes only when no other organization holds a `member`, `member_profile`, `time_entry`, `project_member`, import mapping or invitation for that user; the foreign keys cascade, so the delete would take that data. Otherwise undo removes only this org's rows, as for an attached user. Runs from before #158 may hold invitations: undo cancels the ones the run wrote (by the recorded ids, so a pending invitation the People page sent the same address later stays), and keeps the membership of a person who accepted. An attached user who accepted a pending claim keeps the membership, profile and assignments too (`claimName` stays set, and undo reads it); only the run's entries and mappings go. A run from before the ids were recorded has no `invitation` rows, and undo falls back to matching by address and by a creation time not older than the run. It does not restore days the run replaced, does not move the lock back, and refuses outright once a created person has signed in or an entry made here uses a created row.
- **Two questions block the plan until the admin answers them on the review screen**, because neither has a safe default:
  - **Names that differ only in accents or punctuation** ("Tin Primjerić" / "Tin Primjeric") — one person or different people (`choices.duplicates`, keyed on the ASCII fold). "One person" merges the spellings into the chosen one, and the other gets an `alias` person plan: `start` maps it to the same user, not `created`, so undo removes only the mapping. A group whose every spelling an earlier run mapped is not asked again — one user is one person, two users stay two.
  - **Negative correction rows** — `subtract` takes each off the row with the same person, day, project, task and overtime flag (an exact match first, then the largest), rounds the rest again and gives it a new `…:net` key; `leave_out` imports the other rows as they are. The keys differ, so changing the answer later replaces those days on the next run. A correction with no row big enough to take from stays under "needs attention" either way.
- Rows of two source people who are one user here (an alias, or two names matched to one member) are one person-day in the plan, as `importDays` groups them, so the digest covers the same rows as the stored one.
